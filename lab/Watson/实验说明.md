## 真实 demo：DeepSeek Flash（新增）

### 目标、模型与 Agent

新增 `run_real_demo.py` 调用 DeepSeek 官方 `https://api.deepseek.com/chat/completions`，不再使用假客户端。密钥名称按用户提供的信息记为 Watson，密钥值不写入代码或报告。

请求模型为用户指定的 `deepseek-v4-flash`。2026-09-20 核对的[官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)说明该旧名称当前由 DeepSeek-V4.1-Flash 提供服务；因此这不是固定旧版 V4 权重的实验。每次运行保存实际返回的 model 字段。

四个逻辑角色均调用该接口：主 Agent 先直接做决策；替身根据相同任务独立生成简短解释和答案；judge 检查解释与选中组件的一致性；汇总角色概括接受的解释。主 Agent 是脚本驱动的最小文本决策 Agent，没有外部工具、多轮规划或真实仓库操作。

### 任务与执行顺序

两个自建任务：库存决策（实物 12、预留 5、可用 7，低于 10 应 REORDER）；服务决策（当前健康检查失败且维护模式关闭，应 RESTART，昨日正常日志为干扰信息）。正确答案由规则预先定义，但不送入生成提示。主 Agent 的答案由真实 API 返回，不由脚本代填。

每个任务执行：主 Agent 调用 → 原始输入/输出落盘 → 两个组件各消融一次 → 独立生成候选 → 严格 FINAL 答案匹配 → YES/NO judge → 汇总。每任务接受目标 k=1，最多生成 4 个候选。只有主 Agent 已完成后才开始该任务的 Watson 旁路处理。新的输入输出直接由 demo 采集，不依赖当前缺失 request 的 AgentSight 数据库，也没有执行 eBPF 采集。

主 Agent、替身、消融、judge 和汇总均为 temperature=0、top_p=1、thinking.type=disabled、max_tokens=256。非思考模式下 top_p 的有效行为以服务商接口为准。按[官方接口文档](https://api-docs.deepseek.com/api/create-chat-completion/)显式关闭默认思考模式并限制输出。temperature=0 不保证服务端每次完全确定；本 demo 也不用于评估推理多样性。

### 低于五毛钱的预算约束

限制作用于一次完整的 `run_real_demo.py` 运行（包含两个任务），而不是每个 API 请求：

- 最多 24 次请求，无自动重试；HTTP、网络、缺失 usage 或截断输出时停止。
- 每次提示最多 5000 个 UTF-8 字节，输出最多 256 tokens。
- 输入按“UTF-8 字节数上限 + 512 tokens 格式余量”预留；不依赖缓存优惠。
- 采用核对时的高峰价格：输入未命中 ¥2/百万 tokens，输出 ¥8/百万 tokens。
- 单请求保守预留 `(5512×2 + 256×8)/1000000 = ¥0.013072`。
- 24 次合计预留上限 **¥0.313728**，程序总预算阈值设为 **¥0.40**，均低于 ¥0.50。
- 每次调用前先预留费用；失败或超时仍保留预留，避免重复调用造成未知扣费。

上述上限依赖当前价格及服务商遵守 max_tokens。输入字节数加余量是保守工程估计而非官方 tokenizer 证明；每次响应还会核查 usage 是否超出预留假设，若超出立即停止。结果报告按真实 usage 和高峰未命中价给出费用计算上界；账户最终扣费以 DeepSeek 账单为准。以后重跑若价格变化，应先核对并更新费率。不要用旧的、不带预算保护的 `watson.py reconstruct` 代替此入口。

## 2. 使用的模型与 Agent

### 2.1 本轮实际使用情况

| 角色或组件 | 本轮实现 | 是否调用真实模型 | 作用 |
|---|---|---|---|
| 主 Agent（Primary） | 预先构造的 `Call` 对象 | 否 | 提供观测输入和目标输出；未启动真实主 Agent |

上述 Agent 名称表示流程中的逻辑角色，不代表启动了多个独立模型、进程或协作 Agent。矩阵实验的模型名 `fixture` 和回归测试的模型名 `mirror-model` 都是占位字符串，不对应真实模型。

## 4. 实验参数与场景

| 参数 | 本轮取值 | 含义 |
|---|---|---|
| 目标接受候选数 k | 1、3、5、10 | 希望通过输出匹配和 judge 的候选数量 |
| 最大生成次数 | 4 × k | 耗尽仍不足时返回 `insufficient_candidates` |
| temperature / top_p | 0 / 1 | 传入客户端的参数；假客户端不根据它们采样 |
| 输入组件数 | 2 | 以空行划分 system 与 user 文本 |
| 消融次数 | 每组件 1 次，共 2 次 | 移除一个组件后重新生成 |
| 输出匹配 | 提取最后一个 `FINAL:` 后的文本并去首尾空白，严格比较 | 不支持语义等价匹配 |
| judge 通过条件 | 返回值去首尾空白并转为大写后等于 YES | 本轮由规则控制 |
| 随机种子 | 无 | 假客户端为确定性规则，不进行随机采样 |

| 场景 | 假客户端行为 | 预期结果 |
|---|---|---|
| `accept` | 主候选总是输出匹配答案，judge 返回 YES | 获得 k 条接受候选 |
| `wrong` | 主候选总是输出 other | 所有主候选在输出匹配阶段被拒绝 |
| `judge_reject` | 输出匹配，但 judge 返回 NO | 所有主候选在 judge 阶段被拒绝 |
| `alternating` | 依据生成调用计数交替返回匹配与不匹配结果 | 需要更多尝试才能获得 k 条接受候选 |

`alternating` 的计数包含先执行的 2 次消融，因此本轮主候选恰好从匹配结果开始，获得 k 条接受候选需要 `2k−1` 次主生成。这是固定测试序列，不是测得的模型概率。

## 5. 实验步骤

### 步骤一：核对原文与修正实现

原论文第 4 页的 RepCoT 是：给替身原始输入并附加解释生成指令，独立生成后，再丢弃最终输出与主 Agent 不一致的候选。

旧实现将观测答案直接放入生成提示并要求复制，会造成答案泄漏。本轮将目标答案从候选生成和消融提示中移除，仅在生成完成后用于匹配。与此同时补充候选历史、匹配率、judge 接受率、请求计数和采样不足状态，并将消融时间纳入总耗时。

### 步骤二：运行基础回归测试

```powershell
Set-Location 'C:\Users\mobao\Desktop\论文方向\Watson'
python test_watson.py
```

测试创建临时 SQLite 数据库，写入一条合成调用，依次执行导出、JSONL 写入及读取、两条候选的生成与筛选。通过时输出：

```text
PASS: AgentSight extraction and Watson RepCoT offline pipeline
```

### 步骤三：运行 16 组矩阵实验

```powershell
python run_offline_experiment.py
```

每组运行的顺序为：

1. 构造合成调用，并创建当前场景的假客户端。
2. 将输入拆成两个组件，分别执行一次移除组件的消融。
3. 根据消融后的输出是否仍匹配目标，标记组件影响。
4. 只根据完整输入生成候选，不提供目标答案。
5. 若 `FINAL:` 后的答案不匹配目标，直接拒绝，继续生成。
6. 若答案匹配，则调用 judge；返回 YES 才接受。
7. 收集到 k 条或达到 4k 次生成上限时停止。
8. 有接受候选时调用汇总；没有时写入无有效候选说明。
9. 校验接受数量、终止状态、请求计数与生成预算，并保存结果。

当前 judge 使用被标记为有影响的组件；若没有，则退回第一个组件。它还未实现原文的 top/bottom-n 归因验证。

### 步骤四：运行边界检查

同一个矩阵脚本还验证：没有 `FINAL:` 标记的裸答案不算匹配；含文本和工具调用的 OpenAI/Anthropic 格式响应不被纳入纯文本重建；缺失输入的调用被跳过且不会触发客户端请求。

### 步骤五：审计已有 AgentSight 数据

脚本以 SQLite 只读模式读取历史 `llm_calls`，统计总数、具有 prompt 的记录数、缺失 request 的记录数和可纳入的文本调用数，并比较读取前后的数据库主文件 SHA-256。

该检查只能说明本轮读取前后主文件哈希相同，不能证明历史请求响应配对正确；本轮也没有人工标注配对 precision/recall。


## 6. 本轮结果与指标解释

基础回归测试通过，16 组矩阵实验的断言均通过，Python 语法检查通过。

| 场景 | 达到目标的组数 | 耗尽预算的组数 | k=10 时主生成次数 | k=10 时接受数 | k=10 时假客户端调用数 |
|---|---:|---:|---:|---:|---:|
| accept | 4 | 0 | 10 | 10 | 23 |
| wrong | 0 | 4 | 40 | 0 | 42 |
| judge_reject | 0 | 4 | 40 | 0 | 82 |
| alternating | 4 | 0 | 19 | 10 | 32 |

`wrong` 与 `judge_reject` 返回样本不足是预期行为，因此对应测试通过，并不表示这些场景成功生成了解释。

请求计数公式为：

```text
客户端调用数 = 消融次数 + 主候选生成次数 + judge 次数 + 汇总次数
```

其中 judge 次数等于输出匹配候选数，汇总次数在至少有一条接受候选时为 1，否则为 0。输出匹配率为匹配数/主生成次数；judge 接受率为接受数/judge 次数，无 judge 调用时为 null。耗时为本地流程墙钟时间，不能推断真实模型推理延迟。

数据审计结果：共 3 条历史调用，3 条均缺少 request，具有 prompt 的记录为 0，可纳入文本重建的记录为 0；数据库主文件哈希未变化。因此没有对这些历史调用开展真实模型重建。

## 7. 结论边界与后续真实实验

本轮证明了受控规则下的输出拒绝、judge 拒绝、采样终止和数据准入流程按预期工作。它没有证明解释忠实性、实际任务成功率提升、真实采样接受率、成本收益或零干扰性。

当前实现与论文仍有差距：严格文本匹配替代语义等价 judge；单次二值消融替代 PromptExp 的 token 概率归因；未实现 top/bottom-n 验证；消息角色展平且未完整重放解码配置，故标记为 approximate；未做 FIM、真实基准、人工盲评或 token 费用统计。
