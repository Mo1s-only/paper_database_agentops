## 1. One-sentence contribution

`VERIFIED`：OpenRCA 2.0 提出 PAVE，利用故障注入时已知的干预信息，从系统拓扑和注入前后遥测中前向验证故障传播路径，并把根因标签扩展为节点、边和路径级过程真值，用来识别“根因猜对但理由错误”的诊断。

## 2. 论文真正要解决的问题

已有 RCA 数据集通常只回答“根因是什么”，例如某个服务发生网络延迟，却不标注故障如何从根因传播到最终告警。对于生成式 RCA Agent，这种结果标签会产生一个评测盲区：模型可能猜中根因服务，却编造传播路径。

论文把这种情况定义为 **ungrounded diagnosis**：Agent 至少命中了一个正确根因服务，但没有给出从该服务到观测症状的、可验证的传播路径。Figure 1 的例子是：

```text
注入：Seat 服务发生 NetworkDelay

PAVE 验证路径：Seat → Travel → Order → Gateway
Agent 输出路径：Seat ─────────→ Order → Gateway
                           跳过 Travel，并虚构 Seat→Order 直接边
```

只看最终根因时，`Seat` 命中；看过程时，Agent 的中间边不成立。论文因此主张，RCA Agent 的评价对象应从“最终服务标签”扩大为“根因 + 受影响节点 + 有向传播边 + 到告警节点的路径”。证据见 pp.1–2、Figure 1。

## 3. 问题设定与信息边界

### 3.1 被评测 Agent 看见什么

Agent 只能看到观测遥测 `O_obs`，包括：


- 分布式 Trace：调用树、Span 时延、状态码；
- Metrics：CPU、内存、p99 时延、错误率等时间序列；
- Logs：结构化或半结构化日志；
- 注入前正常窗口与注入后异常窗口。

Agent **看不到** 系统依赖图，也看不到实际故障注入记录，必须从 Trace 等遥测中自行恢复关系和定位根因。证据见 §3.1、Appendix F.4.4，pp.5、26。

### 3.2 标注器 PAVE 多知道什么

PAVE 除了遥测，还使用：

- 系统依赖图 `G`；
- 已知干预 `do(v_root)`，含注入组件、故障类型、注入窗口和参数；
- 注入前基线 `D_base`。

论文明确写成：

```text
Agent: {O_obs}
PAVE:  {O_obs, do(v_root)}
```

这不是把答案泄漏给 Agent，而是让**数据标注阶段**使用实验者掌握的真实注入条件，把难以识别的“从症状反推原因”转成“已知原因后验证哪些效应确实发生”。这是全文最关键的设计。证据见 Eq. (1)、§2.1，p.3。

## 4. PAVE 方法核心

PAVE 的输入是依赖图 `G`、注入窗口内遥测 `O(t)` 和已知干预 `do(v_root)`，输出通过验证的传播路径集合 `Π*`。所有路径边的并集构成过程级真值图 `G*`。

### 4.1 Phase 1：结构剪枝

1. 将高维遥测映射为离散状态：服务/Span 使用 `HighLatency`、`HighErrorRate` 等状态；Pod/容器/主机使用 `CPU_Throttled`、`MemoryPressure` 等状态。
2. 建立时间展开异构图，节点是 `(组件, 状态, 时间)`。
3. 使用人工定义的传播规则集 `R`，只保留存在已知传播机制的状态转换。
4. 从注入点执行受约束 DFS，枚举候选路径 `Π_cand`。

时间展开用于处理微服务中存在的循环依赖，使一次具体故障传播仍表示为有时间顺序的无环链。默认最大路径长度为 5，单节点最多重访 2 次。证据见 §2.2、Appendix D.2–D.6，pp.3、17–19。

规则分为四类：

| 类别 | 典型关系 | 机制 |
|---|---|---|
| 垂直传播 | container/pod → service/span | CPU、内存争用或进程终止 |
| 第一跳 | service → span | 服务异常投影到具体请求 |
| 水平传播 | span → span | RPC 延迟、错误、超时、缺失调用 |
| 跨通道 | span → pod → span | 共享 Pod 中的 JVM/资源影响 |

论文称水平 Span→Span 边占观测传播边的 80% 以上。规则集故意偏宽松，后续再通过遥测验证剔除假阳性。证据见 Table 7、Appendix D.6，p.18。

### 4.2 Phase 2：因果验证

对每条候选路径，PAVE 要求三个条件同时成立：

1. **统计条件**：路径上的每个节点相对注入前基线发生足够显著的偏移；
2. **结构条件**：每条相邻边符合传播规则 `R`；
3. **时间条件**：下游异常开始时间不早于上游原因。

只有端到端通过三道门的路径才进入 `Π*`。若故障没有产生越过 SLO 阈值的下游信号、没有存活路径，或者注入前基线已经漂移，该次注入会被丢弃。证据见 §2.3，p.4。

### 4.3 异常检测细节

- Span/服务检测窗口 3 秒；Pod/容器/主机检测窗口 5 秒。
- CPU/内存等近似高斯指标使用 Z-score：critical `z>3`、warning `z>2`、moderate `z>1.5`。
- 重尾指标使用经验分位数，例如 critical 为超过基线 P99.9 或 `2×P99`。
- 时延使用随基线均值和变异系数变化的自适应倍率。
- 注入前约 15 分钟基线被分成两半：前半用于校准阈值，后半用于检验，避免在同一噪声样本上拟合和评估。

证据见 Appendix D.5、D.8、E.2，pp.18–21。

### 4.4 关于“因果”的准确理解

`VERIFIED`：干预确定了传播的起点，结构、统计和时间条件用于验证后续效应。

`INFERRED`：PAVE 得到的是“与已知干预一致、经规则和遥测筛选的高可信传播子图”，并不等于从数据中无假设地发现完整因果结构。其因果性依赖拓扑完整性、规则词表、基线稳定性和遥测覆盖。

## 5. OpenRCA 2.0 数据集

### 5.1 系统与规模

| 系统 | 服务数 | 技术栈 | 可评测实例 | 故障种类 | 最长路径均值 | 平均因果边数 |
|---|---:|---|---:|---:|---:|---:|
| TrainTicket | 44 | Java/REST | 320 | 25 | 3.0 | 10.1 |
| OTel Demo | 15 | polyglot/gRPC+Kafka | 38 | 9 | 2.5 | 3.0 |
| Hotel Reservation | 9 | Go/gRPC | 142 | 5 | 2.1 | 2.7 |
| **总计/总体** | — | — | **500** | **27** | **2.7** | **7.5** |

数据来自 8,137 次注入运行形成的原始池；在过滤静默注入并运行 PAVE 后，再按 `(系统, chaos family, 根因服务)` 分层选择 500 个实例。还排除了循环服务图、传播深度不超过 1 的样本和 frontend/loadgen 入口。采样目标是故障覆盖平衡，不是模拟生产故障的自然分布。证据见 §3.1、Table 1、Appendix A.2，pp.4–5、12。

### 5.2 每个实例包含什么

1. 注入前和注入后的 Trace、Metric、Log parquet；
2. 注入系统、组件和故障类型等结构化根因标签；
3. 服务、Pod、Span 上的逐步传播图；
4. 每个图节点的异常状态和纳秒时间戳；
5. 根因节点与下游告警节点。

标准图包含 `nodes`、`edges`、`root_causes`、`alarm_nodes` 四个顶层字段。证据见 Appendix A.2、F.3，pp.12、22–23。

### 5.3 故障标签设计

论文覆盖 Pod、资源、HTTP、DNS、网络、时间和 JVM 等 27 种 Chaos 注入原语，但评测时使用按“可观测效果”定义的受控词表。多个在遥测中无法区分的注入 API 会合并为同一标签，例如 PodKill 与 ContainerKill 都可能表现为短暂 Trace 缺口。这样做避免要求 Agent 从遥测中猜测不可辨识的底层 API 名称。证据见 Tables 5–6、Appendix C.2–C.3，pp.16–17。

## 6. 被评测 RCA Agent

所有模型使用同一套 ReAct 风格 Agent：

```text
START → LLM 决策 → 工具执行 → LLM 决策 → … → 结构化压缩 → END
```

四个工具分别用于列出 parquet、读取 schema、执行 DuckDB SQL 和记录阶段反思。每例建议约 50 次工具调用，运行时硬上限 100；失败查询作为观察返回，不使循环崩溃。调查阶段只收集证据，随后由单独一次 LLM 调用压缩为严格 JSON。证据见 Appendix F.2–F.4，pp.21–26。

Agent 输出包括：

```text
root_causes[]: service + fault_kind + evidence[]
propagation[]: from + to + evidence[]
evidence: modality + executable SQL + ≤20词的 claim
```

每个根因和每条传播边都必须绑定至少一条可执行 SQL。评测器在对应 case 的 parquet 上重新执行 SQL。这个设计把自然语言理由收紧为可以重新查询的证据引用。证据见 Appendix F.3–F.4，pp.23–26。

主表比较 11 个模型：Claude Opus 4.7、Gemini 3.1 Pro、Claude Sonnet 4.6、MiMo 2.5 Pro、GLM 5.1、Kimi K2.6、DeepSeek V4 Pro、Qwen3.6-Max、Hy 3.0 Preview、Seed 2.0 Pro、MiniMax M2.7。提示词、工具、重试逻辑和 temperature=0.7 保持一致。GPT-5.4 和 GPT-5.5 因预算不足只报告部分样本，不能与主表直接比较。证据见 §3.2、Appendix F.5、H.3，pp.5、26、29–30。

## 7. 评测指标

### 7.1 结果层

- **EM**：预测的 `(service, fault_kind)` 集合与真值完全一致。
- **Precision/Recall/F1**：按每例的 `(service, fault_kind)` 集合计算后取平均。
- **AnySvc**：忽略故障类型，只要至少命中一个真值根因服务即通过，是最宽松的结果指标。

### 7.2 过程层

- **Node F1**：预测受影响服务集合与 `G*` 节点集合的重合程度。
- **Edge F1**：预测有向服务边与 `G*` 边的精确匹配。
- **Path Reachability（PR）**：至少命中一个正确根因服务，并在预测图中形成通向真值告警节点的路径。
- **SQL Exec**：证据 SQL 执行成功且返回至少一行的比例。

服务名先经过小写、移除 `ts-` 和连字符等规范化；合成 loadgen 的相关边不参与图指标。证据见 Appendix G，pp.26–28。

## 8. 主要实验结果

### 8.1 总体结果

11 个模型在 500 个实例上的平均结果为：

| 指标 | 平均值 | 含义 |
|---|---:|---|
| EM | 20.7% | 完整根因集合很少被精确恢复 |
| Pair F1 | 34.1% | 服务与故障类型联合识别仍弱 |
| AnySvc | 76.0% | 至少猜中一个根因服务相对容易 |
| PR | 61.5% | 命中服务后仍有相当部分没有连到症状 |
| Node F1 | 62.2% | 受影响服务集合识别尚可 |
| Edge F1 | 43.4% | 有向传播关系明显更难 |

`AnySvc - PR = 14.5` 个百分点，即有一批案例命中了服务，却没有满足论文定义的过程路径。Edge F1 比 Node F1 平均低 18.8 个百分点，说明“哪些服务参与”比“谁导致谁”更容易。证据见 Table 2、§3.2，p.6。

各列最佳模型并不相同：Gemini 3.1 Pro 的 EM/F1/Node F1 最高，Claude Opus 4.7 的 AnySvc 最高，Qwen3.6-Max 的 PR 最高，GLM 5.1 的 Edge F1 最高。因此论文没有宣称存在统一最优骨干模型。证据见 Table 2，p.6。

### 8.2 系统难度差异

系统差异大于许多模型差异。以 Claude Opus 4.7 为例：

- TrainTicket：EM 15.6%，AnySvc 75.3%，PR 55.9%；
- Hotel Reservation：EM 54.9%，AnySvc 99.3%，PR 98.6%。

作者把这种差异与服务数量和路径深度联系起来，但这只是相关性解释，并非独立控制实验。证据见 Appendix H.1、Table 8，pp.28–29。

### 8.3 三类典型失败

1. **过早收敛**：找到一个显眼根因后停止探索，遗漏混合注入中的第二个故障或中间传播节点。
2. **可见性偏差**：把“没有 Span”误判为正常；Pod 被杀死时，沉默本身才是异常信号。
3. **显著性捕获**：把下游最响亮的错误、超时或日志当成根因，即使 Trace 与该日志叙述矛盾。

这些模式来自作者对分层样本中 Agent 轨迹的阅读，论文没有给出三类错误各自的完整计数，因此适合作为定性故障分类，不应写成经过统计验证的占比结论。证据见 §3.3，pp.6–7。

## 9. 标注可靠性

作者从 500 例中均匀随机抽取 100 例，由两名具有可观测性经验的论文作者独立审查。每例检查：

1. 节点异常能否在原始遥测中找到；
2. 每条边是否满足时间先后、结构可行和因果而非巧合；
3. 是否遗漏明显传播节点或路径。

案例级一致率为 94/100。6 个分歧全部是审查者认为还存在被 PAVE 遗漏的弱路径；在这 100 例中，没有审查者指出 `G*` 已包含的边明显不合理。论文因此选择高精度、保守召回的真值。证据见 §3.4、Appendix E.1，pp.7–8、20–21。

该结果只能表述为“在抽查的 100 例中未发现已纳入边的假阳性”，不能写成“PAVE 的边精度为 100%”或“全部 500 例都正确”。

## 10. 论文的优点

1. **信息边界清楚**：注入真值只给标注器，不给被评测 Agent，避免把 oracle 信息混入算法输入。
2. **把因果发现降为前向验证**：已知起点后，不再从噪声症状中无约束地搜索所有 DAG。
3. **过程真值可计算**：根因、节点、边、路径均有结构化对象，能机械计算指标。
4. **证据可重新执行**：每个结论绑定 SQL，优于只生成自然语言解释。
5. **正常/异常成对数据**：让 Agent 和标注器都能做差分分析。
6. **按可观测效果定义标签**：不要求模型识别遥测中不可区分的注入实现。
7. **主动报告失败边界**：明确限定为受控测试床，不把结果直接外推到生产系统。

## 11. 局限与精读质疑

### 11.1 作者明确承认的局限（`VERIFIED`）

- 需要真实受控干预、足够完整的依赖图、可观测传播信号和稳定的注入前基线；任一条件失败，结论都只能视为目标场景中的上界。
- 规则集 `R` 可能剪掉词表之外的传播机制。
- 单节点异常检测偏向低漏检，会纳入一些偶然异常，只能依靠联合门进一步过滤。
- 测试床不能代表生产规模；向 serverless、service mesh、完全事件驱动系统迁移需要重新校准。
- 当前没有 train/dev/test 划分，不应把这 500 例同时用于训练与评测。

证据见 §5、Appendix A.2/A.5，pp.9、12–13。

### 11.2 基于原文发现的不足（`INFERRED` / `UNVERIFIED`）

1. **缺少系统消融**（`UNVERIFIED`）：正文和附录没有报告分别移除结构、统计或时间门后的路径精度/召回变化，也没有阈值敏感性曲线。Eq. (3) 使用的 `p_s=0.2, p_r=0.3, p_t=0.5` 是示例值，不是实测误报率。
2. **独立性上界只是说明性推导**（`VERIFIED`）：三道门并不独立，论文自己承认结构与时间条件共享信息。因此 `(p_s p_r p_t)^k` 不能当作实际误报概率保证。
3. **人工审计独立性有限**（`INFERRED`）：两位审查者都是作者并熟悉 PAVE；论文只报告二元案例一致率，没有外部 SRE、边级 precision/recall、Cohen’s κ 或盲于算法输出的重新标注。
4. **数据筛选透明度不足**（`UNVERIFIED`）：Table 1 的标题说原始池规模和静默注入率在 Appendix A，但附录未给出分系统原始数量、各阶段淘汰量和静默率。8,137 到 500 的选择可能改变难度分布。
5. **PR 定义存在歧义**（`UNVERIFIED`）：Eq. (10) 只写“预测图中从正确根因到真值告警节点可达”，没有显式要求路径上的每条预测边属于 `G*`；但 Figure 1 把含虚构捷径边的可达图判为 PR=False。除非实现中的“valid path”还包含未写进公式的真值边约束，否则图例与公式不完全一致，复现前必须检查评测代码。
6. **SQL 可执行不等于证据支持**（`VERIFIED`）：SQL Exec 只检查 SQL 成功且返回至少一行，Appendix G 明确说它不判断返回行是否支持 claim。Appendix F.4.4 提到 `evidence_support_rate`，但 Appendix G 没有给出对应正式定义，主表也没有报告该指标。
7. **“over-approximation”用词与行为矛盾**（`INFERRED`）：Appendix E.1 称 `G*` 是高精度 over-approximation，但同一段说明它会遗漏弱边且拒绝可疑边；从集合关系看更接近保守的 under-approximation/subgraph。
8. **随机性与统计稳定性未充分报告**（`UNVERIFIED`）：模型 temperature=0.7，但没有看到每例重复运行、随机方差、置信区间或显著性检验。主表应理解为论文所执行配置下的点估计。
9. **发布状态有限**（`VERIFIED`）：PDF 写明完整数据集和 PAVE 代码将在录用后公开；当前原文没有提供可核验的正式归档地址，因此“完全可复现”仍待实际公开包验证。

| 标注器与被评测方法的信息隔离 | 故障注入/实验 oracle 只用于生成责任真值，归因方法只能读取统一事件与证据图 |
| `root_causes + nodes + edges + alarm_nodes` | 扩展为 `responsible_agent + responsible_step + root_node + propagation_edge + failure_outcome` |
| 注入前/后遥测对 | 为消息、工具结果、模型输出和进程指标保存正常运行与故障运行对照 |
| 受控可观测故障词表 | 按可观测 Agent 故障语义定义标签，如错误生成、错误传播、错误路由、未拦截、工具静默失败 |
| 每条主张绑定 SQL | 延续现有查询收据，并增加源记录哈希、JSON Pointer、时钟区间和身份映射状态 |
| Node/Edge/Path 分层指标 | 分别报告 Agent、Step、根因节点、责任边、完整路径，缺证据时允许 `abstain` |
| 已知干预后的前向验证 | 对消息替换、工具结果替换、路由修复、Agent 决策替换执行局部重放或反事实验证 |

### 12.2 当前工作相对它可以形成的差异

`INFERRED`：OpenRCA 2.0 的节点主要是服务、Pod 和 Span，边语义主要是资源或 RPC 故障传播；当前论文可以研究动态多 Agent 系统中的 Agent、Step、消息、模型调用、工具调用、进程和文件/网络对象。进一步的差异应建立在可验证的责任语义上：

- **产生错误**：某一步首次生成错误信息或动作；
- **传播错误**：某 Agent 将上游错误继续传递；
- **放大错误**：某一步扩大错误影响范围；
- **未拦截错误**：具有检查职责的 Agent 未阻止失败；
- **修复效应**：替换该消息、工具结果或决策后，最终任务是否恢复。

当前已有工作在 OpenRCA 2.0 之前增加了三项归因前基础：跨层身份对齐、带不确定度的时钟统一、以及关系级来源哈希/查询收据。它们可以解释“这条 Agent 边来自哪些真实事件”，但尚未自动证明“该边承担失败责任”。

### 12.3 不能直接借用的主张

- 不能把微服务传播边直接等同于多 Agent 责任边。
- 不能因为时间在前、消息相连就宣称因果责任。
- 不能把 PAVE 的 94% 案例一致率当作本项目标注器的可靠性。
- 不能在尚未完成干预/重放真值前声称已经实现归因。
- 不能仅报告查询可执行率，还需验证查询结果是否实际支持主张。

## 13. 对当前 schema 和实验的具体建议

在现有 `run/session → agent → step/span → relation → label/evidence` 基础上，建议下一版本加入：

1. `intervention`：被替换/删除/修复的 Agent、Step、消息或工具结果，以及干预时间窗；
2. `alarm_nodes`：最终错误输出、任务失败断言或外部副作用；
3. `node_state`：正常、错误、缺失、超时、误路由、未验证等受控状态；
4. `onset_interval`：使用 `[earliest, latest]` 表示带时钟不确定度的异常开始区间；
5. `edge_semantics`：生成、传递、路由、调用、读取、写入、未拦截、放大；
6. `evidence_support`：除可执行外，检查返回行是否与 claim 中的主体、时间窗和异常谓词一致；
7. `verification_status`：`observed / inferred / intervention_verified / contradicted / abstain`；
8. `counterfactual_result`：修改目标、重放配置、输出变化、任务 oracle、效应大小和重复次数。

评测时可以保留 OpenRCA 2.0 的分层思想，但将 PR 改成无歧义的两个指标：

- **Predicted Reachability**：预测图中根因到失败结果是否连通；
- **Verified Path Match**：是否存在一条路径，其每条边都与真值边或等价责任边匹配。

这样可以避免本文 Figure 1 与 Eq. (10) 暴露的 PR 解释歧义。

## 15. 可用于论文写作的准确表述

可以写：

> OpenRCA 2.0 将受控故障注入中的已知干预作为标注侧信息，通过拓扑约束、基线偏移和时序一致性联合验证传播路径，从而把 RCA 评测从最终根因扩展到节点、边和路径层。其结果表明，模型命中根因服务并不保证其传播解释成立。

不建议写：

> OpenRCA 2.0 已经解决了多智能体失败责任归因。

原因是它验证的是微服务故障效应传播，不区分错误产生、传播、放大和未拦截等责任角色，也没有通过替换 Agent 决策来测量反事实责任。

## 16. 下一研究闸门

在实现归因算法前，先完成一个最小的 **Agent-PAVE 式真值实验**：选择一条已有真实多 Agent 失败轨迹，固定原始证据包，分别替换责任消息、工具结果和无关步骤，各重复至少 3 次；用任务 oracle 判断失败是否消失，再标注责任 Agent、责任 Step、传播边和完整路径。只有当“原始失败可复现、责任干预能修复、无关干预不修复、每条路径都有可重放证据”同时成立，当前归因前观测图才真正升级为可用于归因评测的过程真值。
