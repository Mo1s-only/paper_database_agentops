> **论文标题**：AgentMonitor: A Plug-and-Play Framework for Predictive and Secure Multi-Agent Systems
> **作者**：Chi-Min Chan¹, Jianxuan Yu², Weijian Yu², Weize Chen², Chunyang Jiang¹, Xinyu Liu¹, Weijie Shi¹, Zhiyuan Liu², Wei Xue¹, Yike Guo¹*

> **阅读定位**：LLM 多智能体系统（MAS）的**性能可预测性**与**安全性**——用"非侵入式监控 + 回归模型"提前预测下游任务表现，并顺手解决恶意 Agent 注入问题

## 一、论文总结

### 1.1 一句话概括

AgentMonitor 是一个**即插即用（plug-and-play）**的多智能体监控框架：它在**不修改原有 MAS 工作流**的前提下，通过轻量包装（wrapping）采集两类中间指标——**LLM 判官打出的分数**（personal score / collective score）与**由图结构配置决定的图属性**（PageRank、节点数、边数、聚类系数、中心性等）——再用 **XGBoost 回归模型**把这些指标映射到下游任务表现，从而在任务**执行后立刻（甚至只"偷看"部分样本）**预测整个系统的性能；同时利用"后编辑（post-edit）"机制在推理链中插入对齐 LLM，缓解恶意 Agent 带来的安全退化。

### 1.2 核心动机（Motivation）

- **配置难**：给定一个具体任务，要"有效预配置"一个多智能体系统非常困难。智能体数量、角色划分、拓扑连接、每个 Agent 挂哪个 LLM——组合空间巨大，而**性能只有在真正跑完之后才能观察到**，试错成本极高。
- **灵感来自 Scaling Law**：大语言模型领域已经证明"模型规模 ↔ 能力"存在可预测的幂律关系（Kaplan et al. 2020；Hoffmann et al. 2022 Chinchilla；Isik et al. 2024；Ye et al. 2024）。本文直接把这个问题搬到 MAS 层面：**MAS 的性能是否可预测？** 如果能用廉价可得的中间指标（而非昂贵端到端评测）预测最终表现，就能把"试错"变成"预测"。
- **安全缺口**：MAS 引入了单模型没有的风险面——**一个恶意 Agent 就能污染整个系统的输出**。论文不只做预测，还把"监控"能力延伸到"防护"，用最轻量的后编辑手段做缓解。

### 1.3 方法总览（三段式）

**① 非侵入式采集（Non-invasive wrapping）**

借鉴 PEFT / OpenDelta 的包装思路，AgentMonitor 不侵入业务代码，只做一层外壳：

```python
await monitor.register([agent1, agent2, agent3], **args=...)
```

一行注册即可开始监控，**保持原有工作流不变**——这是本文反复强调的核心卖点（plug-and-play、non-invasive）。

**② 指标设计（Table 1，分两组）**

| 组别 | 指标 | 说明 |
|---|---|---|
| **LLM 判官打分** | **Personal Score**（个人分） | 该 Agent 完成"自己那块被指派的任务"的质量 |
| | **Collective Score**（集体分） | 该 Agent 的行为"对整体系统目标"的贡献度 |
| **配置决定**（无需推理，直接由图算出） | **PageRank** | 每个 Agent 的图重要性 |
| | **Capabilities** | 每个 Agent 的能力标签/描述 |
| | **Number of Nodes / Edges** | 节点数、边数（系统规模） |
| | **Average Clustering / Transitivity** | 平均聚类系数、传递性（小团体程度） |
| | **Average Degree Centrality** | 平均度中心性（连接忙碌度） |
| | **Average Closeness Centrality** | 平均接近中心性（到全图的可达效率） |
| | **Average Betweenness Centrality** | 平均介数中心性（是否为"桥"） |
| | **Heterogeneous Score** | 异构度（Agent 角色/模型是否多样） |

关键洞察：**第一组要花推理成本才能拿到，第二组几乎零成本（纯图论计算）**。论文后续的"偷看实验"（sneak peek）验证——即便只用极少量样本估算打分类指标，预测性能也不会塌，这为"低成本预测"提供了依据。

**③ 回归映射（XGBoost）**

用 **XGBoost**（Chen & Guestrin 2016）以 `reg:squarederror` 为目标、网格搜索调参，把上述指标拟合成"下游任务得分"。选树模型而非线性模型的隐含理由：论文发现**大多数指标与目标分数之间是非单调关系**（non-monotonic），线性模型天然吃亏。

**④ 安全扩展：Post-edit 后编辑**

将推理链 `(A → B)` 改造为 `(A → post-edit LLM → B)`，用一个对齐后的 LLM 在 Agent 之间"过一遍"输出，抑制有害内容。思路对标神经网络里的 **adapter**，理论依据是 Aligner（Ji et al. 2024a）的 **weak-to-strong generalization**——弱监督者也能提升强模型的对齐性。

### 1.4 主要贡献

1. **首次系统研究 MAS 性能的可预测性**，提出以中间指标 + 回归模型做"执行后即时预测"的范式。
2. **提出即插即用、非侵入的监控框架**，一行注册、不改工作流。
3. **构建 1,796 个数据点的指标-性能数据集**，覆盖 5 种 MAS 架构、3 类下游任务、3 种 LLM 骨干。
4. **给出 5 种划分下的泛化评估**（In-Task / In-Arch / In-Domain / Cross-Arch / Cross-Task），揭示域内 Spearman 0.89、跨域约 0.58 的边界。
5. **将监控能力延伸到安全领域**，用 post-edit 缓解恶意 Agent，平均**有害性降低 6.2%、有用性提升 1.8%**。

## 二、应用场景

### 2.1 直接应用场景

| 场景 | 具体用法 | 价值 |
|---|---|---|
| **MAS 架构选型 / A-B 测试前的预筛** | 在真正跑昂贵端到端评测之前，用 AgentMonitor 预测每个候选配置的得分，只把高分配置送入真实评测 | 把"全量试错"变成"预测筛选"，节省大量 API 费用与时间 |
| **运行时成本控制** | 用"偷看"模式（只跑 10% 样本估计指标）做预测 | 论文实测 10% 样本即可把 Spearman 维持在约 0.82 |
| **Agent 角色/拓扑调优** | 观察 PageRank、介数中心性、异构度等图指标与性能的关系，指导加/删 Agent、改连接 | 提供可解释的优化方向，而非盲目调 prompt |
| **多智能体安全护栏** | 在 Agent 之间插入 post-edit LLM，抑制有害输出 | 无需重训模型、无需改架构，只加一层对齐 |
| **系统健康监控 / 异常识别** | 持续采集 personal / collective score，识别哪个 Agent 拖后腿 | 与"失败归因"类工作（Who&When 等）形成互补 |

### 2.2 适用边界（何时不该用）

- **单 Agent 场景**：本文的指标（图属性、页面排序、节点/边）几乎全部为多 Agent 拓扑设计，单 Agent 退化后可用信号极少。
- **需要训练回归模型**：XGBoost 需要该任务/架构域内的历史数据点，**冷启动场景**拿不到训练集就无法预测。
- **Agent 数量/架构变化剧烈**：Cross-Arch 划分下 Spearman 掉到 0.58 量级，说明跨架构泛化仍不够可靠。
- **对安全要求极高的场景**：post-edit 只能"缓解"不能"保证"，论文自述同时提升有用性与无害性很困难。

## 三、实验设置

### 3.1 研究的五个问题（RQ）

| RQ | 内容 |
|---|---|
| **RQ1** | MAS 性能是否可预测？在不同泛化划分（In-Task / In-Arch / In-Domain / Cross-Arch / Cross-Task）下表现如何？ |
| **RQ2** | **训练数据量**对预测性能的影响——需要多少数据点？是否存在饱和点？ |
| **RQ3** | **计算指标所用的样本量**对预测性能的影响——能否"偷看"（只用少量实例）就得到不错预测？ |
| **RQ4** | 各类指标之间的关系如何？（哪些相关、哪些冗余） |
| **RQ5** | 能否用监控能力缓解**恶意 Agent**带来的安全风险？post-edit 应插在什么位置最优？ |

### 3.2 数据划分设计（本文评估的精髓）

论文设计了 **5 种从易到难的划分**，用 **5 折交叉验证**并给出误差棒：

| 划分 | 训练 / 测试差异 | 难度 |
|---|---|---|
| **In-Task** | 同任务、同架构、同实例分布 | 最易 |
| **In-Arch** | 同架构、跨任务实例 | 较易 |
| **In-Domain** | 同领域（域内）内泛化 | 较易（**0.89** 就出自这里） |
| **Cross-Arch** | 测试架构在训练时完全没见过 | 较难 |
| **Cross-Task** | 测试任务在训练时完全没见过 | 较难 |

> 这种"逐步放开泛化维度"的设计非常值得借鉴：它把"泛化能力"拆成了正交的几个轴，能精确定位模型到底在哪一维上失效。

### 3.3 关键实验内容（按 RQ 组织）

- **RQ1（预测能力）**：三个任务 × 五种划分 → Spearman 秩相关矩阵；同时报告误差中位数（median error），论文指出**误差中位数接近 0**，说明预测偏差是对称的而非系统性高估/低估。
- **任务难度差异**：**HumanEval 最难预测**（代码任务），但其预测**误差反而更小**——即"相关性低但偏差小"，这两个指标要分开看。
- **RQ2（训练规模消融）**：逐步增加训练数据量，秩相关随数据增加而上升，**在训练集约 50% 处趋于饱和**——意味着不必用满全部数据点。
- **RQ3（实例数消融 / sneak peek）**：只用 10%、20%… 实例估算 LLM 打分指标。结果：**仅 10% 实例时 Spearman 仍约 0.82**，具备"偷看"能力；同时发现**估算出的指标倾向于被低估**（underestimated），主因是 **LLM 判官的低估偏差**；为控制噪声，实验只在"绝对误差 < 0.05"的实例集上评估。
- **RQ4（指标关系）**：① LLM 打分类指标之间**相互高度相关**，但与图属性相关度低；② **同一 Agent 的指标之间相关性高于不同 Agent 的指标**；③ **大多数指标与目标分数呈非单调关系**（这正是必须用树模型的原因）。
- **RQ5（安全实验，§4.4）**：见 3.4。

### 3.4 安全实验设置（§4.4）

**两个额外架构**（在原有 Arch1–Arch5 之外）：

1. **无害-有用架构**：`harmless agent + helpful agent + summarizer agent`
2. **含恶意 Agent 架构**：在上述基础上加入 **malicious agent**（被明确指示生成**既有害又无用**的回复）

**对照组**：单独使用 u8B / 8B / 70B 三个 LLM（不与 MAS 组合）。

**评测指标**：**Harmless↑**（无害性）与 **Helpfulness↑**（有用性）——两个维度分别打分。

**Post-edit 位置对照（Table 3）**：

| 插入策略 | 效果 |
|---|---|
| 只在恶意 Agent 之后插入 | 改善有限 |
| 只在某个中间位置插入 | **总体不如"在所有 Agent 之后插入"** |
| 只在 summarizer 之后插入 | **某些情况下反而更好** |

> 由此引出论文的一个重要观察与未来工作：应做**按需动态封装（dynamic encapsulation on demand）**——该插的时候插、不需要的时候跳过，以避免不必要的推理延迟。

### 3.5 主要实验发现汇总

1. 恶意 Agent 会同时拉低无害性与有用性 → 证实 MAS 的**安全脆弱性**（与 Zhang et al. 2024 一致）。
2. 用**相同 LLM 骨干**做 post-edit：两个维度都**略有提升**。
3. 用**对齐更好的 LLM 骨干**做 post-edit：无害性**显著提升**，但有用性**下降**（与 Ji et al. 2024a 的观察一致）→ 对齐-有用性权衡。
4. 最终摘要级结论：借助 AgentMonitor，MAS 平均**有害性降低 6.2%**、**有用性提升 1.8%**。

### 4.1 五种 MAS 架构（Arch1–Arch5）

| 编号 | 组成 | 设计意图 |
|---|---|---|
| **Arch1** | coder + tester + reviewer | 最基础的三角色闭环 |

## 五、数据集来源

### 5.1 数据点的构造方式

**每个数据点的定义**：一个元组 `{各种指标, 下游任务表现}`。

- 每个 Agent 从 **{Llama3-8B, Llama3-70B, ChatGPT}** 三选一
- 4-Agent 架构共 **3⁴ = 81** 种模型组合
- 对每种组合采集指标 + 跑下游任务得到性能标签
- **总计 1,796 个数据点**

### 5.2 下游任务数据集

| **GSM8K** | 小学数学应用题 | 多步推理 |

### 5.3 安全实验数据集

| 数据集 | 作用 |

| **BeaverTails**（Ji et al. 2024b） | 安全对齐评测基准 |
| **MaliciousInstruct**（Huang et al. 2023a） | 恶意指令集合 |
| **AdvBench**（Zou et al. 2023） | 对抗性有害行为基准 |

### 5.4 数据规模小结

- **指标-性能数据点**：1,796
- **架构数**：5（+2 个安全实验专用架构）
- **任务数**：3（代码 / 推理 / 数学）
- **LLM 池**：3（Llama3-8B / Llama3-70B / ChatGPT）
- **评测划分**：5 种 × 5 折交叉验证

## 六、结果验证

### 6.1 预测性能（RQ1）

| 场景 | Spearman 秩相关 | 解读 |
|---|---|---|
| **In-Domain（域内）** | **0.89** | 域内预测高度可靠，框架核心价值成立 |
| **更难设置（Cross-Arch / Cross-Task 等）平均** | **约 0.58** | 跨域仍可用但明显退化 |
| **误差中位数** | **接近 0** | 预测偏差对称，无系统性高估/低估 |

**HumanEval 的特殊现象**：代码任务**最难预测**（秩相关最低），但它的**预测误差反而更小**。论文提示要区分两个维度——"排序能力（相关性）"和"数值准确度（误差）"并不总是一致。

### 6.2 训练规模消融（RQ2）

- 秩相关随训练数据量单调上升，**在约 50% 训练集处趋于饱和**。
- 实践含义：**不需要收集满量数据**即可达到接近最优的预测器，显著降低数据采集成本。

### 6.3 实例数消融 / 偷看能力（RQ3）

- **仅用 10% 实例**估算 LLM 打分指标时，Spearman 仍维持在 **约 0.82**。
- 说明"**低成本偷看**"是可行的——不必等全量任务跑完，就能给出有意义的预测。
- **误差来源分析**：估算出的指标**倾向于被低估**，主因是 **LLM 判官的打分偏低（underestimation）**，而非图属性估算误差。
- 实验控制：只使用"绝对误差 < 0.05"的实例构成测试集，以隔离噪声。

### 6.4 指标间关系（RQ4）

1. **LLM 打分类指标之间高度相关**（personal / collective 彼此纠缠），但**与图属性相关性弱** → 两组指标提供互补信息，不应互相替代。
2. **同一 Agent 的指标之间相关性，高于不同 Agent 的指标** → 存在明显的"Agent 内部一致性"。
3. **大多数指标与目标分数是非单调关系** → 直接印证了选用 **XGBoost 等树模型**而非线性回归的必要性。

### 6.5 安全缓解效果（RQ5，§4.4）

| 配置 | Harmless | Helpfulness |
|---|---|---|
| 无恶意 Agent | 基准 | 基准 |
| **加入恶意 Agent** | **下降** | **下降**（双重退化 → 系统脆弱） |
| 恶意 Agent + 用**同骨干** post-edit | 略升 | 略升 |
| 恶意 Agent + 用**更对齐骨干** post-edit | **显著上升** | **下降**（对齐-有用性权衡） |

**Post-edit 位置消融（Table 3）**：
- 只在恶意 Agent 后插入 → 改善有限。
- 只插一个中间位置 → 通常**不如"所有 Agent 之后插入"**。
- **只在 summarizer 后插入 → 某些情况下反而更好**。

**总体指标**：平均**有害性降低 6.2%**、**有用性提升 1.8%**。

### 6.6 论文自述的局限

- post-edit **并非万灵药**：同时提升有用性与无害性非常困难，根源在于 post-edit LLM 自身能力上限。
- 对齐更强的骨干会牺牲有用性 → 说明这是**能力受限下的权衡**，而非工程调参问题。

## 七、启示与局限性

### 7.1 对研究方向的启示

**① "可预测性"是 AgentOps 的一条独立技术线，与"可观测性"互补。**

已读的四篇论文其实构成了一个完整光谱：

| 论文 | 核心问题 | 层次 |
|---|---|---|
| **AgentSight** | 系统**发生了什么** | 操作层可观测（eBPF 边界追踪） |
| **Watson** | Agent **在想什么** | 语义/认知层可观测（替代 Agent 复现推理） |
| **Who&When** | **谁**在**哪一步**错了 | 失败归因层（反事实决定性错误） |
| **AgentDropout** | 怎么**优化**拓扑 | 拓扑搜索层（可微/策略梯度） |
| **AgentMonitor** | 能不能**提前预测**表现 | 性能预测层（指标→回归） |

AgentMonitor 的独特价值在于：它**不解释机制，只预测结果**。这在工程上极其务实——很多时候你并不需要知道"为什么"，只需要知道"这个配置行不行"。

**② "配置决定型指标"（零成本）与"推理型指标"（高成本）的分层，是一个非常可复用的设计。**

这个思路可以推广：任何系统中都存在"**结构性可读的廉价特征**"与"**需执行才能得到的昂贵特征**"。AgentMonitor 证明了**廉价特征 + 少量昂贵特征采样**（10% 实例）就能达到 0.82 的预测力——这对实际部署的性价比极关键。

**③ 泛化边界要按维度拆开评估。**

"5 种划分（In-Task / In-Arch / In-Domain / Cross-Arch / Cross-Task）"这套评估方法论，本身就值得迁移到其他 AgentOps 工作中。相比只报一个总分，它精确定位了失效维度（这里是**跨架构**）。

**④ 监控能力可以顺手转化为安全能力。**

同一个监控外壳，既做预测又做 post-edit 防护，体现了"**观测基础设施的复用价值**"。对于追求工程经济性的工作，这是很好的叙事模板。

**⑤ 用非线性模型是"发现驱动"的，不是"拍脑袋"的。**

论文先发现"指标与目标非单调"，才选用 XGBoost。这种"**先诊断数据形状、再选模型**"的做法比"直接上 Transformer"更扎实。

### 7.2 局限性

| 局限 | 具体表现 | 影响 |
|---|---|---|
| **跨架构泛化不足** | Cross-Arch / Cross-Task 平均仅约 0.58 | 更换拓扑后预测可靠性明显下降，难以"开箱即用" |
| **需要域内训练数据** | 依赖 1,796 点历史数据训练 XGBoost | 冷启动场景不可用；每个新领域都要重新攒数据 |
| **LLM 判官引入偏差** | 打分指标**系统性低估** | 偷看模式下预测会有系统性偏差，需额外校准 |
| **指标因果性不明** | 只做相关性/回归，未做因果分析 | 知道"哪些指标预测准"，但不知道"改哪个指标能提升性能" |
| **安全缓解是权衡而非解决** | 更对齐的骨干 → 无害性↑但有用性↓ | 无法同时优化，只能选点；论文自己承认 post-edit"不是万灵药" |
| **架构与任务覆盖面有限** | 5 架构 / 3 任务 / 3 个 LLM | 结论能否推广到大规模、异构、长流程 MAS 存疑 |
| **工作状态为 Work in progress** | v1 预印本，未同行评审 | 结论稳定性待后续版本验证 |
| **post-edit 引入额外延迟** | 每个插入点都要多跑一次 LLM | 论文提到"按需动态封装"是未来工作，说明当前实现有成本问题 |

### 7.3 对我们自己工作的可借鉴点

1. **"先证可预测性，再做优化"** 是一条清晰的论文故事线：预测 → 归因 → 优化，AgentMonitor 稳稳占住第一环。
2. **指标体系分层（廉价 vs 昂贵）** 可直接复用到我们自己的实验设计中，用于论证方法的经济性。
3. **5 维划分评估表** 建议直接抄作业，写进我们自己的实验章节。
4. **post-edit 位置消融** 提供了"插入点位置是超参"的实证，与我们关心的"干预点选择"（Who&When 的决定性错误定位）直接呼应——两者都在问"**在哪儿动手最有效**"。
5. **承认局限反而增强说服力**：论文明确写"post-edit 不是万灵药""有用性与无害性难以兼得"，这种坦诚在审稿中通常是加分项。

## 附二：与已读论文的对照

### 2.1 与 AgentSight 的对照

| 对比项 | AgentSight | AgentMonitor |
|---|---|---|
| **观测层次** | 系统边界（内核/eBPF，SSL 调用、进程调度） | 语义 + 图结构（LLM 打分、图论指标） |
| **侵入性** | 零侵入（内核层，不改代码） | 非侵入但需包装注册（应用层，一行） |
| **技术手段** | uprobes / kprobes / tracepoints + 事件压缩（521→37） | XGBoost 回归 + 图论特征工程 |
| **目标** | 看得见（可观测性） | 猜得准（可预测性）+ 保安全 |
| **成本** | 2.9% 运行时开销 | 极低（图属性零成本，打分需少量采样） |
| **共同点** | 都强调**不改变原有工作流**，都用"抽象压缩"降低信息噪声 | |

**互补关系**：AgentSight 抓的是"**低层真实行为**"（进程、网络、文件），AgentMonitor 抓的是"**高层语义与结构**"。想做完整的 AgentOps，两者缺一不可——前者回答"有没有异常行为"，后者回答"这个配置行不行"。

### 2.2 与 Who&When 的对照

| 对比项 | Who&When | AgentMonitor |
|---|---|---|
| **核心问题** | 谁在何时犯了决定性错误 | 系统整体表现会是多少 |
| **粒度** | 细粒度（Agent × Step，Δ_{i,t}(τ)=1） | 粗粒度（整个系统打一个分） |
| **方法** | 反事实干预（修掉某错误看结果是否翻转） | 监督回归（指标→性能） |
| **方向** | 事后归因（post-hoc） | 事前/即时预测（predictive） |
| **强弱** | 可解释性强、但需反复重跑；准确率不高（Agent 53.5% / Step 14.2%） | 预测准（0.89）但不可解释因果 |
| **共同点** | 都在做"**结果 → 原因/信号**"的映射，都受限于 LLM 判官能力 | |

**关键呼应**：AgentMonitor 的 post-edit 位置消融（Table 3）与 Who&When 的"决定性错误定位"是**同一问题的两面**——**在哪里动手最有效**。AgentMonitor 发现"并非越早越好、有时最后插最好"，这为 Who&When 的"决定性步骤"概念提供了工程侧的注脚。

### 2.3 与 Watson 的对照

| 对比项 | Watson | AgentMonitor |
|---|---|---|
| **可观测对象** | Agent 的**推理过程**（为什么这么想） | Agent 的**表现分数**（结果会怎样） |
| **手段** | 替代 Agent + FIM/RepCoT 复现推理轨迹 | LLM 判官打分 + 图属性 + XGBoost |
| **是否移动/修改轨迹** | 移动轨迹（surrogate replay） | 完全不干预执行（仅旁路采集） |
| **验证方式** | RO-SR vs WA-SR、Fisher 检验、LLM-as-a-judge | Spearman / 误差中位数 / 5 维划分 |
| **共同点** | 都大量依赖 **LLM 判官**，都受其偏差制约；都是"**用一个模型观测另一个模型**"的元认知范式 | |

**共同软肋**：两篇都暴露出 **LLM 判官不可靠**——Watson 需要 n=10 取多数以稳定判断，AgentMonitor 则实测存在**系统性低估**。这提示我们：**任何基于 LLM 打分的可观测性方法，都必须显式建模并校准判官偏差**。

### 2.4 与 AgentDropout 的对照

| 对比项 | AgentDropout | AgentMonitor |
|---|---|---|
| **目标** | **优化** MAS 拓扑（去冗余 Agent/连接） | **预测** MAS 性能 + 加固安全 |
| **是否改图** | 改（学出 mask，drop 节点/边） | 不改（只读图属性） |
| **优化方式** | REINFORCE 式无偏策略梯度 + 核范数正则 + DAGSample | 无需优化，直接回归 |
| **训练开销** | 40 样本、策略梯度、多个 LLM 骨干 | 1,796 数据点、XGBoost 网格搜索 |
| **共同要素** | **都把 MAS 形式化为图** `G=(V,E,F)`；都关心结构（节点数、边数、连接方式）与性能的关系 | |
| **互补关系** | AgentDropout 问"**哪些节点/边该删**" | AgentMonitor 问"**删了之后性能会变成多少**" → 二者可串联：用 AgentMonitor 做快速评估器给 AgentDropout 的策略提供廉价奖励信号 | |

**最有价值的联想**：AgentDropout 的策略梯度依赖真实执行得到奖励（昂贵），而 AgentMonitor 恰好能**用指标预测奖励**。把二者结合——**"预测器 + 优化器"闭环**——是一个非常自然的后续研究方向（用 AgentMonitor 的预测替代 AgentDropout 的部分真实评测，可大幅降低拓扑搜索成本）。

## 附三：已读论文横向定位表

| 论文 | 核心问题 | 观测层次 | 关键方法 | 侵入性 | 主要产出 | 最强指标 | 最大短板 |
|---|---|---|---|---|---|---|---|
| **AgentSight** | 系统里发生了什么 | 内核/系统边界 | eBPF uprobes/kprobes/tracepoints + 事件压缩 | 零侵入 | 边界追踪可观测性 | 521→37 事件压缩；2.9% 开销 | 语义层缺失 |
