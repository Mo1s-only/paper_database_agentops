# 第 5 章详细教程：多个 Agent 如何协作又如何互相拖累

## 1. 多 Agent 不等于多个并行模型调用

一个多 Agent 系统至少应明确：

- 不同主体的身份或角色；
- 每个主体可见的状态；
- 能调用的模型和工具；
- 消息或共享环境；
- 控制与终止协议；
- 责任和验证边界。

[AutoGen](https://arxiv.org/abs/2308.08155)展示了通过可定制、可对话 Agent 编排多种 LLM、工具与人工输入。框架提供编排能力，不保证多 Agent 一定优于单 Agent。

## 2. 五种常见拓扑

### 2.1 Pipeline

```text
Researcher → Analyst → Writer → Reviewer
```

优点：依赖明确。缺点：上游错误容易一路传播，后续可能无权回问。

### 2.2 Supervisor

```text
            ┌→ Researcher
Supervisor ─┼→ Coder
            └→ Reviewer
```

优点：集中分配和汇总。缺点：Supervisor 是瓶颈和单点责任源。

### 2.3 Debate/Peer

```text
Agent A ↔ Agent B ↔ Agent C → Judge
```

优点：暴露不同观点。缺点：高成本、从众、循环争论，Judge 可能错误聚合。

### 2.4 Shared workspace / Blackboard

```text
Agent A ─┐
Agent B ─┼→ 共享文件/数据库
Agent C ─┘
```

优点：解耦、可异步。缺点：竞态、过期状态、覆盖和来源不清。

### 2.5 Dynamic graph

Agent 和边按任务阶段变化。灵活，但归因与复现更难，必须保存拓扑版本和边变更事件。

## 3. 消息不只是文本

建议把一次 handoff 设计成结构化契约：

```json
{
  "from": "researcher",
  "to": "analyst",
  "goal": "比较三种配对策略",
  "inputs": ["trace.jsonl"],
  "completed": ["去重", "时间归一化"],
  "open_risks": ["3 个 response 无 request"],
  "constraints": ["不得强行配对"],
  "expected_output": "pairing_audit.csv",
  "acceptance": "Precision >= 0.95 on labeled subset"
}
```

若只发“数据已处理，请继续”，下游不知道完成定义、证据边界和风险。

## 4. 通信图、依赖图和因果图

假设 A 把消息发给 B，B 再把报告交给 C：

```text
通信图：A → B → C
```

但若 B 完全忽略 A 的消息，C 的错误不一定由 A 导致。只有当 A 的内容实际改变 B 的状态并影响 C，才有因果候选。

区分：

- 通信边：消息被发送；
- 数据依赖边：后一步读取了前一步产物；
- 控制边：前一步决定后一步是否执行；
- 因果边：干预前一步会改变结果，需额外假设或验证。

## 5. 教学案例：错误如何被放大

任务：根据三篇论文写研究结论。

```text
Researcher 错误记录论文年份为 2023
→ Analyst 把年份当成熟度证据
→ Writer 写“已有长期验证”
→ Reviewer 只检查语言，不核对来源
→ 最终报告通过内部流程但事实错误
```

可标注为：

- 触发点：Researcher 的错误事实；
- 传播边：Researcher → Analyst；
- 放大点：Analyst 将单一事实升级为论证；
- 检测遗漏：Reviewer 未执行来源核验；
- 暴露点：最终文本。

最后输出错误的 Writer 不一定是根因；Reviewer 也可能承担验证责任。

## 6. 共享状态和并发冲突

时间线：

```text
t0 A、B 同时读取 version=4
t1 A 写入 version=5
t2 B 基于旧 version=4 写入，覆盖 A
```

控制办法：

- 乐观并发：写入时要求 expected_version=4，B 的写入被拒绝；
- 文件锁或数据库事务；
- append-only 事件日志；
- 每个 Agent 独立分支，最后显式合并；
- 共享状态只保存事实，不保存无来源的推断。

## 7. 拓扑、成本和冗余

假设有 4 个 Agent，每轮所有节点两两通信。消息边可快速增长；增加节点也会增加模型调用和上下文重复。

区分：

- 节点冗余：某 Agent 移除后任务表现不降；
- 边冗余：某通信关系移除后表现不降；
- 保护性冗余：看似重复，但在故障时提供独立验证。

本地 AgentDropout 材料讨论节点与边的动态裁剪；学习时重点理解“成本下降必须与任务表现、稳定性和错误传播一起评价”。

## 8. 多 Agent 失败分类

[MAST](https://arxiv.org/abs/2503.13657)把失败模式归入系统设计、Agent 间失配、任务验证与终止等大类。可转化为检查表：

1. 角色是否完整且不冲突？
2. Agent 是否知道何时交接？
3. 信息是否被正确传递和使用？
4. 有没有独立验证节点？
5. 是否存在明确终止和失败升级？

## 9. 评价拓扑不能只看成功率

[MultiAgentBench](https://aclanthology.org/2025.acl-long.421/)使用里程碑式 KPI 分析协作过程，并比较不同协调拓扑。你的实验至少同时报告：

- 任务成功；
- 里程碑进展；
- 消息和模型调用成本；
- 错误传播长度；
- 关键路径延迟；
- 重复运行稳定性。

## 10. 实践与答案要点

### 实践

用“论文精读并写综述”任务实现纸面设计：单 Agent、pipeline、supervisor、shared-workspace 四版。为每版计算最坏情况下的模型调用数，并注入一个错误 DOI。

### 答案要点

- 多 Agent 的价值来自分工、并行或独立验证，而非数量本身。
- 通信发生不等于内容产生了因果影响。
- handoff 必须包含目标、证据边界、风险和验收条件。
- 共享状态需要版本、来源和并发控制。
- 拓扑实验要联合评价效果、成本和传播。
