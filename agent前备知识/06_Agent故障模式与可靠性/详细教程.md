# 第 6 章详细教程：从“失败了”到可操作的故障分类

## 1. Fault、Error、Failure

教学定义：

- **Fault**：系统中的缺陷或潜在原因，例如错误工具实现。
- **Error**：运行中出现的错误状态，例如工具返回了错误库存数。
- **Failure**：对外没有满足任务要求，例如未创建补货单。

一条链可以是：

```text
库存 API 缓存键错误（fault）
→ 返回旧库存 80（error）
→ Agent 判断无需补货（传播）
→ 实际库存 2 但没有下单（failure）
```

最终失败发生在末端，但修复点在上游。

## 2. 五个诊断问题

遇到失败时依次问：

1. 预期结果是什么？判据是否明确？
2. 第一个可观察异常是什么？
3. 异常通过哪些数据或控制边传播？
4. 哪个干预最可能阻止失败？
5. 当前证据能否区分竞争解释？

不要一开始就问“哪个 Agent 背锅”，否则容易把可见症状误当根因。

## 3. 分层故障本体

### 3.1 任务规范层

需求含糊、约束冲突、成功判据缺失。Agent 的输出可能合理，却无法客观评测。

### 3.2 模型决策层

错误事实、错误计划、遗漏约束、不恰当工具选择。

### 3.3 工具层

参数错误、权限错误、显式异常、静默错误、重复副作用。

### 3.4 协作层

角色缺失、handoff 不完整、共享状态冲突、错误消息被放大。

### 3.5 控制层

提前停止、无限循环、重试策略错误、预算耗尽、错误回退。

### 3.6 系统层

进程崩溃、网络中断、资源耗尽、数据库锁、时间同步问题。

### 3.7 评价层

真值错误、judge 偏差、解析错误、分母错误。评价器故障会让正确系统看似失败，或反之。

## 4. 显式错误与静默错误

### 显式错误

```json
{"ok": false, "error": "timeout"}
```

系统至少知道发生异常。

### 静默错误

```json
{"ok": true, "temperature": 230}
```

若单位应为摄氏度且环境是机房，这可能明显异常；如果没有范围、冗余传感器或后续验证，Agent 会把它当事实继续推理。[Tools Fail](https://aclanthology.org/2024.emnlp-main.790/)说明工具可靠性问题不能只简化为“选对工具”。

## 5. 级联失败的四个角色

建议不要只标一个根因标签：

| 角色 | 含义 |
|---|---|
| Trigger | 首个触发错误的事件 |
| Propagator | 传递或复制错误的节点/边 |
| Amplifier | 把局部错误扩大为更严重影响 |
| Detector/Masker | 发现错误或掩盖错误的步骤 |

教学例子：Researcher 给错数字；Analyst 复制；Writer 把它写进结论；Reviewer 未核验。四者责任不同。

## 6. 循环与“无进展”

循环不一定是完全重复文本。可检测特征：

- 同一工具和参数反复调用；
- 状态哈希长时间不变；
- 目标距离/里程碑没有改善；
- 错误类型重复出现；
- Token 增长但新证据为零。

恢复顺序：

```text
检测 → 暂停 → 汇总已知状态 → 改变策略/工具 → 降级或人工介入
```

仅增加最大步数可以止损，但不能解释为什么循环。

## 7. 重试、回退、回滚和修复

| 动作 | 适用 | 例子 |
|---|---|---|
| Retry | 暂时性故障 | 网络 503 后指数退避 |
| Fallback | 主路径不可用 | 换只读缓存或备用模型 |
| Replan | 原计划前提失效 | API 不可用，改用本地数据 |
| Rollback | 已发生副作用可撤销 | 回退数据库事务 |
| Compensate | 无法直接撤销 | 已发邮件后再发更正邮件 |
| Repair | 消除 fault | 修正配对算法或工具实现 |

错误分类应能指导动作，否则分类过于抽象。

## 8. 如何构造可复现故障

以“工具静默错误”为例：

1. 固定任务和正确工具输出；
2. 在特定 call_id 注入确定性错误；
3. 验证注入确实到达 Agent；
4. 保存 clean 与 faulty 两条轨迹；
5. 定义任务失败判据；
6. 标注责任步骤和传播区间；
7. 用替换为正确输出的局部重放验证。

若注入没有触发或被 Agent 自然纠正，该样本不能直接放进“失败归因”分母。

## 9. 标注协议示例

```yaml
task_id: T17
failure_observed: true
failure_type: tool.silent_wrong_value
trigger_event: E12
responsible_agent: inventory_agent
responsible_step: S4
propagation_edges: [E12->E15, E15->E19]
root_cause_confidence: 0.9
ground_truth_method: deterministic_injection_plus_replay
counterfactual: replace E12.output with clean output
counterfactual_result: task_success
annotator_notes: "最终 writer 仅消费错误事实"
```

教学字段需要根据你的最终 schema 调整。

## 11. 实践与答案要点

### 实践

设计三条 clean/faulty 对：工具静默错误、handoff 丢字段、重复工具调用。为每条写触发、传播、暴露、验证和恢复。

### 答案要点

- failure 是对外未满足要求，fault 是潜在原因，error 是错误状态。
- 第一个异常、最后错误和最有效修复点可以不同。
- 静默错误需要独立预期或事实验证。
- 故障注入必须验证实际触发。
- 分类的价值在于支持可复现实验和恢复策略。
