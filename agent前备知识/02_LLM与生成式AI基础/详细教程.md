# 第 2 章详细教程：从 Token 到模型调用

## 1. 先建立正确心智模型

一个基础自回归语言模型接收 token 序列，并为下一个 token 计算概率分布：

```text
P(token_t | token_1, token_2, ..., token_{t-1})
```

然后通过某种解码策略选出 token，再把它追加到上下文中继续生成。Agent 的“计划”“工具选择”和“反思”最终都要通过这种逐 token 生成表现出来，但 Agent 系统还额外包含状态、工具、控制流和环境。

### 1.1 agent的组成部分
Agent = LLM + Tool + State + Environment + Control Loop

🧠LLM（大脑 / 决策中枢）
角色：负责感知、推理、规划和决策。
局限：LLM 本身是无状态的、被动的——它不会主动调用工具，也不会记住上一轮对话。它只是一个“函数”：output = llm(input)。
在多智能体中的体现：每个 Agent 实例通常绑定一个 LLM 调用，但不同 Agent 可以使用不同的模型或不同的 Prompt 角色设定。
🛠️ Tool（手脚 / 执行器）
角色：LLM 与外部世界交互的接口，包括 API 调用、文件读写、代码执行、数据库查询等。
关键点：Tool 是 Agent 改变环境的唯一途径。没有 Tool，LLM 只能“说”，不能“做”。
在多智能体中的体现：一个 Agent 的 Tool 可以是另一个 Agent——这就是多智能体系统中“Agent 作为工具”的协作模式。
📦 State（记忆 / 上下文）
角色：维护 Agent 的短期工作记忆（当前对话、任务进度）和长期经验（向量库、知识图谱）。
关键点：State 是 Agent 跨轮次保持一致性的基础。没有 State，每一轮对话都是“失忆”的。
在多智能体中的体现：多智能体系统需要共享状态（Shared State），让不同 Agent 能读取彼此的工作成果，实现任务交接与协同。
🌍 Environment（环境 / 世界）
角色：Agent 所处的外部世界，包括文件系统、网络、数据库、其他 Agent、用户等。
关键点：Environment 是 Agent 感知和作用的客体。Agent 通过 Tool 改变 Environment，Environment 的变化又通过 Observation 反馈给 Agent。
在多智能体中的体现：Environment 不仅是物理/数字世界，还包括其他 Agent 构成的社会环境——Agent 之间通过共享环境间接通信。
🔄 Control Loop（控制流 / 执行循环）—— 你公式中缺失的关键
这是让 Agent 从“静态组件拼装”变成“动态自主系统”的核心：

```text
while !goal_achieved:
    observation = perceive(environment)       # 感知环境
    thought = llm(state + observation)        # LLM 推理决策
    action = parse(thought)                   # 解析为具体动作
    execute(action, tool)                     # 调用工具执行
    state.update(action, observation)         # 更新状态
    environment = apply(action, environment)  # 环境被改变
```
角色： orchestrator（编排器），负责驱动“观察→思考→行动→反馈”的循环。
关键点：没有 Control Loop，LLM + Tool + State + Environment 只是一堆静态组件，无法形成自主闭环。
在多智能体中的体现：Control Loop 可以是中心化的（一个主 Agent 调度子 Agent），也可以是去中心化的（每个 Agent 独立运行自己的循环，通过消息队列或共享状态协调）。
📌 总结：五要素的关系图
```

                    ┌─────────────┐
                    │   LLM       │ ← 决策中枢
                    │  (Brain)    │
                    └──────┬──────┘
                           │ 输出决策
                    ┌──────▼──────┐
   Environment ◄───┤   Tool      │ ← 执行器
   (环境)          │  (Hands)    │
       ▲           └──────┬──────┘
       │                  │ 改变环境
       │           ┌──────▼──────┐
       └───────────┤   State     │ ← 记忆与上下文
    反馈(Observation)│ (Memory)   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │Control Loop │ ← 驱动循环（你缺失的部分）
                    │ (Orchestrator)│
                    └─────────────┘
```

## 2. Token：成本和上下文的最小计量单位

### 2.1 Token 不是字符，也不总是单词

分词器会把文本映射为整数 ID。不同模型的分词器可能把同一句话切成不同 token：

```text
输入：AgentOps用于观测Agent运行

可能切分 A：Agent | Ops | 用于 | 观测 | Agent | 运行
可能切分 B：Ag | ent | Ops | 用 | 于 | 观 | 测 | Agent | 运 | 行
```

这是教学示意，不代表某一实际模型。实际切分必须用该模型对应 tokenizer 验证。

### 2.2 为什么这对你的项目重要

- Token 影响调用费用和上下文上限。
- 中文、JSON、代码和转义字符的 token 密度不同。
- 多 Agent 重复转发完整历史会快速放大 Token。
- `input_tokens`、`output_tokens`、`cache_read_tokens` 应分开记录。

可用 [Hugging Face LLM Course](https://huggingface.co/learn/llm-course/chapter2/7)学习 tokenizer、input IDs 和 attention mask 的基础操作。

## 3. Transformer 与注意力：学到够用即可

[Attention Is All You Need](https://arxiv.org/abs/1706.03762)提出以注意力为核心的 Transformer 架构。对 AgentOps，最重要的不是完整推导，而是理解：每个位置的表示可根据其他 token 的表示动态加权。

简化示例：

```text
“工具返回 200，但文件没有生成，所以任务失败。”
```

理解“所以任务失败”时，模型需要同时参考“200”和“文件没有生成”。注意力帮助建立上下文依赖，但它不是可导出的真实因果图，也不能证明模型内部使用了人类所理解的因果规则。

## 4. 自回归生成与非确定性

假设下一 token 的概率为：

| token | 概率 |
|---|---:|
| 调用 | 0.45 |
| 检查 | 0.35 |
| 返回 | 0.15 |
| 其他 | 0.05 |

贪心解码总选“调用”；采样可能选“检查”。Temperature 通常通过改变概率分布的尖锐程度影响随机性，top-p 则从累计概率质量内采样。

### 实验含义

即使 Prompt 相同，只要使用采样，轨迹也可能不同。即使 temperature 接近 0，后端版本、工具响应、并行时序和服务实现也可能造成差异。因此论文需记录：

```text
provider/model/version
temperature/top_p/max_tokens/seed（若支持）
system/user/tool messages
tool schema
重试策略和时间
```

## 5. 上下文、状态与记忆

### 5.1 上下文

当前模型调用实际可见的 token，包括系统指令、用户输入、历史消息、工具定义和检索内容。

### 5.2 状态

Agent 控制器用于决定下一步的结构化信息，可能只有一部分会发给模型，例如：

```json
{
  "task_id": "T17",
  "phase": "verify",
  "budget_left": 3,
  "artifact_path": "report.md"
}
```

### 5.3 记忆

跨步骤或跨运行保存并检索的信息。常见故障：

- 写入了错误事实；
- 检索不到需要内容；
- 找到过期版本；
- 相似度高但任务无关；
- 恶意内容被长期保存。

## 6. 结构化输出为何有用又会失败

假设希望模型输出：

```json
{
  "responsible_agent": "researcher",
  "step": 4,
  "confidence": 0.78
}
```

结构化输出便于解析、校验和统计，但至少有六类失败：

1. 非法 JSON；
2. 缺字段；
3. 类型错误，例如 step 为字符串；
4. 枚举值越界；
5. schema 合法但语义错误；
6. 输出被截断。

校验流程：

```text
原始输出
→ JSON 解析
→ schema 校验
→ 业务约束校验
→ 环境事实校验
→ 接受/修复/重试/人工介入
```

“符合 schema”只能证明形式正确，不能证明归因正确。

## 7. Prompt、工具结果和外部事实

考虑问题：“库存是否需要补货？”

- 模型参数提供一般知识；
- Prompt 提供决策规则；
- 工具读取当前库存；
- Agent state 保存已检查的商品；
- 数据库最终状态证明是否创建补货单。

若最终错误，必须分别检查这几层。把一切归为“模型幻觉”会掩盖工具、数据或控制流问题。

## 8. LLM-as-a-Judge 的正确用法

Judge 输入候选输出和评分准则，返回分数或标签。它适合开放文本的辅助评价，但有四个主要风险：

- 位置、长度、文风偏差；
- 与被评模型共享错误知识；
- 提示变化导致标准漂移；
- 自己也具有随机性。

一个较稳妥的评价层次：

```text
可执行真值（数据库终态、单元测试）
  > 明确规则
  > 盲化人工标注
  > 校准后的 LLM judge
  > 未校准的单次 LLM 判断
```

这不是绝对排序；开放任务可能没有完整可执行真值，但应组合多种证据。

## 9. 教学案例：为什么模型成功而 Agent 失败

任务：创建 `summary.md`，其中必须包含三条来源。

模型输出：

```json
{"tool":"write_file","arguments":{"path":"summary.md","content":"...三条来源..."}}
```

可能的失败链：

1. 模型正确选择工具；
2. 控制器把 `path` 误改为 `summay.md`；
3. 工具正常返回成功；
4. Agent 没有检查目标文件；
5. 最终声称完成；
6. 任务判定失败。

这条轨迹中，模型决策可能正确，故障在控制器或验证步骤。需要 trace 而不是只看最终文本。

## 10. 实践与答案要点

### 实践一：重复生成

对同一分类任务运行 10 次，保存完整参数、响应和 Token。计算一致率，并检查分歧是否集中在模糊样本。

### 实践二：结构化输出破坏测试

构造非法 JSON、缺字段、错误类型、合法但错误四种响应，验证解析器能否区分。

### 答案要点

- Token 是模型输入输出单位，不等同字符或单词。
- 注意力权重不应直接当因果解释。
- 模型非确定性要求重复运行和区间报告。
- schema 合法性与语义正确性必须分层验证。
- Judge 输出是测量工具的读数，不自动是真值。
