# 第 8 章详细教程：从相关事件走到可验证归因

## 1. 五种关系不要混用

考虑事件：

```text
A 在 10:00 输出错误数字
B 在 10:01 生成错误分析
最终任务失败
```

可能存在：

1. **时间关系**：A 早于 B；
2. **通信关系**：A 给 B 发了消息；
3. **数据依赖**：B 的输入包含 A 的数字；
4. **统计相关**：A 错时 B 常错；
5. **因果关系**：在保持其他条件可比时，修正 A 会改变 B 或最终结果。

前四项都不能自动推出第五项。

## 2. 观察、干预和反事实

因果学习可按三个问题层次理解：

- 观察：看到 `X=x` 时，`Y` 通常怎样？
- 干预：主动设置 `X=x` 后，`Y` 会怎样？
- 反事实：对这次已经发生的失败，如果当时把 `X` 改掉，结果会怎样？

[Pearl 等人的因果推断入门](https://bayes.cs.ucla.edu/PRIMER/)和 [Brady Neal 的公开课程](https://www.bradyneal.com/causal-inference-course)可用于系统补充 DAG、干预和潜在结果。

## 3. 用 DAG 表达假设

教学图：

```text
TaskDifficulty ─→ AgentA_Error ─→ AgentB_Error ─→ Failure
       └────────────────────────────────────────→ Failure
ModelQuality ───→ AgentA_Error
ModelQuality ───→ AgentB_Error
```

这里 `TaskDifficulty` 和 `ModelQuality` 可能是混杂因素。如果只观察“AgentA 错时更容易失败”，不能立刻断定全部效应来自 A；困难任务可能同时造成两者。

在故障注入实验中，你主动随机化某个工具输出，可以减少这类混杂，但注入本身必须足够真实且验证已触发。

## 4. Who&When 的“决定性步骤”直觉

[Who&When](https://proceedings.mlr.press/v267/zhang25cq.html)把自动失败归因任务细化为责任 Agent 和关键步骤。教学上可把决定性错误理解为：修正该步骤并保持合理后续执行后，任务有机会从失败转为成功。

困难在于：

- 一步错误可能被后续修复；
- 多个错误共同必要；
- 修复一个步骤会改变后续轨迹；
- “保持其他不变”在交互 Agent 中往往不现实。

因此 step-level 归因通常比 Agent-level 更难。

## 5. 执行图、错误依赖图和因果图

### 执行图

记录实际发生的 Agent、步骤、工具、消息和副作用。

### 错误依赖图

只保留错误事件及其可能传播关系，便于搜索候选。

### 因果图

表达干预假设和变量机制。它可能包含未直接记录的因素，边需要假设或实验支持。

构建流程：

```text
原始事件 → 执行图 → 异常节点 → 候选错误依赖边
→ 干预/重放验证 → 经验证的因果子集
```

不要把执行图所有边直接重命名为因果边。

## 6. 反事实重放实例

失败轨迹：

```text
E1 Researcher 检索论文
E2 Researcher 输出错误年份 2023
E3 Analyst 依据年份判断“研究已长期成熟”
E4 Writer 写入结论
E5 Outcome 判定事实错误
```

### 单点替换

把 E2 的年份替换为正确值，固定任务、模型配置和其他输入，重放 E3–E5。

结果可能是：

- 成功：E2 是强根因候选；
- 仍失败且理由不同：还有其他原因；
- 轨迹完全分叉：说明局部干预影响大，需要多次重放和分布性评价；
- 无法重放：当前系统的可复现性不足。

### 删除测试的风险

直接删除 E2 可能让 B 缺少输入，制造一个新故障。更合理的反事实通常是“替换为干净对应值”或“使用符合接口的中性输入”。

## 7. 多原因情形

假设任务只有同时满足 `A正确` 和 `B正确` 才成功：

```text
Success = A_correct AND B_correct
```

若 A、B 都错，单独修复 A 后仍失败，单独修复 B 后也仍失败；只有共同修复才成功。单事件反事实会漏掉联合必要原因。

因此标注可包含：

- singleton cause；
- joint cause set；
- upstream trigger；
- propagation edge；
- missing verifier。

## 8. 从简单基线到方法

按难度递增：

1. **最后错误基线**：选最终失败前最近的异常；
2. **最早错误基线**：选最先出现的异常；
3. **规则/图中心性**：按错误传播图排序；
4. **LLM 全轨迹判断**；
5. **检索+候选排序**；
6. **因果候选+反事实重放**。

简单基线很重要。如果复杂方法只略高于“最后错误”，可能没有真正学习因果结构。

## 9. 诊断报告格式

```yaml
failure: "目标报告不存在"
candidates:
  - rank: 1
    target: "writer.step_4"
    type: "wrong_output_path"
    evidence: [E31, E34, E39]
    supporting_relations: ["tool-call", "file-write", "outcome-check"]
    confidence: 0.87
    alternative: "目标目录权限不足"
    missing_evidence: "工具内部路径规范化日志"
    proposed_test: "replace path and locally replay step_4_to_outcome"
```

置信度要说明来源：模型分数、排序概率、规则强度或人工判断，不能只是随意小数。

## 10. 教学实验：四档证据归因

为 30 条可控失败准备：

- D0：最终输出；
- D1：Agent 消息；
- D2：完整执行图；
- D3：执行图 + 反事实结果。

每档用相同候选空间和相同真值，报告 Agent/Step/Edge 指标。若 D2 直接包含 `responsible=true` 标签，应移除，否则是答案泄漏。

## 11. 答案要点

- 时序、通信、依赖和相关是因果证据，但通常不充分。
- 反事实必须明确干预内容、保持条件和成功判据。
- 删除节点可能引入接口破坏，应优先使用语义匹配替换。
- 多原因需要联合干预，单点重放可能漏检。
- 归因报告应保留替代解释和缺失证据。
