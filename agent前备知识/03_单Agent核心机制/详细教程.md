# 第 3 章详细教程：一个 Agent 怎样完成任务

## 1. 从“调用模型”到“Agent”

下面两个程序并不相同。

### 固定 LLM 工作流

```text
用户输入 → 调用模型生成摘要 → 返回摘要
```

控制流由程序员预先确定，模型只生成一次内容。

### Agent 闭环

```text
用户目标
→ 观察状态
→ 模型选择动作
→ 工具改变环境
→ 观察工具结果
→ 更新状态
→ 决定继续、重试、换计划或停止
```

Agent 的关键是“模型输出参与下一步控制”，并且环境反馈会再次影响模型或控制器。

## 2. 最小 Agent 状态机

教学任务：读取一个 CSV，计算平均值并写报告。

```text
START
  ↓
CHECK_INPUT ──文件不存在──→ ASK_USER/FAIL
  ↓存在
READ_FILE ──解析错误──→ REPAIR_OR_FAIL
  ↓成功
COMPUTE ──结果异常──→ VERIFY
  ↓
WRITE_REPORT
  ↓
VERIFY_OUTPUT ──不满足──→ RETRY/REPLAN
  ↓满足
DONE
```

每个状态都应定义：允许动作、输入、输出、超时、失败转移和证据。这比把整个过程记为一段聊天更适合监控。

## 3. ReAct：推理与行动交错

[ReAct 论文](https://arxiv.org/abs/2210.03629)把 reasoning trace 与任务动作交错，用环境观察更新后续计划。一个简化教学轨迹：

```text
Thought: 我需要知道实验目录有哪些文件。
Action: list_files("results/run-17")
Observation: session.db, record.log, verification.txt

Thought: 先检查验证结果。
Action: read_file("verification.txt")
Observation: passed 13, failed 0

Thought: 这只证明采集链路通过，还要检查 orphan_response。
Action: search("report-audit.txt", "orphan_response")
Observation: 1 match
```

重点不是公开模型内部思维，而是理解控制循环：动作产生新观察，观察改变后续动作。工程 trace 至少应记录 Action 和 Observation；不可获得的内部推理不能伪装成真实证据。

## 4. Planner–Executor 与 Router

### 4.1 Planner–Executor

```text
Planner: 生成步骤 [检查数据, 查询数据库, 生成图, 写结论]
Executor: 逐步调用工具
Verifier: 检查每步产物
Replanner: 失败时修改剩余计划
```

优势是计划和执行职责清晰；风险是最初计划可能过时，执行器机械遵守错误计划。

### 4.2 Router

Router 根据任务特征选择专用路径：

```text
输入
├─ 代码问题 → coding agent
├─ 文献问题 → research agent
└─ 数据问题 → analysis agent
```

Router 错误会让后续所有步骤在错误能力边界内运行，因此路由决策应作为可观察事件。

## 5. 状态、上下文和事件如何对应

教学状态：

```json
{
  "run_id": "R1",
  "goal": "生成实验摘要",
  "phase": "verify",
  "artifacts": ["summary.md"],
  "budget": {"steps_left": 2},
  "last_error": null
}
```

一次状态转移：

```json
{
  "event_id": "E9",
  "parent_event_id": "E8",
  "agent_id": "writer",
  "step_id": "S4",
  "event_type": "tool_call",
  "tool": "read_file",
  "status": "success",
  "output_ref": "sha256:..."
}
```

状态是“当前世界的压缩表示”，事件是“状态怎样变化的记录”。重放需要事件，继续执行需要状态。

## 6. 记忆机制的四步链

```text
写入 → 存储 → 检索 → 使用
```

每一步都可能失败：

| 环节 | 例子 | 诊断证据 |
|---|---|---|
| 写入 | 把错误结论记为事实 | 写入内容、来源、版本 |
| 存储 | 覆盖旧记录或丢失 | 数据库事务、对象版本 |
| 检索 | 找到相似但无关记录 | query、候选、相似度 |
| 使用 | 正确记忆被错误解释 | Prompt、决策和后续动作 |

因此“记忆模块出错”太粗，论文级诊断要定位到具体环节。

## 7. 反思、验证、重试和重规划

### 反思

让模型根据反馈写一段改进意见。[Reflexion](https://arxiv.org/abs/2303.11366)研究了把语言反馈放入情景记忆以改进后续试验。它改变的是后续上下文，不一定更新模型参数。

### 验证

用外部标准检查结果，例如单元测试、数据库终态、文件哈希或独立人工标签。

### 重试

在策略基本不变时重新执行，适合暂时性网络错误，不适合确定性的错误计划。

### 重规划

根据新证据改变剩余步骤，适合工具不可用或原计划前提失效。

示例：文件路径错误时，重复 5 次相同写入是无意义重试；先列目录、修正路径再写是重规划。

## 8. 停止条件与循环

Agent 不应只依赖模型说“完成”。可组合：

- 明确终态判据；
- 最大步骤数；
- Token/时间/费用预算；
- 重复动作检测；
- 无进展检测；
- 人工升级条件。

教学循环：

```text
搜索 A → 没找到 → 换关键词搜索 A → 没找到 → 再换表达搜索 A
```

若连续三步没有新增来源或状态变化，可以标记 `no_progress`。注意这是一条规则，需要在不同任务上校准，不能直接当通用真理。

## 9. 工程伪代码

```python
state = initialize(task)

while not terminal(state):
    if state.steps >= MAX_STEPS:
        return fail("budget_exhausted")

    observation = observe_environment(state)
    action = policy(model, state, observation)
    event = execute_with_audit(action)
    state = reduce(state, event)

    if violates_invariant(state):
        state = recover_or_escalate(state)

return verify_outcome(state)
```

这里的 `execute_with_audit` 和 `verify_outcome` 是 AgentOps 的关键：前者保留动作证据，后者避免把自我声明当成功。

## 10. 映射到 AgentSight

| Agent 抽象 | AgentSight 证据候选 |
|---|---|
| run/session | session 数据库与运行元数据 |
| model call | `llm_calls`、`token_usage` |
| tool action | `tool_calls` |
| environment effect | `audit_events`、文件与网络事件 |
| process hierarchy | `process_nodes` |
| budget/resource | `resource_samples`、Token |

缺少的是稳定的高层 `agent_id/step_id` 映射和完整请求—响应配对，这正是统一 schema 的研究空间。

## 11. 实践与答案要点

### 实践

为“读取一次 AgentSight 实验并生成诊断摘要”设计：

1. 状态机；
2. 每个状态允许的工具；
3. 每次转移的审计事件；
4. 三个终态判据；
5. 两个恢复策略。

### 答案要点

- Agent 与固定工作流的区别在于模型/策略是否参与控制闭环。
- 计划、执行、环境副作用和验证应分开记录。
- 记忆错误要分解到写入、存储、检索、使用。
- 反思是语言反馈机制，不自动等于外部验证。
- “完成”必须由任务判据确认，而非模型自报。
