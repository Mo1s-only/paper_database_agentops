# 第 1 章详细教程：Agent 运行在什么之上

## 1. 为什么研究 Agent 还要学操作系统和网络

LLM 只负责根据输入生成下一个输出。一个 Agent 真正完成任务，还要依赖进程调度、文件系统、网络请求、数据库和权限系统。下面是一个“让编码 Agent 创建文件”的真实抽象：

```text
用户输入
  ↓
claude 主进程（PID 348）
  ├─ 发起模型 HTTP 请求
  ├─ 得到“调用 Write 工具”的决定
  ├─ 调用工具进程或内部函数
  └─ 写入 hello.txt
        ↓
操作系统记录文件打开/写入
        ↓
AgentSight 将进程、工具、模型、文件事件写进 session.db
```

如果只看模型最后说“文件已创建”，你观察到的是**声明**；如果看见文件、文件哈希和系统审计事件，才观察到**副作用**。AgentOps 的第一原则就是把“模型说了什么”和“系统做了什么”分开。

推荐先读免费的 [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/)。它用“虚拟化、并发、持久化”组织操作系统知识，正好对应 AgentOps 的三个问题：谁在运行、事件如何交错、证据如何保存。

## 2. 进程、线程和进程树

### 2.1 程序与进程

- 程序是磁盘上的静态代码。
- 进程是程序的一次运行实例，包含 PID、地址空间、打开的文件、权限和运行状态。
- 线程是进程内部的执行流；多个线程共享进程的大部分内存和文件描述符。

教学例子：同一个 `python agent.py` 同时启动两次，会得到两个 PID。它们代码相同，但内存、网络连接和任务状态不同。因此 trace 不能只用程序名作身份。

### 2.2 PID、PPID 能证明什么

假设事件表是：

| PID | PPID | 命令 | 时间 |
|---:|---:|---|---|
| 100 | 1 | `claude` | 10:00:00 |
| 112 | 100 | `python tool.py` | 10:00:03 |
| 119 | 112 | `git status` | 10:00:04 |

它支持的直接判断是：112 由 100 派生，119 由 112 派生。它**不能单独证明**：

- PID 112 一定属于哪个逻辑 Agent；
- `git status` 是由哪条模型消息决定的；
- 这次命令导致最终任务失败；
- 两台机器上的进程有什么关系。

需要继续加入 `run_id`、`agent_id`、工具调用 ID、时间、参数和消息依赖。父子关系是结构证据，不是完整因果结论。

### 2.3 退出码也只是一个局部信号

```text
exit_code = 0   → 程序认为自己正常退出
exit_code != 0  → 程序报告异常退出
```

反例：脚本成功生成了一个格式错误的报告，退出码仍可能是 0。相反，一个完成主要任务的脚本可能因清理失败返回 1。任务语义需要独立的 outcome 判据。

## 3. 文件、标准流与副作用

进程常见 I/O：

- `stdin`：输入；MCP 本地服务器常通过它接收 JSON-RPC。
- `stdout`：正常输出。
- `stderr`：诊断输出。
- 文件描述符：进程访问文件、管道、socket 的数字句柄。

### 例子：为什么“工具返回成功”仍不够

工具返回：

```json
{"ok": true, "path": "report.md"}
```

至少还要核对：

1. 文件是否存在；
2. 路径是否在预期工作区；
3. 内容是否满足要求；
4. 写入者是否为预期进程；
5. 是否覆盖了不该覆盖的文件；
6. 返回后文件是否又被其他 Agent 修改。

这就是“工具层证据”和“环境层证据”的区别。

## 4. HTTP、TLS 和流式响应

[MDN 的 HTTP 概览](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)将 HTTP 描述为请求—响应式的应用层协议。模型 API 通常是：

```http
POST /v1/messages HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer ***
X-Request-ID: req-17

{"model":"m1","messages":[...]}
```

响应：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
X-Request-ID: req-17

data: {"delta":"先"}
data: {"delta":"读取文件"}
data: [DONE]
```

关键点：

- HTTP 200 只说明协议请求成功处理，不保证模型答案正确。
- HTTPS 是 HTTP 语义经过 TLS 加密传输；系统探针可能看到连接，却看不到明文。
- 流式响应由多个 chunk 组成，不能把每个 chunk 当成一次完整模型调用。
- 代理、重试、连接复用和 HTTP/2 多路复用都会让“一个 socket = 一次调用”失效。

## 5. 并发为什么会破坏“最近时间配对”

教学例子：

```text
10:00:00.000 请求 A 发出
10:00:00.010 请求 B 发出
10:00:00.100 响应 B 返回
10:00:00.200 响应 A 返回
```

若算法把响应配给“最近请求”，响应 A 很可能被错误配给 B。可靠配对优先级可设计为：

1. 协议/业务 request ID；
2. 同一连接与流 ID；
3. 同一进程/线程和明确序列号；
4. 内容哈希或唯一 marker；
5. 最后才用受约束的时间窗口，并输出置信度。

这直接对应项目中的 P0 配对任务：不确定的匹配应保留为候选或舍弃，而不是制造一个看似完整的调用。

## 6. SQLite、事务与 WAL

### 6.1 三个文件

```text
session.db       主数据库文件
session.db-wal   尚未 checkpoint 回主库的提交记录
session.db-shm   WAL 索引与进程间协调所需的共享内存文件
```

[SQLite 官方 WAL 文档](https://www.sqlite.org/wal.html)说明：WAL 模式把修改追加到单独日志，之后通过 checkpoint 合并回数据库；读者与写者可更多地并发，但通常仍只有一个写者。

因此复制正在运行的实验时，只复制 `session.db` 可能丢失已经提交但尚未 checkpoint 的数据。三者应作为一个证据包处理。

### 6.2 用 SQL 重建证据链

先查看 schema：

```sql
.tables
.schema process_nodes
.schema tool_calls
```

再做从健康检查到关联分析：

```sql
-- 每张关键表有多少行
SELECT 'process_nodes' AS table_name, COUNT(*) AS n FROM process_nodes
UNION ALL SELECT 'tool_calls', COUNT(*) FROM tool_calls
UNION ALL SELECT 'llm_calls', COUNT(*) FROM llm_calls;

-- 查找非成功工具调用（字段名以实际 schema 为准）
SELECT *
FROM tool_calls
WHERE status IS NULL OR status NOT IN ('success', 'ok')
ORDER BY timestamp;
```

不要直接复制示例字段名到论文结论中；先用 `.schema` 核对当前版本。

## 7. 时间戳、时钟和事件顺序

### 7.1 两类时钟

- 墙上时钟：可转换为日期时间，但可能被 NTP 校正或人为修改。
- 单调时钟：适合计算持续时间，不会因系统时间调整倒退，但通常不能跨主机直接比较。

### 7.2 同时间不等于同因果

两个事件相隔 5ms 可能有关，也可能只是并发。因果关联还需进程关系、调用 ID、数据匹配或显式上下文传播。时间邻近是候选生成信号，不应单独成为归因真值。

## 9. 本章实践与答案要点

### 实践

选一个历史 AgentSight 实验，不运行新模型：

1. 画进程树；
2. 按时间排列模型、工具、文件与网络事件；
3. 标出直接关联、推断关联和无法关联；
4. 写出三条“当前证据不能证明”的结论。

### 答案要点

- `PID/PPID` 支持进程派生，不直接支持语义责任。
- 成功状态应至少有协议、工具和任务三个层次。
- request–response 配对应优先依赖稳定 ID，而非纯时间。
- WAL 文件属于数据库持久状态的一部分。
- 时间顺序是因果推断的必要线索之一，但通常不充分。
