# 练习与验收答案：AgentOps 可观测性与追踪

## 一、三层证据源

| 层 | 代表数据 | 能回答 | 不能单独回答 |
|---|---|---|---|
| 应用日志 | prompt 摘要、计划、工具语义、验收状态 | Agent 为什么选择某动作（声明层） | 实际系统调用是否发生 |
| OpenTelemetry | trace/span、属性、事件、状态、link | 跨服务时序、依赖和延迟 | 模型内部因果、未插桩行为 |
| 系统事件 | 进程、文件、网络、系统调用/eBPF | 实际资源活动 | 业务意图和内容正确性 |

专业设计不是让三层重复记录同一大段文本，而是使用稳定 ID 串联互补证据。

## 二、统一标识设计

```text
trace_id: 一次端到端任务
span_id: 当前操作（model_call/tool_call/verification）
parent_span_id: 同一树中的直接父操作
span_link: 非树状关系，如批处理、消息队列、一次结果被多任务消费
session_id/conversation_id: 产品会话语义
pid + process_start_time: 操作系统进程身份
tool_call_id/request_id: 协议级调用身份
artifact_id + content_hash: 副作用对象身份
```

示例：应用 span `tool.write` 携带 `tool_call_id=C17`、`pid=348`；系统文件事件携带同一 pid、时间区间和 `artifact_id=F9`；结果记录保存 `sha256`。显式 ID 是主要连接，时间区间和进程是交叉验证。

W3C `traceparent` 解决跨服务传播，格式含 trace-id、parent-id 和 flags；`tracestate` 只放厂商状态，不能放 PII。异步 fan-in/fan-out 不宜伪造成单父树，可用 OpenTelemetry span links 表示。

## 三、缺失证据实验

设计：从 100 个完整任务构造固定诊断问题集，如“哪个工具首次产生错误副作用”“哪次重试改变结果”。对 span/系统事件按 10%、30%、50% 随机删除，并另做结构化删除（专删失败 span），每个比例重复抽样。

| 缺失率 | 可回答率（教学占位） | 根因 Top-1（教学占位） | 未知率 |
|---:|---:|---:|---:|
| 0% | 待测 | 待测 | 待测 |
| 10% | 待测 | 待测 | 待测 |
| 30% | 待测 | 待测 | 待测 |
| 50% | 待测 | 待测 | 待测 |

必须区分 MCAR 式随机缺失与 MNAR 式结构性缺失。生产故障常让采集器同时失效，因此随机删除通常高估鲁棒性。

## 四、成本估算

令每任务 span 数为 `S`，平均序列化字节 `B`，任务速率 `R/day`，保留天数 `D`，采样率 `p`：

`raw_storage = S × B × R × D × p`。

再乘索引/副本系数 `k`（常大于 1，但必须实测）得到平台存储。时间成本包括埋点 CPU、导出队列和查询延迟；token 成本只在将 trace 送入 LLM 时产生；隐私成本需按字段敏感等级、访问者和保留期评估，不能折算成单一字节数。

建议用价值密度优化：错误任务全量、成功任务抽样；大 payload 存对象仓库，仅在 span 留摘要和引用；秘密字段不采集而非事后打码。

## 五、验收问题参考答案

1. **observability 与 monitoring？** monitoring 围绕预定义指标/告警判断已知问题；observability 强调从外部输出推断内部状态，支持探索未知问题。可观测性不是“日志很多”。
2. **父子 span 等于因果吗？** 不等于。它首先表达执行上下文关系；共享原因、异步消息、错误链接或插桩策略都可能使树关系与实际因果不同。
3. **eBPF 看得见什么？** 能观测内核边界的进程、系统调用、网络和文件事件；通常看不懂加密后的应用语义、模型意图和内存中的业务对象，需要应用层关联。
4. **`orphan_response` 为什么信息不足？** 它说明配对算法未找到请求，不说明请求一定不存在；原因可能是采集缺失、跨进程、流式协议、时间窗错误或真正孤立。应保留候选集合与置信度。

## 六、评分标准（100 分）

分层证据 20；统一 ID 25；缺失实验 20；成本/隐私 20；边界论证 15。若把 `parent_span_id` 直接当因果真值，最高 65 分。
