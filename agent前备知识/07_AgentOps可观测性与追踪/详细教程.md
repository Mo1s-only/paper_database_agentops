# 第 7 章详细教程：怎样看见 Agent 的真实运行

## 1. 监控、日志、指标、追踪和可观测性

### 日志 Log

离散事件记录：

```json
{"time":"10:00:03","level":"ERROR","message":"tool timeout","call_id":"C4"}
```

擅长回答“发生了什么具体事件”，但若缺少 `run_id/trace_id`，很难串成端到端过程。

### 指标 Metric

聚合数值：

```text
tool_error_rate = 3.2%
p95_latency = 1.8s
tokens_per_run = 42,100
```

擅长发现趋势和告警，不擅长解释某一次任务为什么失败。

### 追踪 Trace

把一次请求或任务经过的多个操作关联起来。OpenTelemetry 将 Span 定义为一个工作单元；多个 Span 通过上下文传播组成 Trace。官方概念页可从 [Signals](https://opentelemetry.io/docs/concepts/signals/)和 [Traces](https://opentelemetry.io/docs/concepts/signals/traces/)开始。

### 可观测性 Observability

目标不是“收集很多数据”，而是能依据外部信号回答系统内部状态问题，例如：

- 哪个 Agent 的哪一步首先偏离？
- 模型调用成功后为什么没有文件副作用？
- 错误通过哪条消息传播？
- 诊断失败是因为方法弱还是证据缺失？

## 2. 一个 Span 的组成

```json
{
  "trace_id": "T1",
  "span_id": "S3",
  "parent_span_id": "S1",
  "name": "tool.write_file",
  "start_time": "...",
  "end_time": "...",
  "status": "OK",
  "attributes": {
    "agent.id": "writer",
    "tool.name": "write_file",
    "file.path_hash": "..."
  },
  "events": [
    {"name":"validation_passed","time":"..."}
  ]
}
```

注意：父子 Span 通常表达操作嵌套或上下文传播，不自动证明因果责任。例如父 Span 可能启动两个并行子 Span，其中一个失败但不影响最终结果。

## 3. 上下文传播为何关键

分布式调用：

```text
Agent Host → MCP Client → MCP Server → 外部 API
```

若每层都创建本地 ID 但不传播 trace context，后端只能看到四段孤立日志。传播 `trace_id`、span context 或等价调用 ID 后，才能构建一条完整链。

异步场景中，producer 和 consumer 可能不是严格父子调用；需要 Span Link 或显式消息 ID 表示关联。不要为了得到漂亮树形图而伪造父子关系。

## 4. 三种观测位置

### 4.1 应用层插桩

在 Agent 框架中记录 `agent/step/message/tool`。

优点：语义最强。缺点：框架依赖、容易遗漏绕过框架的真实动作。

### 4.2 代理/网关层

通过模型 API 网关或工具代理记录请求响应。

优点：集中、容易统计。缺点：看不到本地文件/进程副作用，无法观察绕过代理的流量。

### 4.3 系统边界层

通过进程、文件、网络、stdio、TLS 边界观测。AgentSight 使用 eBPF 等系统机制建立跨框架证据。

优点：更接近实际动作。缺点：原始信号缺少 Agent 语义，TLS/静态链接/异步线程会增加解析和关联难度。

[Linux Kernel BPF 文档](https://docs.kernel.org/bpf/index.html)是 eBPF 机制的官方入口；eBPF 是采集机制，不是自动因果推理器。

## 5. 统一事件 schema：逐字段理解

教学 schema：

```json
{
  "run_id": "R17",
  "event_id": "E34",
  "parent_event_id": "E20",
  "agent_id": "writer",
  "step_id": "S5",
  "event_type": "file_write",
  "source_layer": "kernel",
  "timestamp_start": 1000234000,
  "timestamp_end": 1000239000,
  "clock_domain": "monotonic_host_A",
  "process": {"pid":348,"ppid":100,"host":"host_A"},
  "input_ref": "sha256:...",
  "output_ref": "sha256:...",
  "status": "success",
  "confidence": 0.98,
  "completeness": "payload_redacted"
}
```

字段解释：

- `run_id`：端到端任务边界；
- `event_id`：事件唯一身份；
- `parent_event_id`：操作层父事件，不等同因果责任；
- `agent_id/step_id`：高层语义；可能需要从多个信号推断；
- `source_layer`：证据从应用、传输还是内核获得；
- `clock_domain`：避免跨主机直接比较不可比时间；
- `input_ref/output_ref`：原文可脱敏，保留引用和哈希；
- `confidence`：关联置信度，不是任务正确概率；
- `completeness`：明确丢失、截断或脱敏。

## 6. 一个跨层追踪例子

任务失败：“报告未生成”。

| 时间 | 层 | 事件 | 解释 |
|---|---|---|---|
| t1 | Agent | 决定调用 write_report | 高层意图 |
| t2 | Tool | tool_call status=success | 工具自报成功 |
| t3 | Process | writer 子进程 exit=0 | 进程正常退出 |
| t4 | File | 写入 `reports/tmp.md` | 实际副作用路径错误 |
| t5 | Agent | 未执行目标路径验证 | 控制流缺失 |
| t6 | Outcome | `reports/final.md` 不存在 | 任务失败 |

若只看 t1–t3，会误判成功；系统层文件证据揭示了“意图—效果”差距。

## 7. 采样与证据缺失

### 头部采样

任务开始时决定是否记录。成本可控，但可能错过后来发生的失败。

### 尾部采样

看到任务结果后决定是否保留完整 trace。更适合保留异常，但需要临时缓冲。

### 自适应采样

平时记录低成本元数据，检测到异常后提高粒度。研究问题是：触发是否足够早，升级前丢失的证据是否可恢复。

### 缺失不是随机的

如果高负载时最容易丢事件，而高负载又最容易失败，那么缺失机制与失败相关。不能把缺失样本简单删除后声称结果无偏。

## 8. 观测开销怎样测

成对运行同一任务：

```text
overhead_time = (T_on - T_off) / T_off
overhead_cpu  = (CPU_on - CPU_off) / CPU_off
```

还要报告：

- 日志字节/任务；
- 数据库写放大；
- 内存峰值；
- 丢事件率；
- 对任务成功率的影响；
- 隐私和人工处理成本。

必须重复运行并报告区间，不能用一次差值当稳定开销。

## 9. AgentSight 数据映射

```text
process_nodes     → 进程与父子关系
audit_events      → 进程、文件、LLM 审计事件
llm_calls         → 模型请求/响应与状态
tool_calls        → 工具输入输出及关联 PID
network_targets   → 外部主机、路径和错误
resource_samples  → CPU、RSS 等资源
token_usage       → 输入、输出、缓存 Token
```

当前项目中出现 `orphan_response` 时，应记录为“捕获到响应但缺少可靠 request 关联”，而不是补一个猜测的 request。

## 10. 实践：证据消融

对同一失败构造四种输入：

1. 只给最终输出；
2. 加消息和工具日志；
3. 加完整应用/系统 trace；
4. 加反事实重放结果。

让同一诊断方法输出候选根因。比较准确率前，先检查不同证据档是否直接暴露标签，避免“更多证据”只是“答案泄漏”。

## 11. 答案要点

- 日志描述事件，指标描述聚合趋势，Trace 关联一次执行路径。
- Span 父子关系是结构关系，不自动等于因果责任。
- 应用层语义强，系统层接近实际副作用；跨层组合才有价值。
- schema 必须表达来源、缺失和不确定性。
- 观测成本与证据价值要一起评价。
