# 练习与验收答案：论文研究方法与课题衔接

> 本章给出可直接改写的研究卡，但不是替用户宣称论文结果。所有尚未完成的实验均标为 `UNVERIFIED` 或 `AUTHOR_INPUT_NEEDED`。

## 一、六字段研究问题

| 字段 | 参考答案 |
|---|---|
| Population | 具有模型、工具和多 Agent 通信的开源 Agent 工作流 |
| Intervention | 融合应用 trace、系统事件和错误传播图的诊断方法 |
| Comparator | 仅应用日志、仅 trace、无传播图、代表性现有方法 |
| Outcome | 根因 Top-1/MRR、未知率、诊断时延、token/存储/人工成本 |
| Context | 预定义任务与故障注入；版本、模型、预算和机器固定 |
| Unit | 独立的任务–故障实例，而不是单条 span |

主 RQ 示例：**在预定义 Agent 任务与故障实例上，相比仅使用应用日志，融合多层证据与传播图的方法是否提高根因定位 Top-1，并在可接受的观测和推理成本内保持跨框架效果？**

子问题：RQ1 诊断有效性；RQ2 不同证据源的增量贡献；RQ3 证据缺失下鲁棒性；RQ4 跨框架迁移；RQ5 开销与人工负担。

## 二、贡献—新颖性—证据—风险表

| 候选贡献 | 新颖性主张 | 所需证据 | 主要风险 | 当前状态 |
|---|---|---|---|---|
| 统一事件/传播 schema | 跨应用与系统层关联 | 多框架映射覆盖、案例与失败分析 | 只是工程整合 | `UNVERIFIED` |
| 根因候选排序方法 | 多层证据提高定位 | 强基线、消融、统计区间 | 标签泄漏 | `UNVERIFIED` |
| 反事实 replay 验证 | 区分异常与因果影响 | 可重复干预、保真度分析 | replay 不代表在线环境 | `UNVERIFIED` |
| 数据/基准与工具链 | 可复现实验工件 | 文档、版本、许可、独立复现 | 样本窄 | `UNVERIFIED` |

“设计并实现了系统”是系统贡献，不等于研究结论。方法贡献必须由对照实验支持；数据贡献要说明采样、标签质量和许可。

## 三、Claim–Evidence 示例（10 条）

| Claim | Evidence needed | 状态 |
|---|---|---|
| C1 现有应用日志无法稳定覆盖系统副作用 | 文献 + 本地覆盖率审计 | 待验证 |
| C2 统一 schema 可表达目标框架事件 | schema 映射与未映射比例 | 待验证 |
| C3 系统事件增加静默工具错可见性 | `-System` 消融 | 待验证 |
| C4 传播图提高级联故障定位 | `-Graph` 配对实验 | 待验证 |
| C5 方法优于仅日志基线 | 主指标与 95% CI | 待验证 |
| C6 对 30% 证据缺失仍具鲁棒性 | 缺失机制实验 | 待验证 |
| C7 跨两个框架仍有效 | 留一框架外部验证 | 待验证 |
| C8 观测开销可接受 | CPU/内存/存储/延迟测量 | 待定义阈值 |
| C9 标签具可靠性 | 双人标注、一致性与裁决记录 | 待验证 |
| C10 工件可复现 | 干净环境独立复现 | 待验证 |

不要把“计划采集”“系统支持”写成“实验表明”。只有结果产生、核验并固定后才能把状态改为 `VERIFIED`。

## 四、实验矩阵与 Go/No-Go

| 维度 | 水平 |
|---|---|
| Framework | 至少 2 个，且事件模型不同 |
| Task | 检索写作、代码/文件操作、工具交互 |
| Failure | 模型、工具、通信、环境、观测缺失 |
| Evidence | Full、App-only、-Trace、-System、-Graph |
| Method | 本方法、规则、最近异常、现有代表基线 |
| Repeat | 每任务/条件多 seed；数量由功效与预算决定 |

Go/No-Go 关卡：

1. **Instrumentation gate**：关键事件覆盖率和关联 precision 达到预定阈值，否则先修采集。
2. **Label gate**：标注指南稳定、分歧可解释，否则不能做大规模评测。
3. **Pilot gate**：小样本能区分最弱/最强基线且没有明显泄漏，否则重新定义任务。
4. **Main-study gate**：冻结代码、数据划分、指标与排除规则后才运行主实验。
5. **Claim gate**：只有 CI、消融和失败分析共同支持时才升级论文主张。

具体阈值与样本量是 `AUTHOR_INPUT_NEEDED`：必须结合时间预算、先导方差和导师要求决定，不能凭空写数字。

## 五、五个审稿问题参考回答

1. **“只是集成已有组件？”** 回答应把工程工件与可检验方法分开：若统一证据模型、跨层链接或干预式归因确有新机制，分别用覆盖、准确率和消融证明；若没有，则诚实定位为系统化实证研究。
2. **“root cause 定义含糊？”** 预先定义系统边界、结果变量和干预：在保持其他输入不变时，修复候选事件能显著降低失败概率，并报告多因与未知。
3. **“是否标签泄漏？”** 做字段审计、盲化方法名、移除注入器特征、反事实打乱、跨框架留出测试；报告发现的泄漏而非只说“没有”。
4. **“能否跨框架？”** 使用框架无关核心 schema 加来源特定 adapter；在未参与开发的框架上报告映射覆盖和性能下降。两个相似框架不能支撑普适性。
5. **“人工成本呢？”** 记录埋点、标注、诊断和复核分钟数；报告每任务成本与学习曲线，将人的时间与 token/存储一起纳入总成本。

## 六、关键概念答案

1. **demo/prototype/feasibility/effectiveness**：demo 展示一条成功路径；prototype 是可运行早期系统；feasibility 证明在限定条件下可实施；effectiveness 需要对照、代表性样本和统计证据证明效果。
2. **方法与系统如何互相支持？** 系统实现使方法可执行和测量；方法定义可检验机制。系统功能多不代表方法有效，算法分数高也不代表工程可用。
3. **最容易被质疑的主张？** 通常是“准确识别根因”和“跨框架泛化”，因为需要可信真值、因果定义、强基线和外部验证。
4. **最小判别实验？** 选择一类静默工具故障，在同一批实例上配对比较 Full 与 App-only；冻结候选集和预算，报告 Top-1 差、CI、未知率与成本。若没有差异，说明新增系统证据至少在该范围内未体现价值。

## 七、评分标准（100 分）

RQ 可检验性 20；贡献与证据对应 20；Claim–Evidence 20；实验矩阵/关卡 25；威胁与诚实边界 15。任何把未运行实验写成“结果显示”的答案直接不通过。
