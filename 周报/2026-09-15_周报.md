## 一、为什么做？（Why）

**问题起点**：LLM 智能体正在走向生产（Devin、Claude Code、多智能体协作系统），但它们有两个致命特性让传统调试手段失效：

- **非确定性**：同样输入产出不同轨迹，无法复现
- **推理黑箱**：内部决策不可见，出错时难以定位是"哪一步、哪个 Agent"的问题

**具体痛点**：如果 Agent 系统在生产中失败了，现有的工具链**答不出三个最基本的问题**——
1. **发生了什么？**（系统里实际执行了什么动作）
2. **为什么发生？**（内部推理在哪个环节偏离）
3. **该怪谁？**（哪个 Agent / 哪个组件该负责）

**因此需要**：系统性地搞清楚这个领域**已经解决了什么、还缺什么、哪里可以切入**。这也是本次调研的直接目的——为后续选题建立地图。

## 二、怎么做的？（How）

### 2.1 阅读方法：统一七维结构化精读

对每篇论文统一按七个维度拆解，确保横向可比：

> **论文总结 / 应用场景 / 实验设置 / 实验平台 / 数据集来源 / 结果验证 / 启示与局限性**

每篇产出 2–6 万字的精读笔记，并统一附加三块：
- **附一：一页速览**（表格化核心事实）
- **附二：与已读论文的逐篇对照**
- **附三：已读论文横向定位表**

### 2.2 选文策略：按"链路"而非"主题"选取

不是随机收集 Agent 相关论文，而是**按一条完整链路的各个环节选文**：

```
观测层 → 诊断层 → 干预层 → 底座
```

| 环节 | 选取的论文 | 选它的理由 |
|---|---|---|
| **元层规范** | AgentOps (CSIRO) | 提供领域术语与追踪模板 |
| **系统观测** | AgentSight | 代表性的零侵入系统级方案 |
| **认知观测** | Watson | 唯一聚焦"推理重建"的工作 |
| **故障归因** | Who&When | 该问题的开创性定义工作 |
| **性能预测** | AgentMonitor | 非侵入预测的代表 |
| **拓扑优化** | AgentDropout | MAS 结构优化代表 |
| **表达优化** | Beyond Natural Language | 挑战"NL 最优"假设 |
| **系统底座** | DistServe | 全栈最底层（GPU 调度） |

### 2.3 关键做法：每篇都做"批判性核验"而非机械摘要

- 逐条核对论文自述的局限（8 篇中 7 篇都有 Limitation 章节）
- 交叉验证数据一致性（如发现 AgentOps 原文表格计数不一致：正文称 17 个工具，Table 3 仅 16 行）
- 记录**统计规范差异**（是否做显著性检验、是否报样本量、是否展示方差）
- 识别**并行工作**（如 DistServe 的同类思路被 Splitwise / Tetris-Infer / DéjàVu 独立提出）

### 3.2 核心认知结果

**① 领域已形成清晰的分层结构（这是本次调研最主要的发现）**

8 篇论文不是并列关系，而是**一条完整链路的各个环节**：

| 层次 | 论文 | 回答什么 |
|---|---|---|
| 元层（规范） | AgentOps | 该记录什么字段 |
| 表达层 | Beyond NL | 用什么格式说话最省 |
| 认知层 | Watson | Agent 在想什么 |
| 归因层 | Who&When | 哪个 Agent、哪一步错 |
| 预测层 | AgentMonitor | 这套配置能跑多少分 |
| 拓扑层 | AgentDropout | 该保留哪些节点和边 |
| 系统边界层 | AgentSight | 系统里实际执行了什么 |
| 推理系统层 | DistServe | 算力怎么调度最快 |

> **并且发现一个贯穿 8 篇的共性方法论**：**都是用廉价代理量去预测/定位昂贵的真实量**（Who&When 用反事实干预找责任方、AgentMonitor 用指标回归预测性能、DistServe 用排队论预测 SLO）。这可能就是 AgentOps 研究的通用范式。

**② 三个关键判断**

- **可观测性已分层，但层间未打通**：AgentSight 看得见动作、Watson 看得见想法、AgentOps 定义了字段，但"动作 ↔ 意图"的自动关联仍是各做各的。
- **故障归因是最不成熟的一环**：Who&When 的实际水平是 Agent 级 53.5%、Step 级 14.2%，**远不可用于生产**；而它下游的"改了之后是否真变好"完全空白。
- **部分方向已红海化**：DistServe 的 prefill/decode 分离思路同期被至少 4 个团队独立提出——提示选题时要避开饱和区。

**③ 8 个可做缺口（按可行性排序）**

| # | 缺口 | 判断依据 | 可行性 |
|---|---|---|---|
| **1** | **把"跨度之间的边"形式化进 AgentOps 分类法** | AgentOps **自陈遗漏**步骤间的链接与交互；而 AgentDropout 优化边、AgentSight 捕捉跨边界交互、Who&When 度量步骤间影响——**三篇各自触及却无人统一** | ⭐⭐⭐⭐⭐ |
| 2 | 用 AgentOps 的 Span 类型作为 Who&When 归因的结构化输出空间 | 一个提供"地址空间"、一个提供"归因方法"，无人对接 | ⭐⭐⭐⭐ |
| 3 | Guardrails 的可追踪化与自动化安全案例生成 | AgentOps 数据显示护栏覆盖率仅 **35%**（对比追踪 100%） | ⭐⭐⭐⭐ |
| 4 | "格式压缩 × 服务分离"联合优化 | Beyond NL（token −72.7%）与 DistServe（7.4×）正交可叠加，无人做过 | ⭐⭐⭐⭐ |
| 5 | AgentOps 分类法的演绎验证 | 作者明确列为未来工作 | ⭐⭐⭐ |
| 6 | 跨架构泛化的性能预测 | AgentMonitor 跨架构 Spearman 仅 0.58（域内 0.89） | ⭐⭐⭐ |
| 7 | 归因后的效果闭环验证 | Who&When 明确未验证"改后是否变好" | ⭐⭐⭐ |
| 8 | Implicit Feedback 的自动化采集 | AgentOps 指出隐式反馈更难但更可靠 | ⭐⭐⭐ |

### 3.3 已形成的候选选题

> **"基于 Span 图的 Agent 故障归因：把拓扑结构纳入可观测性分类法"**
>
> **核心创新**：现有归因只看**节点**（谁错），本选题看**边**（信息在哪里断）；并把归因结果直接用于指导拓扑优化，形成**"观测 → 归因 → 干预 → 复验"的完整闭环**——这恰是目前 8 篇论文各占一段、无人打通的全链。
