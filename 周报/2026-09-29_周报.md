# 周报（2026-09-23 ~ 2026-09-29）

**一句话总结：**本周的主要工作是检查 AgentSight/eBPF 采集结果中的数据缺失问题，并将已经收集到的 AgentSight 原始观测、Claude 应用日志和任务工件规范化为可追溯的 Adapter 输入，为后续开发通用、自动化的 Trace Adapter 做准备；同行论文调研用于确定规范化字段、证据边界和后续评价目标。

**本周主工作：**确认哪些运行真正保存了 eBPF/AgentSight 原始观测，区分“有原始观测”“只有派生 trace”“只有任务真值”的实验；在一次真实 API canary 中验证 AgentSight SQLite 数据可以落盘，并将 7 类 AgentSight 表和应用结果日志转换成带来源引用的证据记录。当前完成的是 Adapter 输入层和数据质量检查，不是通用 Trace Adapter 本身。

## 1. 本周主要工作：检查观测缺失并规范化原始数据

### 1.1 检查 eBPF/AgentSight 数据缺失

对现有 `failure_pilot`、`p0_pairing` 和 `evaluation_gate` 结果进行了逐目录扫描，建立了 34 个实验目录的运行索引。检查结果显示：部分历史运行只有合成 `trace.jsonl` 和 `ground_truth.json`，没有原始 AgentSight 数据；部分运行只有 AgentSight/HTTP 观测，没有完整 Agent 应用事件流。因此不能把所有已有 trace 都当成同等可信的原始证据。

针对采集失败问题，定位到默认 Ubuntu 20.04 的 glibc 2.31 无法运行 AgentSight 1.0.31。切换到 Ubuntu 24.04（glibc 2.39）后，真实 AgentSight 采集成功，并修改采集脚本，使 AgentSight 进程提前退出或数据库为空时直接报错，避免出现采集失败但脚本返回成功的情况。

### 1.2 将原始观测规范化为 Adapter 输入

新增 `my_paper_coding/trace_adapter/`，完成以下输入准备工作：

- 为每个实验目录生成 manifest，记录来源路径、数据类别、文件大小、SHA256、模型、session 和成本元数据；
- 读取 AgentSight SQLite 中的 `llm_calls`、`tool_calls`、`audit_events`、`process_nodes`、`resource_samples`、`token_usage` 和 `network_targets`；
- 读取 Claude 应用结果日志，并明确标记其仍是最终结果摘要，不是完整 step/tool JSONL；
- 为规范化记录保留原始文件、表名或行号引用；
- 将已有 `trace.jsonl` 标记为 `derived_untrusted`，不把它作为原始事实或 ground truth；
- 使用 `smoke_check.py` 检查原始观测、应用日志、任务工件和独立判据是否同时存在。

真实 canary 的规范化结果包含 222 条证据记录：220 条 AgentSight 原始 SQLite 记录和 2 条应用层结果记录。这为下一步实现跨层候选匹配器提供了实际输入。

## 2. 同行论文调研及其作用

本周重点阅读和整理了 `Reference paper/` 中与当前方向最接近的工作，并为每篇论文建立了精读笔记。论文结论按“同行已经做到什么、还没有做到什么、我的工作应避开什么重复”进行归纳。

| 方向 | 代表工作 | 对本课题的启发 | 仍存在的边界 |
|---|---|---|---|
| Agent 运行观测 | AgentSight、AgentTrace | 需要同时保存 Agent、工具、模型、进程、网络和资源证据 | 单纯增加系统观测不等于完成任务层责任归因 |
| 故障归因基准 | TraceElephant、MAST | 完整执行轨迹、故障分类、可重放环境和独立标注是归因实验的基础 | 现有工作没有解决 eBPF 系统事件与应用语义事件的通用对齐 |
| 反向诊断与验证 | ErrorProbe、ToolsFail | 可以从失败症状反向检索候选，再通过工具执行或重放验证 | 候选搜索和验证本身不是本课题的唯一创新，且会带来额外调用成本 |
| 跨层 RCA | TELLER、GALA | trace、日志、依赖图和模态消融说明跨层证据需要结构化对齐 | 研究对象主要是 LLM 推理服务或微服务，不是多 Agent 任务责任和消息传播边 |
| 日志与调试效用 | ReLog | 日志质量应按下游定位和修复效果评价，而不是按文本完整性评价 | 其对象不是 Agent 角色、工具边和系统边界观测 |
| Agent 评价协议 | AgentBench、AgentBoard、τ-bench、MultiAgentBench | 任务成功、过程进展、可靠性、里程碑和协作质量需要进入评价体系 | 这些工作不能直接提供系统观测到责任边的证据链 |

由此得到的调研结论是：同行已经分别覆盖了观测、失败分类、候选诊断、图结构 RCA 和任务评价，但“系统边界观测 + Agent 应用日志 + 独立任务 oracle + 责任边反事实验证”仍缺少统一的、可审计的 Adapter 和评价协议。论文调研的作用是帮助定义本周的数据结构和研究边界，而不是把这些工作直接当作本文创新。这个研究缺口仍需通过后续跨任务、跨框架实验验证。

## 3. 本周确定的研究方向

当前主线确定为：

```text
AgentSight/eBPF 系统观测
        + Agent 应用日志
        + 独立任务判据
        ↓
Trace Adapter
        ↓
带 provenance 的规范化执行轨迹
        ↓
Agent / Step / Edge 责任图
        ↓
候选搜索、反事实验证和可拒答归因
```

研究贡献的候选表述不再是“使用 eBPF 监控 Agent”，而是：

1. 设计一个把系统层和应用层证据对齐为统一执行轨迹的 Trace Adapter；
2. 在证据引用、冲突和缺失字段下生成可审计的 Agent/Step/Edge 候选责任图；
3. 用独立任务判据和反事实干预区分“最早错误”和“使任务不可恢复的决定性错误”；
4. 对无法可靠对齐的案例输出 `unknown/uncertain/abstain`，而不是强行给出责任结论。

### 4.2 Trace Adapter 输入链路

新增 `my_paper_coding/trace_adapter/`：

- `build_run_index.py`：为 34 个实验目录生成 manifest，记录来源路径、文件类别、大小、SHA256、模型、session 和成本元数据；
- `normalize_runs.py`：读取 Claude 结果日志、AgentSight SQLite 表和已有派生 trace，生成带来源定位的 `evidence-events.jsonl`；
- `smoke_check.py`：检查真实运行是否同时存在原始观测、应用日志、任务工件和独立判据；
- `run-metadata.template.json`：定义下一次运行必须保存的版本、命令、时钟、session、PID 和 artifact 元数据。

成功 canary 的规范化输出为 222 条证据记录，其中 220 条来自 AgentSight 原始 SQLite 观测，2 条来自应用层最终结果日志。已有 `trace.jsonl` 被标记为 `derived_untrusted`，不会被当作原始事实或 ground truth。

## 5. 当前证据判断

- **VERIFIED：** 已有数据足以开始开发 Trace Adapter 的输入层、SQLite 解析器、应用日志解析器、来源追踪和系统侧候选匹配器。
- **VERIFIED：** `tool_call_id`、`related_pid`、进程节点和时间戳可以形成系统侧候选证据链。
- **UNVERIFIED：** Agent 应用 `session_id` 与 AgentSight `conversation_id` 的自动映射。
- **UNVERIFIED：** 从原始证据自动恢复 `agent_id`、`step_id`、父子边和决定性责任边。
- **UNVERIFIED：** 跨任务、跨故障、跨 Agent 框架的泛化效果。
- **不能推出：** 单个真实 canary 不能证明归因准确率、统计显著性或论文级方法优越性。

当前真实应用日志仍主要是最终结果 JSON，缺少完整 Agent step/tool JSONL。因此现在可以开发“候选对齐器”，但不能把 PID 和时间启发式结果直接写成确定责任。

## 6. 本周遇到的问题和成本控制

- WSL 发行版之间的 glibc 版本差异会导致 AgentSight 二进制启动失败；已固定可运行的 Ubuntu 24.04 作为后续采集环境。
- Agent 应用 session ID 和 AgentSight conversation ID 没有直接共享的关联字段；需要在 Adapter 中保留候选集合和不确定状态。
- 真实应用日志不是完整事件流，历史运行无法事后恢复丢失的工具调用和时间戳。
- 本周新增真实 API 成本 `0.3766092 USD`，累计账本约 `1.3206682 USD`。后续停止继续扩大真实 API 调用，优先使用本周 canary 和已有 P0 数据开发 Adapter。
