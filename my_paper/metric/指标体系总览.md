    # 面向多智能体 AgentOps 的评价指标体系

> 用途：为“面向多智能体系统的因果边级故障归因与自治拓扑修复闭环（CERA）”整理可直接进入实验设计和论文方法章节的指标候选。
>
> 重要说明：本文所有带数字的“例子”都是为了说明计算方法而构造的教学算例，不是已经取得的实验结果；任何阈值在成为论文验收标准前，都需要由任务需求、基线实验或可引用文献确定。

## 1. 指标选取原则与证据状态

当前研究对象不是单次 LLM 调用，而是由多个 Agent、工具调用、消息传播、Span、系统事件和修复动作组成的闭环。因此，评价需要同时回答五个问题：

1. **任务是否完成**：最终结果正确吗，满足约束吗？
2. **过程是否可观测**：关键 Span、消息、工具与系统证据是否被完整、正确地记录？
3. **故障是否找得准**：能否定位错误 Agent、步骤，以及真正传播失败的 Span 间因果边？
4. **干预是否有效且安全**：修复是否抑制错误，同时保留有益信息，且不会引入新回归？
5. **系统是否可承受**：观测与修复带来的时延、Token、费用和资源开销是否合理？

本文使用以下证据状态：

| 状态 | 含义 |
|---|---|
| `VERIFIED` | 已在本仓库研究计划或用户提供的指标笔记中明确出现；表示“来源可追溯”，不等于其行业阈值已经被论文证实。 |
| `INFERRED` | 根据当前 CERA 研究问题，从已有指标组合或实验逻辑中推导出的建议指标。 |
| `UNVERIFIED` | 笔记中存在具体阈值或经验说法，但尚未在本仓库中完成原始文献核验。 |
| `AUTHOR_INPUT_NEEDED` | 必须由作者依据具体任务、SLO、故障定义或标注协议确定。 |

### 1.1 论文优先级

| 优先级 | 使用方式 |
|---|---|
| **P0 核心** | 回答论文主张，摘要、主结果表和消融实验都应报告。 |
| **P1 关键支撑** | 解释核心结果是否可信、安全、可复现。 |
| **P2 条件指标** | 仅在具备 GPU、能耗计量、长稳压测或生产 SLO 环境时报告。 |

## 2. 任务结果与大模型调用指标

### 2.1 任务成功率（Task Success Rate）— P0 核心，`VERIFIED`

- **定义**：满足任务完成判据的样本数占全部样本数的比例。
- **公式**：`TSR = 成功完成的任务数 / 总任务数`。
- **具体例子**：一个三 Agent 代码修复系统处理 100 个缺陷，其中 76 个通过测试且没有违反文件修改约束，则任务成功率为 `76/100 = 76%`。
- **论文作用**：衡量 CERA 修复前后最终业务效果；必须同时报告“无干预、随机干预、节点修复、边级修复”对照。
- **注意**：何为“成功”依任务而变，测试通过、答案正确、格式合规等判据需要预注册。`AUTHOR_INPUT_NEEDED`

### 2.2 请求成功率（Request Success Rate）— P1 关键支撑，`VERIFIED`

- **定义**：未发生网络错误、模型服务错误、限流、超时或未处理异常，并正常返回的请求占比。
- **公式**：`RSR = 正常返回请求数 / 总请求数`。
- **具体例子**：规划 Agent 向模型发出 1,000 次请求，20 次因 429、10 次因超时失败，则请求成功率为 `970/1000 = 97%`。
- **论文作用**：区分“基础设施请求失败”和“请求虽成功但 Agent 任务做错”。

### 2.3 任务质量（Task Quality）— P0 核心，`VERIFIED`

- **定义**：对最终结果的正确性、相关性、有用性和约束满足程度进行任务特定评分。
- **计算**：优先使用可执行判据；必要时采用人工盲评或经独立验证的评分量表。分类任务可报告 Accuracy、Precision、Recall、F1；生成任务不应只依赖单一文本相似度。
- **具体例子**：研究 Agent 需要返回 10 条带来源的事实。若 8 条事实正确、7 条能被引用直接支持、10 条均满足 JSON 格式，可分别报告事实正确率 80%、证据支持率 70%、格式满足率 100%，而不是把三者混成一个不透明总分。
- **论文作用**：确保“减少错误传播”没有以牺牲答案质量为代价。

### 2.4 约束满足率（Constraint Satisfaction Rate）— P1 关键支撑，`VERIFIED`

- **定义**：输出满足预先声明的格式、长度、工具权限或流程约束的比例。
- **公式**：`CSR = 满足全部目标约束的样本数 / 总样本数`；也可逐类约束分别报告。
- **具体例子**：要求执行 Agent 只修改 `src/` 且输出合法补丁；50 次运行中 47 次路径合规、45 次补丁可解析，则路径约束满足率 94%，可解析率 90%。
- **论文作用**：识别拓扑修复后是否出现越权、协议破坏或不可解析通信。

### 2.5 Groundedness / 证据支持率 — P1 关键支撑，`VERIFIED`

- **定义**：输出中的可核查主张能够被提供证据直接支持的比例。
- **公式**：`Groundedness = 有充分证据支持的主张数 / 可核查主张总数`。
- **具体例子**：检索 Agent 给总结 Agent 传递 12 条事实，人工核验发现 9 条可由检索文档直接推出，则证据支持率为 75%。
- **论文作用**：可作为数据边传播质量的一部分，用于区分“边存在”和“边上传播的信息可靠”。

### 2.6 TTFT（Time to First Token）— P2 条件指标，`VERIFIED`

- **定义**：从请求发出到收到首个输出 Token 的时间。
- **具体例子**：协调 Agent 在 `10:00:00.000` 调用规划模型，在 `10:00:00.420` 收到首 Token，则 TTFT 为 420 ms。
- **论文作用**：在实时交互或 GPU 推理服务实验中评价首响应体验；对非流式 API 应标记“不适用”。
- **注意**：原笔记中的通用阈值尚未核验，不能直接写成本文行业标准。`UNVERIFIED`

### 2.7 TPOT（Time per Output Token）— P2 条件指标，`VERIFIED`

- **定义**：首 Token 之后生成每个后续 Token 的平均时间。
- **公式**：`TPOT = (总生成时间 - TTFT) / (输出 Token 数 - 1)`。
- **具体例子**：某 Agent 调用总生成时间为 5,370 ms，TTFT 为 420 ms，共输出 100 个 Token，则 `TPOT = (5370-420)/(100-1) = 50 ms/token`。
- **论文作用**：解释长回复慢在预填充阶段还是解码阶段。

### 2.8 端到端任务时延（End-to-End Task Latency）— P0 核心，`VERIFIED`

- **定义**：从用户提交任务到系统给出最终可验收结果的总时间，包括 Agent 编排、模型调用、工具执行、重试与验证。
- **具体例子**：规划耗时 2 s、两个并行执行 Agent 中最慢者耗时 8 s、验证和汇总耗时 3 s，则关键路径端到端时延约为 13 s，而不是各 Agent 耗时简单相加。
- **论文作用**：衡量 CERA 修复机制带来的真实用户等待成本，并结合 Trace 分解瓶颈。

### 2.9 输出一致性率 — P1 关键支撑，`VERIFIED`

- **定义**：相同配置下重复运行时，结果在预定义语义或任务判据上保持一致的比例。
- **具体例子**：同一多 Agent 数学任务独立运行 10 次，其中 8 次答案正确且推导出的关键结论一致，则按预先定义的语义判据，一致性率为 80%。
- **论文作用**：衡量非确定性是否掩盖干预收益；需同时报告随机种子、温度和模型版本。

### 2.10 扰动鲁棒性率 — P1 关键支撑，`VERIFIED`

- **定义**：在输入错别字、消息顺序扰动、非关键 Agent 延迟等轻微扰动下仍成功完成任务的比例。
- **具体例子**：对 100 个基准任务分别加入一处无语义影响的错别字，原系统成功 68 个，CERA 系统成功 81 个，则两组扰动鲁棒性率分别为 68% 和 81%。
- **论文作用**：检验修复策略是否只记住固定 Trace，而非提升真正的系统韧性。

## 3. 负载、可靠性与系统协同指标

### 3.1 截止期错失率（Deadline Miss Ratio, DMR）— P1 关键支撑，`VERIFIED`

- **定义**：未在任务截止时间前产生可验收结果的任务比例；即使最终成功，超时仍计为错失。
- **公式**：`DMR = 超过 Deadline 的任务数 / 总任务数`。
- **具体例子**：客服 Agent 的截止时间为 10 s，100 个任务都最终成功，但有 7 个耗时超过 10 s，则任务成功率为 100%，DMR 为 7%。
- **论文作用**：防止边级验证和 replay 虽提高正确率，却使实时系统失约。

### 3.2 P99 / P99.9 尾部时延与抖动 — P1 关键支撑，`VERIFIED`

- **定义**：P99/P99.9 分别表示 99%/99.9% 样本不超过的时延；抖动描述时延波动，可报告标准差、IQR 或相邻窗口百分位变化，必须明确口径。
- **具体例子**：10,000 次工具调用的 P50 为 120 ms、P99 为 1.8 s。即使平均值只有 180 ms，仍说明约 1% 调用存在明显长尾。
- **论文作用**：多 Agent 并行时，整体往往被最慢分支拖住，因此必须与均值同时报告。

### 3.3 观测最大响应时间（Observed Maximum）— P2 条件指标，`VERIFIED`

- **定义**：固定观测窗口内记录到的最慢单次响应时间。
- **具体例子**：1 小时实验中 9,999 次调用小于 2 s，但一次工具冷启动耗时 27 s，则观测最大响应时间为 27 s。
- **论文作用**：暴露冷启动、死锁前兆或第三方超时等极端异常。
- **注意**：它只是有限样本中的最大值，不等于理论最坏情况。

### 3.4 外部依赖可靠性 — P1 关键支撑，`VERIFIED`

- **定义**：按具体依赖分别统计工具/API/数据库的成功率、超时率、错误码分布和延迟分位数。
- **具体例子**：搜索 Agent 调用检索 API 500 次，其中 15 次 5xx、10 次超时，P99 为 4.2 s，则依赖成功率为 95%，超时率为 2%。
- **论文作用**：判断最终失败来自 Agent 推理、边传播，还是外部工具本身。

### 3.5 SLO 达标率（SLO Attainment）— P1 关键支撑，`INFERRED`

- **定义**：同时满足预设质量、时延和可靠性目标的任务比例。
- **公式**：`SLO Attainment = 同时满足全部 SLO 的任务数 / 总任务数`。
- **具体例子**：规定“答案正确且端到端时延 ≤ 15 s”。100 个任务中 85 个正确，但只有 78 个同时在 15 s 内完成，则 SLO 达标率为 78%。
- **论文作用**：避免只优化成功率或只优化时延；具体 SLO 需由实验场景确定。`AUTHOR_INPUT_NEEDED`

### 3.6 有效吞吐（Goodput）— P1 关键支撑，`VERIFIED`

- **定义**：单位时间内成功交付且满足 SLO 的有效任务数或有效 Token 数。
- **公式**：任务口径可写为 `Goodput = SLO 达标任务数 / 时间`。
- **具体例子**：系统一分钟完成 120 个任务，但只有 90 个同时满足正确性与时延 SLO，则 Goodput 为 90 tasks/min，而标称吞吐为 120 tasks/min。
- **论文作用**：比较不同观测或修复方案的真实产能，不把失败、重试和无效输出算作贡献。

### 3.7 单成功任务成本（Cost per Successful Task）— P0 核心，`INFERRED`

- **定义**：总模型、工具与基础设施费用除以成功任务数，比单 Token 成本更贴近 Agent 任务价值。
- **公式**：`C_success = 总运行成本 / 成功任务数`。
- **具体例子**：100 个任务总费用 20 元，基线成功 50 个，则每成功任务 0.40 元；CERA 总费用增至 22 元但成功 80 个，则降为 0.275 元。
- **论文作用**：解释额外的 Trace、replay 和验证成本是否值得。

### 3.8 E/token 与 Cost/token — P2 条件指标，`VERIFIED`

- **定义**：每生成一个 Token 的能耗或经济费用。
- **具体例子**：一次多 Agent 任务消耗 20,000 Token、计费 0.60 元，则 Cost/token 为 `0.60/20000 = 0.00003 元/token`；若可测得能耗 40 Wh，则为 `0.002 Wh/token`。
- **论文作用**：在模型与硬件配置稳定时分析通信压缩、拓扑剪枝或额外验证的资源代价。
- **注意**：跨模型比较时，Token 粒度和质量不同，不能脱离任务成功率单独解读。

### 3.9 资源争抢边界（Resource Contention Boundary）— P2 条件指标，`VERIFIED`

- **定义**：并发或资源利用率增加时，系统首次持续违反既定 SLO 的工作点。
- **具体例子**：并发从 8 增至 32 时 SLO 达标率始终大于 95%，并发达到 40 后连续三个窗口降至 88%，则按预注册规则可把 32–40 之间视作争抢边界区间。
- **论文作用**：确定 Agent 数量、并行工具调用和 replay 任务的安全容量。
- **注意**：原笔记中的显存百分比经验值尚未核验，不作为固定边界。`UNVERIFIED`

### 3.10 观测开销率（Instrumentation Overhead）— P0 核心，`VERIFIED`

- **定义**：开启 Trace/系统探针后，相对关闭观测时增加的时延、CPU、内存、网络、存储或 Token 开销。
- **公式**：时延开销可写为 `OH_latency = (L_on - L_off) / L_off`。
- **具体例子**：关闭观测时平均任务时延为 10.0 s，开启 AgentSight 式观测后为 10.4 s，则时延开销率为 4%；CPU 和内存开销应另列，不能合成一个数字。
- **论文作用**：验证“可观测”没有显著改变被观测对象。

### 3.11 恢复时间（Recovery Time / MTTR）— P1 关键支撑，`VERIFIED`

- **定义**：从故障被注入或发生，到系统恢复可接受服务状态的时间；多次事件可报告中位数、P95 和均值。
- **具体例子**：执行 Agent 在第 20 s 崩溃，系统在第 23 s 检测，在第 31 s 完成重路由并恢复任务，则检测时延为 3 s，恢复时间为 11 s。
- **论文作用**：评价 CERA 的“检测—归因—验证—重配—恢复”闭环速度。

### 3.12 恢复成功率 — P1 关键支撑，`VERIFIED`

- **定义**：故障后无需人工介入即可恢复并满足验收标准的事件比例。
- **具体例子**：注入 50 次工具不可用故障，系统自动重路由 44 次，其中 40 次最终任务成功，则严格恢复成功率为 `40/50 = 80%`。
- **论文作用**：不能把“执行了恢复动作”误当成“恢复成功”。

### 3.13 长时间性能衰减率 — P2 条件指标，`VERIFIED`

- **定义**：长时间运行末期相对初始稳态窗口的性能退化比例，可分别对吞吐、时延、错误率和资源占用计算。
- **具体例子**：首小时 Goodput 为 100 tasks/min，第 24 小时为 92 tasks/min，则 Goodput 衰减率为 8%；若内存同时单调增长，应单独报告泄漏斜率。
- **论文作用**：检验长 Trace、缓存、重试队列和修复记忆是否积累导致退化。
- **注意**：72 小时等时长应由资源条件和论文目标决定，不是默认行业门槛。`AUTHOR_INPUT_NEEDED`

### 3.14 温度漂移（Thermal Drift）— P2 条件指标，`VERIFIED`

- **定义**：持续负载下，温度变化与频率、时延或吞吐变化之间的关联；不能仅凭相关性声称温度是因果原因。
- **具体例子**：GPU 温度从 65°C 升到 84°C 的同一时段，TPOT 从 35 增至 48 ms/token，并记录到降频事件，可报告两者的时间关联，再通过控温或重复实验验证因果性。
- **论文作用**：仅适用于自有 GPU 长稳实验；API 模型场景通常无法测量。

## 4. 可观测性与 Trace 数据质量指标

### 4.1 事件检测 Precision / Recall / F1 — P0 核心，`VERIFIED`

- **定义**：比较观测器捕获的系统/Agent 事件与独立真值日志，衡量误报和漏报。
- **公式**：`Precision = TP/(TP+FP)`，`Recall = TP/(TP+FN)`，`F1 = 2PR/(P+R)`。
- **具体例子**：真值中有 100 次工具调用，观测器报告 95 次，其中 90 次匹配真值，则 Precision 为 `90/95=94.7%`，Recall 为 `90/100=90%`，F1 约为 92.3%。
- **论文作用**：证明底层观测事件本身可信，避免后续归因建立在错误 Trace 上。

### 4.2 请求—响应配对 Precision / Recall / F1 — P0 准入门槛，`VERIFIED`

- **定义**：观测器是否把每个模型/工具请求与其真实响应正确配对。
- **具体例子**：真值有 200 对请求—响应；系统输出 195 对，其中 190 对正确，则配对 Precision 为 97.4%，Recall 为 95%，F1 约为 96.2%。
- **论文作用**：是语义 Trace、数据边和因果传播边构建的共同前提；应优先使用连接/消息 ID、流方向、PID/TID 与协议证据，而不是只依赖时间邻近。

### 4.3 Trace 字段完整率 — P0 准入门槛，`VERIFIED`

- **定义**：必填字段中实际被可靠记录的比例，可在字段级与调用级分别统计。
- **公式**：字段级 `Completeness = 非缺失必填字段数 / 应有必填字段数`。
- **具体例子**：100 个调用各要求 request、response、model、start/end time、source ID 共 6 个字段，应有 600 项，实际可靠记录 570 项，则字段完整率为 95%；若只有 82 个调用六项全齐，则调用完整率为 82%。
- **论文作用**：决定某条 Trace 能否进入 replay、认知重建或因果验证实验。

### 4.4 Span 覆盖率 — P0 核心，`INFERRED`

- **定义**：真值工作流中应存在的 Agent、Task、LLM、Tool、Evaluation 等 Span 被观测到的比例，并按 Span 类型分层报告。
- **具体例子**：一次工作流真值包含 5 个 Agent Span、8 个 LLM Span、4 个 Tool Span，共 17 个；观测器漏掉 2 个 Tool Span，则总体覆盖率为 88.2%，Tool Span 覆盖率为 50%。
- **论文作用**：总体覆盖率可能掩盖关键类型缺失，因此必须按类型分层。

### 4.5 边重建 Precision / Recall / F1 — P0 核心，`INFERRED`

- **定义**：对 sequential、communication、data、responsibility 等可观测边，衡量重建图与人工/插桩真值图的一致程度。
- **具体例子**：真值图含 40 条通信边，系统重建 38 条，其中 35 条正确，则 Edge Precision 为 92.1%，Recall 为 87.5%，F1 约为 89.7%。
- **论文作用**：区分“Trace 中有节点”和“节点间关系被正确恢复”，是边级归因的直接数据基础。

### 4.6 跨层关联正确率 — P0 核心，`VERIFIED`

- **定义**：Agent/LLM 语义 Span 与对应进程、网络、文件、工具或 GPU 系统事件正确关联的比例。
- **具体例子**：抽检 100 个 LLM Span，92 个被关联到正确进程与 TLS 连接，5 个关联错误，3 个缺失；若只把已关联项作为预测，则 Precision 为 `92/97=94.8%`，覆盖率为 97%。
- **论文作用**：验证系统证据确实投影到正确的因果边，而非仅在时间上相邻。

### 4.7 原始证据保留率 — P1 关键支撑，`VERIFIED`

- **定义**：经压缩、聚合或语义化之后，仍可回到原始事件进行审计的关键证据比例。
- **具体例子**：系统从 1,000 条原始事件生成 120 个 Span；其中 114 个 Span 保留了可解析的原始事件 ID，则原始证据保留率为 95%。
- **论文作用**：支撑“证据 → 边 → 归因结论”的可追溯性。

### 4.8 可 Replay 率 — P0 核心，`INFERRED`

- **定义**：具备足够输入、配置、工具状态或替身，使关键干预能够被重放验证的 Trace 比例。
- **具体例子**：220 条失败 Trace 中，160 条具有完整输入、模型配置和可模拟工具结果，可执行反事实 replay，则可 Replay 率为 72.7%。
- **论文作用**：明确哪些样本能支持因果结论，哪些只能用于相关性分析。

### 4.9 Trace 压缩比 — P1 关键支撑，`VERIFIED`

- **定义**：原始事件量与保留下来的结构化事件/字节量之比，必须与证据保留率联合解读。
- **公式**：`Compression Ratio = 原始事件量 / 输出事件量`。
- **具体例子**：10,000 条内核/网络事件被聚合为 500 条结构化 Span 事件，压缩比为 20:1；若原始证据保留率只有 40%，则该压缩可能过度。
- **论文作用**：衡量观测存储经济性，但不能把“压得多”本身当作好结果。

### 4.10 观测非干扰性 — P0 核心，`INFERRED`

- **定义**：开启观测后，任务输出分布、成功率和关键路径性能没有出现不可接受的改变。
- **具体例子**：同一组 200 个任务在观测关闭/开启下成功率分别为 74%/73%，同时报告差值置信区间；若观测器还修改了 Prompt，则不能声称是旁路无干扰观测。
- **论文作用**：比单纯报告平均开销更严格；统计上“不显著”也不自动等于工程上“等价”，应预先给出可接受界限。`AUTHOR_INPUT_NEEDED`

## 5. 故障定位与边级归因指标

### 5.1 Agent Attribution Accuracy — P1 基线，`VERIFIED`

- **定义**：预测的根因 Agent 与标注真值 Agent 一致的样本比例。
- **具体例子**：100 条失败 Trace 中，系统正确指出根因 Agent 62 条，则 Agent Accuracy 为 62%。
- **论文作用**：与 Who&When 式 Agent 级方法比较，但不能代替更细粒度的 Step/Edge 指标。

### 5.2 Step Attribution Accuracy — P1 基线，`VERIFIED`

- **定义**：预测的决定性错误步骤与标注真值步骤完全一致的样本比例。
- **具体例子**：80 条具有唯一决定性步骤的失败 Trace 中，模型定位正确 24 条，则 Step Accuracy 为 30%。
- **论文作用**：评价从完整 Trace 到步骤定位的增益；多根因样本不宜强行压成单标签 Accuracy。

### 5.3 Edge Precision / Recall / F1 — P0 核心，`VERIFIED`

- **定义**：预测的失败传播边集合与人工标注或反事实验证真值边集合的重合程度。
- **具体例子**：一条 Trace 有 4 条真值失败边，系统预测 5 条，其中 3 条正确，则 Precision 为 60%，Recall 为 75%，F1 约为 66.7%。
- **论文作用**：是“边本身作为诊断对象”这一主张的首要指标；应分别报告 communication、data、responsibility、causal-propagation 各类边。

### 5.4 Edge Hit@k — P0 核心，`VERIFIED`

- **定义**：至少一条真值失败边是否出现在排名前 k 的候选边中，再对样本取平均。
- **具体例子**：10 条失败 Trace 中，有 8 条的真值边出现在模型 Top-3 候选内，则 Edge Hit@3 为 80%。
- **论文作用**：适合工程排障场景，因为开发者通常只检查少量高排名边。

### 5.5 Edge MRR（Mean Reciprocal Rank）— P0 核心，`VERIFIED`

- **定义**：每条 Trace 中第一条真值边排名倒数的平均值。
- **具体例子**：三条 Trace 的第一条真值边分别排第 1、2、4 名，则 `MRR=(1+1/2+1/4)/3=0.583`。
- **论文作用**：比 Hit@k 更敏感地反映真值边是否被排在最前。

### 5.6 多错误 Macro-F1 — P0 核心，`VERIFIED`

- **定义**：对每种失败类型分别计算 F1 后等权平均，避免高频错误类型支配总结果。
- **具体例子**：规划错误、工具错误、通信错误三类 F1 分别为 0.8、0.5、0.2，则 Macro-F1 为 `(0.8+0.5+0.2)/3=0.5`，即使规划错误样本最多也不会获得额外权重。
- **论文作用**：用于 MAST 式多失败类型分层和 EDGE 式多错误传播评估。

### 5.7 反事实下游消除效应（Counterfactual Downstream Elimination）— P0 核心，`VERIFIED`

- **定义**：仅修复、屏蔽或替换候选边上的信息后，下游目标失败消失的比例。
- **公式**：`CDE = 候选边干预后目标失败消失的样本数 / 接受干预的失败样本数`。
- **具体例子**：对 40 条预测高风险边分别 replay，修复边上传递的错误数据后有 30 条 Trace 的最终失败消失，则 CDE 为 75%。
- **论文作用**：把相关性排名推进到干预证据；仍需随机边和时间邻近边作为排他对照。

### 5.8 错误传播效应 — P0 核心，`INFERRED`

- **定义**：上游边携带错误时下游失败概率，相对将该边信息纠正/屏蔽时下游失败概率的变化。
- **公式**：可写为 `RiskEffect(e)=P(Y_fail|do(e=error))-P(Y_fail|do(e=correct))`。
- **具体例子**：在可控 replay 中，边 e 传递错误数据时下游失败率 80%，纠正该边后为 20%，则估计错误传播效应为 60 个百分点。
- **论文作用**：对应 CAPE 风险侧的可操作化；真实计算需明确干预和可比条件。

### 5.9 洞察贡献效应 — P0 核心，`INFERRED`

- **定义**：保留某条边上的正确信息，相对屏蔽该信息时任务成功率或质量的提升。
- **具体例子**：保留 critic→solver 的有效反例时任务成功率 85%，屏蔽该消息后为 60%，则该边的洞察贡献效应为 25 个百分点。
- **论文作用**：防止系统因“风险高”而永久剪掉同时具有高正向价值的边。

### 5.10 归因置信度校准误差（ECE / Brier Score）— P1 关键支撑，`INFERRED`

- **定义**：预测置信度是否与真实正确频率一致；ECE 比较置信区间与准确率差异，Brier Score 衡量概率预测平方误差。
- **具体例子**：系统给 100 条边都约 0.8 的因果置信度，但只有 55 条经 replay 证实，则该置信区间明显过度自信。
- **论文作用**：让系统在证据不足时选择“请求更多观测”或“不自动修复”，而不是强行行动。

### 5.11 归因解释可接受率 — P1 关键支撑，`VERIFIED`

- **定义**：专家在盲评中认为“证据 → 候选边 → 因果结论”链条完整、可理解且可行动的比例。
- **具体例子**：两名评审独立审查 50 条解释，协商后 38 条被判定为可接受，则可接受率为 76%；同时必须报告评审一致性。
- **论文作用**：补充 Edge F1，检验归因结果是否真正可用于排障。

### 5.12 标注者一致性（Cohen's κ / Krippendorff's α）— P1 关键支撑，`VERIFIED`

- **定义**：衡量人工标注在扣除随机一致后的可靠程度；两名标注者、名义标签可用 κ，多标注者或缺失值场景可用 α。
- **具体例子**：两名标注者对 100 条 Trace 的失败边标签表面一致率为 85%，计算 κ 为 0.72，则报告 κ=0.72，而不是只报 85%。
- **论文作用**：说明边级真值是否足够可靠；不能把仲裁后的最终标签反过来当成独立一致性证据。

### 5.13 长 Trace 性能衰减 — P1 关键支撑，`VERIFIED`

- **定义**：按 Trace 长度分桶后，归因准确性随步骤数增加的变化。
- **具体例子**：Edge Hit@3 在 `≤10`、`11–30`、`31–60`、`>60` 步四组分别为 90%、82%、65%、38%，表明方法在长链路上明显退化。
- **论文作用**：定位边级方法的适用边界，避免总体平均值掩盖长 Trace 失败。

## 6. 自治拓扑修复与闭环安全指标

### 6.1 修复成功率（Repair Success Rate）— P0 核心，`VERIFIED`

- **定义**：对已失败任务实施候选修复后，任务转为成功且满足约束的比例。
- **公式**：`Repair SR = 修复后成功的失败样本数 / 被修复的失败样本数`。
- **具体例子**：对 50 条失败 Trace 实施边重路由，32 条最终转为成功，则修复成功率为 64%。
- **论文作用**：是 CERA 闭环有效性的直接结果指标，但不能单独证明边归因正确。

### 6.2 错误抑制率 — P0 核心，`VERIFIED`

- **定义**：干预后，目标错误传播到下游的次数相对干预前减少的比例。
- **公式**：`Suppression = (传播次数_before - 传播次数_after) / 传播次数_before`。
- **具体例子**：100 次 replay 中，基线错误传播到最终 Agent 80 次，边隔离后传播 20 次，则错误抑制率为 75%。
- **论文作用**：直接衡量拓扑动作是否阻断失败路径。

### 6.3 洞察保留率 — P0 核心，`VERIFIED`

- **定义**：干预后仍能到达下游并被有效利用的正向信息占干预前正向信息的比例。
- **具体例子**：基线中 critic Agent 提供 40 条被最终答案采用的有效建议，隔离高风险边后仍保留 34 条，则洞察保留率为 85%。
- **论文作用**：与错误抑制率成对报告，避免通过“切断全部通信”获得虚假的安全提升。

### 6.4 误修复率（False Repair Rate）— P0 核心，`VERIFIED`

- **定义**：修复动作针对错误边、无必要执行，或使原本可恢复的任务变差的比例。
- **具体例子**：系统自动执行 60 次修复，其中 9 次经 replay 发现目标边并非原因，另 3 次使任务质量下降；若两类不重叠，则误修复率为 `12/60=20%`。
- **论文作用**：约束自治系统的过度干预；各类误修复应拆分报告。

### 6.5 回归率（Regression Rate）— P0 核心，`VERIFIED`

- **定义**：在原本成功的任务或独立回归集上，修复策略使结果从成功变为失败的比例。
- **具体例子**：将新拓扑应用于 200 个原本成功的任务，其中 8 个变为失败，则回归率为 4%。
- **论文作用**：证明局部修复没有破坏其他任务或信息路径。

### 6.6 回滚率 — P1 关键支撑，`VERIFIED`

- **定义**：部署或 shadow 验证中的修复动作因未通过门控而需要撤销的比例。
- **具体例子**：系统提出 50 次拓扑变更，10 次因质量下降触发回滚，则回滚率为 20%。
- **论文作用**：高回滚率可能说明归因不准、动作空间不合适或验证门槛过严，需要结合原因分布解释。

### 6.7 修复恢复时间（Time to Mitigation）— P0 核心，`INFERRED`

- **定义**：从检测到故障开始，到经过归因、候选动作、shadow/replay 验证并恢复服务的总时间。
- **具体例子**：检测 2 s、归因 4 s、replay 验证 10 s、拓扑切换 1 s，则 Time to Mitigation 为 17 s。
- **论文作用**：比基础设施 MTTR 更贴合 CERA 算法闭环，可进一步报告各阶段占比。

### 6.8 干预代价 — P0 核心，`VERIFIED`

- **定义**：修复引入的额外模型调用、Token、费用、时延、网络消息与计算资源。
- **具体例子**：一次边验证新增 2 次模型调用、3,000 Token 和 6 s 时延，则分别报告三项代价；不建议未经依据地合成为单一分数。
- **论文作用**：与修复成功率、误修复率组成收益—风险—成本三维评估。

### 6.9 Token 节省率 — P1 关键支撑，`VERIFIED`

- **定义**：修复或拓扑调整后，相对基线减少的总 Prompt 与 Completion Token 比例，二者应分别报告。
- **公式**：`Saving = (Token_base - Token_method) / Token_base`。
- **具体例子**：基线每任务平均 20,000 Token，修复拓扑后 15,000 Token，则总 Token 节省率为 25%；若成功率同时下降，则不能视为有效优化。
- **论文作用**：评价剪边、重路由和通信格式调整的经济性。

### 6.10 相对随机干预增益 — P0 核心，`INFERRED`

- **定义**：归因驱动修复相对等预算随机边修复的效果差值。
- **公式**：可报告 `ΔSR = RepairSR_CERA - RepairSR_random`，并给出置信区间。
- **具体例子**：相同干预次数下，CERA 修复成功率 64%，随机边修复为 28%，则相对随机干预增益为 36 个百分点。
- **论文作用**：排除“只要缩短链路或随便改图就会变好”的替代解释。

### 6.11 拓扑切换次数与振荡率 — P1 关键支撑，`INFERRED`

- **定义**：单位任务/时间内拓扑状态改变次数，以及同一边在隔离与恢复状态间反复切换的比例。
- **具体例子**：100 个任务中发生 30 次拓扑切换，其中 8 次是同一边在短窗口内“隔离→恢复→再隔离”，则可报告 0.3 次切换/任务及 26.7% 的振荡动作占比。
- **论文作用**：评价自治修复是否稳定，防止控制策略频繁抖动。

## 7. 统计报告与跨场景泛化指标

### 7.1 均值、标准差与 95% 置信区间 — P1 必报，`VERIFIED`

- **定义**：重复实验中同时报告中心趋势、离散程度与估计不确定性，不只报告最好一次。
- **具体例子**：三次运行 Edge F1 为 0.61、0.66、0.64，应报告均值约 0.637、标准差及 95% CI，而不是只写 0.66。
- **论文作用**：反映 LLM 与 Agent 非确定性；重复次数和置信区间方法需要预注册。

### 7.2 跨任务 / 跨架构泛化差值 — P1 关键支撑，`VERIFIED`

- **定义**：域内结果与 Cross-task、Cross-architecture 结果之差。
- **具体例子**：域内 Edge F1 为 0.72，跨架构为 0.48，则泛化下降为 0.24；应报告绝对差和相对下降，并分析边类型覆盖变化。
- **论文作用**：确定方法是否只适配某一 Agent 框架或固定拓扑。

### 7.3 预测 MAE / Spearman 相关 — P2 条件指标，`VERIFIED`

- **定义**：若使用廉价观测特征预测昂贵端到端结果，MAE 衡量数值误差，Spearman 衡量排序相关。
- **具体例子**：对 50 个 MAS 配置预测最终成功率，MAE 为 0.06、Spearman 为 0.81，表示平均误差 6 个百分点且排序相关较强；仍需报告校准和跨架构结果。
- **论文作用**：用于 M5 观测经济性，不属于 CERA 第一版必须完成的核心贡献。

### 7.4 统计与工程显著性 — P1 必报，`INFERRED`

- **定义**：同时回答“差异是否可能由随机波动造成”和“差异是否大到具有实际价值”。
- **具体例子**：CERA 将成功率从 70.0% 提升至 70.5%，大样本下可能统计显著，但若每任务额外增加 10 s 和 50% 成本，工程价值仍可能不足。
- **论文作用**：避免只凭 p 值或单一平均提升下结论；最小有意义效应需作者结合场景确定。`AUTHOR_INPUT_NEEDED`

## 8. 推荐的论文主结果指标集

为避免指标过多导致论文主线模糊，建议将指标分成以下三组。

### 8.1 主结果表（回答 CERA 是否有效）

1. Edge Precision / Recall / F1；
2. Edge Hit@1、Hit@3、MRR；
3. 反事实下游消除效应；
4. 修复成功率；
5. 错误抑制率与洞察保留率；
6. 误修复率与回归率；
7. 端到端任务成功率；
8. 干预代价与 Time to Mitigation。

### 8.2 可信性表（回答结论能否相信）

1. 请求—响应配对 Precision / Recall / F1；
2. Trace 字段完整率、Span 覆盖率、边重建 F1；
3. 可 Replay 率与原始证据保留率；
4. 标注者一致性；
5. 归因置信度校准误差；
6. 均值、标准差、95% CI；
7. 长 Trace 与跨架构分层结果。

### 8.3 工程代价表（回答系统是否可用）

1. 观测开销率；
2. Token、费用与单成功任务成本；
3. 端到端时延、P95/P99 与 DMR；
4. Goodput / SLO 达标率；
5. 回滚率与恢复时间。

## 9. 建议的最小对照组

| 对照 | 目的 |
|---|---|
| 无干预 | 给出自然失败与恢复基线。 |
| 随机边干预 | 排除“随便改图也有效”。 |
| 仅时间邻近边 | 排除因果边只是时间相关。 |
| 仅语义日志 | 测量系统级证据的增益。 |
| 节点级归因/修复 | 证明边级对象相对 Agent/Step 对象的价值。 |
| 错误类别级图 | 区分单条 Trace 的 Span 边与全局错误类型依赖。 |
| 静态剪边或仅节点剪枝 | 排除收益仅来自减少通信/缩短执行链。 |
| Prompt 修复 | 将拓扑修复与已有提示词修复路径比较。 |

所有方法应使用相同任务、模型版本、随机种子策略、干预预算和评测器；若无法完全相同，需要把差异列为有效性威胁。

## 11. 下一研究闸门

在开始大规模跑实验前，应先完成一个小型、可 replay 的 2–3 Agent 原型，并固化以下四项：

1. **边真值协议**：什么条件下 sequential、communication、data、responsibility、causal-propagation 边算作存在；
2. **失败与修复判据**：什么叫决定性错误、修复成功、误修复和回归；
3. **最小数据契约**：每条 Span/Edge 必须保存哪些 ID、时间、输入输出、配置、来源和证据等级；
4. **主指标预注册**：确定 5–8 个主指标、计算脚本、统计方法、分桶规则和对照组，避免看到结果后再挑指标。

只有请求—响应配对、Trace 完整性和边重建达到预先设定的准入条件后，才应进入 Edge F1 与自治修复评测；否则归因结果无法形成可靠的因果证据链。
