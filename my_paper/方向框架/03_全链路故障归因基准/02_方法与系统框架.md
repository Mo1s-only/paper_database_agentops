# 基准构建框架

## 1. 数据单元

每个 `run` 至少包含：

```text
manifest.json
task_spec/
agent_config/
trace/application/
trace/system/
environment_snapshot/
outcome/
labels/
replay/
license_and_privacy/
```

实际发布格式可调整，但字段语义必须版本化。

## 2. 证据等级

- O0：最终输出与任务判据；
- O1：Agent 输出序列；
- O2：输入、输出、消息、工具与配置；
- O3：O2 + 进程/文件/网络/资源等系统证据；
- O4：O3 + 可重放环境和受控干预接口。

基线必须在不同等级上分别运行，禁止把不可见证据泄漏给低观测组。

## 3. 真值层次

- `fault_injection_point`：注入位置，事实真值；
- `triggered`：故障是否真正触发；
- `responsible_agent/step`：导致失败的责任单元；
- `propagation_path`：错误被使用和放大的路径；
- `root_cause_type`：按预注册分类法编码；
- `counterfactual_validated`：干预后结果是否改变。

注入点不自动等于责任根因。例如注入发生但被系统正确处理时，不应标为失败责任。

## 4. 标注协议

1. 标注者先看 O2，不看方法预测；
2. 独立标注 Agent/Step/Edge 与置信度；
3. 用 O3/O4 证据复核争议；
4. 仲裁多因果、不可判定和证据不足样本；
5. 报告 Cohen's kappa 或 Krippendorff's alpha；
6. 保存标注指南、变更历史和不可判定比例。

## 5. 数据治理

- 原始 prompt、response、路径和密钥先分类再脱敏；
- 明确模型/工具许可、代码许可和数据再分发权限；
- 公开数据与受限数据分层；
- 为每个版本发布 Data Card、Evaluation Card 和 changelog。
