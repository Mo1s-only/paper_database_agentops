# 系统执行证据是否改善归因：下一阶段执行方案

日期：2026-10-27。基于同步后的 `d9de276`、进展v0.22、10/22关联报告和当前代码。用户已确定主题并授权由助手决定方案；本文交付执行计划，不启动新实验，也不把计划计为完成。旧累计API预算上限不再作为阻塞条件，成本审计与有界运行仍保留。

## 1. 本次决定

主问题固定为：**对于同一次多Agent任务失败，加入可追溯的系统执行证据，能否纠正完整应用trace下的错误归因，或把无法区分的解释缩小到有证据支持的故障机制和位置？**

“结论改变”本身不是收益：正确变错误是退化，错误换成另一个错误也不是改善。首先测证据收益，再研究算法改进。

第一阶段固定一个栈（现有Claude Code＋已配置模型接口＋AgentSight/eBPF）、两个Agent、短而可重放的外部程序任务。保留既有关联器、独立预测/评分接口；不重建整套Adapter，不同时铺开多个框架、复杂因果发现算法和大型公共基准。

输出定位分三个层次：

1. 故障机制/层级：应用决策、工具内部执行、环境条件，或证据不足。
2. 关联位置：Agent/Step/tool_call和实际故障组件；故障发生在某Agent调用的工具内，不自动等于Agent决策有错。
3. 支持与反证：哪些事件支持解释，哪些事件排除竞争解释，哪些仍未知。

即使B1与跨层组定位到同一个Bash步骤，若跨层组正确区分了工具内部错误与Agent参数错误，也单独记录为“机制细化”；不能伪装成Step准确率提升。

## 3. 第一批场景：两个目标故障、两种对照

共用流程：Agent A准备输入/任务契约 → Agent B选择并调用处理工具 → Agent B检查结果并提交产物。保留完整消息、工具参数与返回、框架已记录的stdout/stderr和结果工件。独立任务检查器判断最终产物，不依赖归因器。

### F1：工具内部选错执行程序

- Agent给出的工具参数与任务要求一致；工具内部调度配置使它实际启动另一程序/版本，产物格式合法但数值或功能不符。
- 竞争解释：输入/参数错、工具内部选错程序、下游使用错结果。
- 应用证据：原始请求、工具返回与产物；若现有日志已经暴露实际程序，完整保留。
- 系统证据：实际EXEC路径/参数、进程谱系、调用归属。预期程序路径来自预先公开的工具契约；二进制/脚本哈希来自工件清单，不冒称由eBPF读取。
- 修复操作：仅纠正该工具的后端选择，恢复同一任务初始状态后重跑；无关控制改变独立诊断操作，不改目标程序选择。
- 限制：路径不同只是偏离证据，要结合错误产物与真实修复结果支持责任。

### F2：子进程非零退出，但工具包装器报告成功

- 子进程普通非零退出；包装器返回success，下游拿不到有效结果或使用旧产物。
- 竞争解释：下游Agent处理错误、工具执行失败、环境条件导致执行失败。
- 系统证据：调用所属的EXEC/EXIT与普通退出码；配合应用语义识别“对外成功—内部失败”的矛盾。
- 初始可支持结论只到“工具内部子进程失败且失败未上报”。没有stderr或失败系统调用证据时，不进一步猜测权限、网络或内存根因。
- 修复分开评分：使子进程正确执行能否恢复任务；使包装器正确报告失败能否阻止错误传播。后者不一定让任务完成，不能都算task repair success。
- 加入至少一个不影响产物的非零退出诊断子进程作为干扰，避免算法见到任意exit!=0就判责。

### C1：纯应用语义错误

错误路由或错误输入参数导致失败，但程序按收到的指令正常执行。采用已有路由场景及独立判据改造，避免把`route_valid=false`这样的测试答案直接提供给归因器。

该组不预设系统证据有增益；检查归因器是否会被无关系统异常诱导，从应用错误误转向环境。

### C0：正常运行

沿用同一任务模板，关闭故障注入；保留真实后台/诊断事件。评估误报和无依据归责，避免只在失败任务上测“总能找到一个责任步骤”。

所有执行路径、run ID、配置名使用中性命名。`faulty`、`wrong_backend`等实验标签不进入算法可读路径；任务本身合法的参数和业务语义仍完整保留，不能因含有“error”字样就删去真实观测。

## 4. 证据对照：先受控桥接，再验证无hook适用性

沿用10/23规划的编号，不把受控桥接混入纯被动组：

| 条件 | 归因器可见证据 | 阶段 |
|---|---|---|
| B1 | 完整应用trace、任务契约、运行中可用的工具结果与工件 | 每一轮的主要基线 |
| B5 | 同一run的B1＋系统EXEC/EXIT等＋受控hook桥接关系及其来源 | 第一轮验证系统证据在可靠调用归属下有没有价值 |
| B3 | 同一无hook run的B1＋被动系统证据＋既有保守关联器给出的accepted/inferred/uncertain/abstain | 第二轮验证无需显式tool ID桥接时能保留多少收益 |
| B1+ | 应用trace＋增强工具包装器记录的实际子进程路径/退出结果 | 后续强对照：区分执行证据价值与eBPF采集方式价值 |
| B4 | 冻结预测后执行真实repair/control并检验结果 | 分别记录B3/B5来源，不能与初始归因分数混合 |

第一轮B1与B5来自**同一条真实采集运行**。B1中的原始应用内容不能因它“已经足够定位”而删减；hook产生的公开应用信息对两组保持一致。允许给B5的新增内容仅限明确声明的系统证据与关联关系。

第二轮必须实际关闭hook后重新采集，在每条新run内部比较B1/B3。只从hook运行里删掉关系标签，不能证明被动部署可行，因为exec argv可能仍有标记，hook也可能改变执行环境。hook on/off另作采集扰动与任务行为检查。

若只有B5有效：可以支持“带受控桥接的系统证据有用”，不能宣称“完全被动eBPF归因有效”。若B1+达到同样效果，则eBPF价值需要由接入成本、覆盖范围或独立观测能力解释，不能说它独有这些信息。

## 5. 如何归因：先固定一个可检查的方法

第一轮用一个固定模型归因器作为主诊断器，沿用现有可用接口，执行前冻结模型标识、提示词、采样设置和响应格式；不在开发样例表现不好时悄悄换模型。另保留简单规则诊断作为辅助检查，规则结果不替代主实验。

每个证据视图独立启动推理上下文，流程统一：

1. 识别任务失败表现与可观察的异常。
2. 生成少量竞争解释，允许没有充分依据的候选保持未决。
3. 对每个解释列出支持证据、矛盾证据、缺失证据。
4. 输出故障层级、组件、关联Step/tool、候选排序或拒答。

两组采用同一个提示模板，只替换证据区；相同的最大输出和推理预算。输入窗口必须容纳完整B1，不能为了容纳系统记录而截断B1；必要时使用固定、与真值无关的分块查询策略，并记录查询成本。主分析不把B1答案传给B5；顺序展示“新增证据如何修正解释”仅作辅助案例分析。

建议输出字段：

```text
prediction_status: located / unresolved / no_failure
failure_layer: agent_decision / tool_execution / environment / unknown
mechanism: 有证据支持的故障机制，允许unknown
location: agent_id, step_id, tool_call_id, component_id
candidates: 候选及排序
support_event_ids: 支持结论的事件
contradiction_event_ids: 排除竞争解释的事件
unknowns: 仍缺的证据
```

最初不要求一个未经校准的百分比置信度。事件引用做自动存在性及来源核验；“引用确实支持解释”需独立检查，不把引用存在等同于解释正确。

## 6. 数据工件和隔离

复用既有规范化事件与来源引用，仅新增视图、预测与真实干预记录：

```text
run/
  raw/                  原生应用日志、AgentSight数据库、eBPF流
  observations/         规范化事件、语义内容、关联状态
  views/b1.json         完整应用证据
  views/b5.json         同run应用＋系统＋受控关联（第一轮）
  predictions/          独立上下文的预测及哈希
  evaluation/           独立任务判据、责任/机制真值、评分
  interventions/        候选操作、执行前快照、真实重跑与control
  manifest.json         配置、采集版本、输入/输出哈希和成本
```

`evaluation/`及注入配置不可由预测器读取。算法只能访问冻结视图或白名单证据查询，不能自由遍历含真值的仓库。对原始标签置换、删除后，视图内容及哈希必须不变；原始文件完整哈希放审计层，避免标签变更通过元数据进入输入。

hook、被动系统事件、应用日志、独立oracle各自标来源。跨层缺失不靠后处理补造；被捕获运行集合、可关联集合、可评分集合分别列分母。所有失败采集和无法归因的run都登记，不能只保留成功对齐样本。

## 7. 真值与真实干预怎么做

- 在看预测前固定工具契约、故障注入、任务成功判据及允许的正确机制/位置集合。区分故障源、显现步骤与下游传播位置；允许多个合理归因，不强迫所有故障都归责于Agent。
- 独立oracle直接运行产物检查或行为测试，不读取预测的解释；注入点提供候选真值来源，但还需实际运行结果与机制检查，不能把注入参数原样当作唯一因果责任。
- 预测生成并冻结后，按候选位置及公开工具契约选择修复操作；修复表覆盖可操作位置，不只给gold位置提供修复。
- 从同一故障前快照恢复，真实重跑目标工具及所需下游；保存新的执行记录与产物。不能通过编辑原trace的status或output使判据变真。
- 独立运行无关位置控制和不改动重跑控制，检查自然波动。若控制也恢复，修复证据不具区分力；若修复无效，保留失败，不改真值迎合预测。
- 先固定工具输入做局部复验；有依据后再从上游检查点重跑Agent流程。局部程序修复成功不能自动外推为端到端Agent任务必然成功。
- 真实任务的验证入口应新建；保留`blind_counterfactual.py`的合成协议用途和声明，不改名冒充真实反事实引擎。

## 8. 第一批规模与执行顺序

以下均为建议执行规模，不是已完成样本，也不用于承诺统计显著性。

### M0：原始工件与协议预检（约1个工作日）

交付`run_inventory.json`、字段白名单、两种视图契约、开发案例规格。先复用可访问历史原始工件核查接口；只有报告的案例不补造B1/B5。若新原始run无法找到，直接按授权采集新案例，不长期等待旧数据。

验收：来源齐全的样例可导出同run视图；标签变更不影响输入；模型推理无法读到真值；明确记录hook及事件能力边界。

### M1：两个故障的机制样例（约2–3个工作日）

每类先做1个故障样例和正常对照，完成程序执行、采集、关联、独立任务判据及实际重跑。在第一类通过后再做第二类。先确定性本地执行验证机制，再接真实双Agent，不用LLM调用代替工具语义检查。

验收：出现预期失败表现，且关键EXEC/EXIT可靠归属；正常对照不被误判。该阶段样例用于开发、调试，不纳入冻结效果集。

### M2：冻结探索性pilot（约3–4个工作日）

计划12条真实双Agent任务运行：F1、F2、C1、C0各3条，使用不同输入/产物或后端配置；不是把同一确定性trace复制三遍。每条生成B1与B5，形成12组成对输入。失败样本9条，正常样本3条，不能报告成12条失败轨迹。任务运行、CLI会话、模型请求和诊断调用分别计数。

先冻结开发后的代码和提示，再运行这12条；若修复影响预测的实现错误，旧pilot保留并重新编号，不能挑选新旧结果拼表。首轮每视图一次独立诊断作为机制探索；下一轮对模型不稳定性进行全样本统一重复，不只重试不理想答案。

验收：逐例输出B1/B5判断变化表，必须包括错误改正、正确退化、仍不确定、无变化，以及系统证据引用。12条只用于决定方向和定位失败模式，不用于宣称总体显著优越。

### M3：真实性与必要性核查（约2–3个工作日）

对F1/F2已有候选执行真实repair/control/no-change。若B5确有正确纠偏，再在实际无hook条件下跑少量配对任务比较B1/B3；同时检查增强包装器日志B1+是否达到同样结果。若无收益，先分析原因，不继续扩样以追求正结果。

正式样本量、第二模型、第二框架和并发共享资源故障，在pilot之后依据效应、变异、可复现性决定。

## 9. 预先固定结果口径

逐run表至少包含：任务是否失败、B1/B5预测状态、故障机制正确性、位置正确性、错误归责、支持引用、采集/关联状态、修复/控制结果和成本。

主要报告：

- **纠正数**：B1明确错误 → B5正确。
- **退化数**：B1正确 → B5明确错误。
- **消歧数**：B1不确定 → B5正确；与“错误被纠正”分开统计。
- **合理退让数**：B1错误且确定 → B5拒答；属于风险下降，不计作正确定位。
- **机制与位置准确性**分别报告，避免Step不变却把解释改善写成定位提升。
- 覆盖率、已回答样本错误率、全体样本正确率同时报告；正常样本单独报告误报率。
- 关键证据删除后的预测变化作补充诊断；不能把删除后变差单独作为因果证明。

成对样本的统计单位是原始任务run。系统事件数、重复诊断次数和干预重跑数均不能扩充独立任务N。正式阶段再在冻结任务拆分上做配对区间估计；不在12条探索pilot上用显著性包装强结论。

## 10. 决策门

1. **至少有可复查的纠偏/消歧案例，且真实局部干预支持机制：**继续验证跨输入稳定性、无hook关联和强基线；只支持限定场景有效。
2. **只有定位不变、解释机制更准确：**论文贡献转向机制诊断分辨率，不能宣称责任Step准确率提高。
3. **B1已经足够，系统信息重复：**保留无增益结果；不削弱B1来制造收益。审查选定场景是否确实有应用观测盲区。
4. **B5有效但B3无效：**明确结论依赖受控桥接，关联可用性成为条件；不抹去hook成本。
5. **新增系统噪声增加错误归因：**先改进证据筛选与歧义处理，再冻结新版本验证，不直接扩大数据量。
6. **repair和control都成功或都失败：**不声称已验证决定性责任；检查干预、环境重置与oracle。

下一项实际交付固定为 **M0的可评分运行清单＋B1/B5输入契约＋两个案例的冻结规格**。随后进入M1，而不是再次开展全目录扫描或泛文献调研。
