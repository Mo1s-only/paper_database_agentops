# 实验与统计计划

> **2026-10-22 修订：**硬件与跨架构安排见 `research_notes/2026-10-22-实验硬件与跨架构计划.md`。核心实验固定一个 Agent/观测栈和一个候选主平台；ARM/AMD 是主平台结果后的外部有效性扩展。旧 9/9 合成结果已发现标签条件逻辑，不是盲测准确率。

## 1. 数据设计

- 任务：至少覆盖代码/文件操作、检索总结、结构化决策三类。
- 系统：核心实验先固定一个 Agent/观测栈（Claude Code + AgentSight/eBPF）和一个候选主平台；保留 Agent、模型、工具、任务和随机性设置。ARM64/AMD 作为后续平台复现，不是启动主实验的必要条件。
- 故障：工具静默错误、错误消息传播、角色/路由错误、循环/掉队、外部依赖异常。
- 真值：优先由注入点和可执行任务判据产生；自然失败由两名标注者独立标注并仲裁。
- 分割：按任务模板或项目分组，避免同源 trace 泄漏到训练与测试。

## 2. 对照组

| 组别 | 可见证据 | 目的 |
|---|---|---|
| B0 | 最终输出/错误信息 | 最弱现实基线 |
| B1 | 消息与 Agent 日志 | 应用层基线 |
| B2 | AgentSight/eBPF 系统事件单独输入 | 系统层单独可提供的候选 |
| B3 | B1 + 系统事件 + provenance 状态 | 主比较：同一运行内 B3 对 B1 的增量 |
| B4 | B3 + 预测冻结后的 repair/unrelated-control 复验 | 可重放案例中的验证增量 |

## 3. 主指标

- Agent-level / Step-level / Edge-level Precision、Recall、F1、Hit@k、MRR；
- 证据链完整率、校准误差或 Brier Score；
- 反事实修复增益、误干预率；
- 诊断时延、额外 token、存储量、观测开销、单个正确诊断成本。

## 4. 统计计划

- 每个任务重复多次，报告 bootstrap 95% CI；
- 对配对样本使用 McNemar、Wilcoxon 或置换检验，按指标分布选择；
- 同时报告效应量与多重比较校正；
- 预注册主要比较 B4 vs B1，B4 vs B3；
- 分层报告故障类型、trace 长度、框架、模型和证据缺失率。

## 5. 消融

- 去除消息、工具、进程/文件/网络、拓扑边、认知候选；
- 取消边类型、候选切片或反事实验证；
- 注入不同配对错误率和时间戳扰动；
- 比较规则、传统分类器、图模型、LLM judge。

## 6. 停止条件

- P0 配对 Precision 未达到 0.95：停止跨层归因实验。
- 小型准入/pilot 未能稳定采集或完整证据无可解释增益：先检查标签、任务、关系质量与运行方差，再决定是否扩大样本。
- 反事实操作无法可靠复现：将论文主张降为 evidence-aware localization，而非 causal attribution。

## 7. 当前 pilot 状态

- 请求—响应配对：5 条受控 marker 调用，Precision/Recall 均为 1.000；
- 真实 AgentSight：已完成 attach 模式两 Agent 观测，能捕获 LLM、工具、进程、文件和网络事件；
- 旧合成故障矩阵与旧跨任务 gate：预测/反事实逻辑读取 `fault_type` 或 `task_name/spec`，其 9/9 仅为标签条件的 harness 试跑，不是盲测准确率或独立反事实效果；
- 新盲化协议：trace-only predictor、独立评分和 repair/control 在各 9 条合成夹具中通过协议检查；不作论文效果结论，详见 `lab/experiment/blind_attribution_protocol_20261022/protocol-report.md` 与 `lab/experiment/blind_counterfactual_protocol_20261022/protocol-report.md`；
- 真实主实验：已完成 1 条 `inventory-silent-tool` 两 Agent 受控 pilot；Agent/Step/Edge 均与 manifest 真值匹配，反事实仅完成离线任务判据回放，不能把该单条结果写成方法总体效果。

下一轮先在候选主平台完成硬件盘点和 AgentSight/eBPF smoke test，再做少量真实运行的采集资格 pilot。正式样本量依据注入成功率、事件丢失、运行间方差、配对效应和预算制定，不预设每类 10 次或总计 30–50 条。每次运行保存硬件/OS 清单、SQLite/原始流、统一 trace、独立真值、冻结预测、干预计划、评分和资源负载记录。

## 8. 主/次硬件平台与资源控制

- **候选主平台**：Intel 6326 双路、32 核/64 线程、503 GB RAM、8×RTX 3090、Ubuntu 22.04、Linux `5.15.0-131-generic`。用户提供配置，远程现场核验后才能写为已验证实验环境。
- **次平台**：双路 Ampere Altra、160 核、249 GB RAM、Ubuntu 22.04、Linux `5.15.104`，用于 ARM64 观测栈兼容性和受控任务复现。表格未列 GPU；需确认“一张 Ampere ARM 架构卡”是否指此 CPU 节点。
- **可选 AMD 平台**：AMD9555 节点与 4 张 AMD 卡的准确型号、显存、主机映射、RAM/内核/驱动/ROCm 尚未提供，暂不进入正式矩阵。
- 主实验固定 Agent 框架、模型端（API 或本地二选一）、CPU/GPU 分配、并发和负载策略。若使用 Claude Code/API，RTX/AMD 卡不计作 Claude 推理资源；若使用本地 LLM，冻结 checkpoint/hash、推理引擎、量化、采样参数和卡分配，并独立分组。
- 记录 CPU/GPU 利用率、温度/功耗策略、驱动/运行时、collector 版本、eBPF 丢事件和 observer 开销。各平台分别计算 B1/B3 配对效应，不跨机器拼接进程树，也不直接比较未经校准的 monotonic clock。
- ARM/AMD 不兼容时记录边界，不阻塞主平台结论，不从别的节点补造缺失证据。

## 9. API 成本闸门

- 所有 schema、归因和反事实代码先用零 API 的确定性 harness 验证；
- 真实运行按“预检 → 每类 1 次 pilot → 扩展”的阶段推进；
- 每次运行从 Claude JSON 日志读取实际成本，并记录到 `cost.json`；
- 未通过预算预检或 pilot 质量检查时，停止扩展，不执行 30–50 条批量调用；
- 当前已有 11 个可计价运行，累计 `0.944059 USD`；原定 `1.00 USD` 硬停止线只剩约 `0.055941 USD`，后续真实调用暂停，除非重新明确预算。
- 首个 2-call case 已完成，实际成本 `0.218846 USD`；`service-error-propagation` 和 `retrieval-routing-error` 尚未运行。
