# 后续实验数据结构与归因流程设计

日期：2026-10-27。本文为INFERRED设计建议；示例数据全部为说明用合成数据，不是新实验结果。沿用已有application event v0.2、跨层关联记录、查询收据与真值协议，不修改历史结果或现有schema。

## 1. 实验问题与边界

RQ：相对只使用应用日志，加入有来源和质量标记的跨层证据，是否改善多Agent责任步骤定位，并减少证据不足时的错误归因？

对象：具有工具调用和显式交接的双Agent工作流，先覆盖静默工具错误、错误信息传播、路由错误。主输出为责任Step候选与证据；Agent为辅助，传播路径只在有真实依赖及相应真值时评价。错误位置、错误引入点、传播点、可修复位置分别记录，不能混为一谈。

主要风险：系统证据可能只有身份确认价值，并不增加语义辨别力；受控工具输出的consistent=false等字段会使归因过于简单。需要区分可观测错误信息和只供评分的注入元数据。

## 2. 每次运行的建议目录

```text
run-<id>/
  manifest.json                 # 版本、运行条件、来源哈希、预算与采集配置
  observation/
    raw/                        # 原始框架日志、AgentSight SQLite等
    events-v0.2.jsonl           # 已有生命周期/身份/时钟事件
    alignments.jsonl           # 已有应用—系统关联
    contents.jsonl             # 新增：白名单语义内容及来源
    objects.jsonl              # 新增：消息/文件版本等数据对象
    dependencies.jsonl         # 新增：产生、消费、调用等观察依赖
    evidence-package.json      # 已有查询、观察关系与收据
    quality-gate.json          # 当前输入可用于哪些推断
  prediction/
    attribution.json            # 候选、证据、未决项与拒答
  intervention/
    replay-plan.json            # 由候选生成，不读取评测真值
    replay-results.jsonl        # 实际执行后才产生
  evaluation/                   # 评分器独占；算法输入不挂载
    truth.json
    scores.json
```

这是建议逻辑布局，不表示这些文件当前均已实现。原始日志如有真值、注入说明或其他敏感字段，必须先经白名单导出；只将truth移出目录并不充分。预测器读取的manifest、文件名、ID和证据指针也需审计。

## 3. 数据对象

### 已有事件与关联

events-v0.2.jsonl继续保存run/event/session/agent、step/tool_call、process和clock。现有schema不允许额外属性，语义内容采用侧表，不把字段随意塞入原协议。process映射仍继承accepted/inferred/abstain；不将共享tool ID成功等同直接PID映射完成。

### 新增内容侧表

示例：

```json
{
  "content_id": "content-a1-result",
  "run_id": "demo-run",
  "session_id": "session-a",
  "step_id": "a1",
  "tool_call_id": "tool-a1",
  "kind": "tool_result",
  "payload": {"reported_status": "healthy"},
  "source_ref": "framework-event-17",
  "visibility": "attribution_input"
}
```

实际应增加内容哈希、来源定位与读取校验；正文可按授权脱敏或存为可访问引用。哈希不能替代语义内容。工具参数、返回值、消息正文、外部状态观察分别记录，不将注入真值写入payload。

### 数据对象与版本

```json
{
  "object_id": "handoff-v1",
  "run_id": "demo-run",
  "kind": "file_version",
  "logical_name": "handoff.json",
  "version_id": "write-event-21",
  "producer_step": "a2",
  "consumer_steps": ["b1"],
  "content_ref": "content-handoff-v1",
  "evidence_refs": ["write-event-21", "read-event-30"]
}
```

同文件路径不等于同版本。并发写入、覆盖、缓存读取或缺少读取证据时，消费关系应保持inferred/abstain。仅observed read系统调用也未必证明Agent语义上采用了内容，需区分读取与决策使用。

### 观察依赖

```json
{
  "relation_id": "dep-handoff",
  "run_id": "demo-run",
  "source": {"kind": "step", "id": "a2"},
  "target": {"kind": "step", "id": "b1"},
  "relation_type": "data_dependency",
  "object_id": "handoff-v1",
  "evidence_status": "direct",
  "evidence_refs": ["write-event-21", "read-event-30"],
  "causal_claim": false,
  "responsibility_claim": false
}
```

direct仅指文件版本交接证据直接，不代表错误传播的因果责任已经确认。内部节点键使用(run_id,session_id,step_id)，工具键也带session；示例短ID只为阅读。

### 任务与结果

算法可以读取实际任务要求及可见最终输出；独立评分oracle、注入位置、参考答案和额外隐藏状态不得进入算法。若运维任务允许查询外部服务状态，该查询需记录为公开观察或主动取证动作，并对方法统一权限和成本；不能把隐藏真值伪装成系统证据。

## 4. 归因流程

1. 验证输入与质量门：拒绝哈希不匹配、生命周期断裂或明确无效输入；局部缺失不自动升级为不存在。按子图标记可用范围。
2. 建观察依赖图：保留身份/包含/调用/产出/消费边；只有数据交接证据才能跨Agent连接。时间仅用于约束，时间相近不产生依赖或责任。
3. 确定失败表现：从实际输出和允许使用的任务检查取得失败节点。失败表现不是根因。
4. 沿有依据的依赖反向切片：得到可能影响失败的候选Step，保留并行分支、遗漏边和不确定关联。原输入已有缺失时，搜索范围不声称完整。
5. 逐候选审计：检查输入、操作、输出与任务要求之间的矛盾，区分错误引入、传播、恢复和观察到的失败。确定性规则优先，无法规则判断时可使用固定模型接口；模型必须引用证据，不能把自身判断作为真值。
6. 排序和拒答：先使用可解释的约束与排序元组，如有独立矛盾依据、与失败的可达性、关系支持强度。排序分数不是校准概率；同等解释保留多候选，不强行选择唯一根因。
7. 受控重放：修正候选处的行为/返回，保持上游状态、外部输入和其他可控条件，再让下游重新执行。记录哪些条件固定、哪些随机。对照包含不干预重放、无关位置干预，必要时比较替代候选。
8. 生成新归因输出与独立评分：不修改观察图的causal_claim。预测落盘并固定哈希后，评分器才加载truth。

## 5. 贯穿示例

合成工作流：a1获得工具报告healthy；a2写handoff-v1；b1读取该版本；b2按照healthy输出NO_RESTART；实际任务失败。

只有以上信息时，不能确认a1错误：服务可能确实健康。观察图仅得到a1→a2→b1→b2依赖候选路径。若采集到任务允许的独立状态探针down，并且确认同一服务、同一状态版本及时间条件，则可形成a1结果与状态观察矛盾的证据，优先检查工具/Agent A的交接环节。

责任粒度要分开：工具错误返回、Agent A错误转述、Agent B错误使用，各自可能发生。若A准确转发了错误工具结果，可定位到A的工具步骤，但不能不加说明地称为A推理错误。若无独立状态证据，输出证据不足或多候选，而不是从评测真值补一个down。

修正a1返回值为down后若下游变为RESTART并满足任务要求，只能支持该处修正对该失败有作用；不能单凭翻转证明它是唯一根因。应排除固定重启等无关补救也能成功的解释。

## 6. 输出契约建议

```json
{
  "run_id": "demo-run",
  "status": "candidate_supported",
  "failure_step": "b2",
  "candidates": [{
    "agent_id": "agent_a",
    "step_id": "a1",
    "rank": 1,
    "suspected_role": "error_introduction",
    "evidence_refs": ["tool-result-observation", "independent-state-probe"],
    "dependency_relation_ids": ["dep-1", "dep-2", "dep-3"],
    "confidence_probability": null,
    "limitations": ["alternative causes not excluded"]
  }],
  "validation": {"status": "not_run"},
  "abstain_reason": null
}
```

本示例假设独立状态观察可用，validation未执行。没有证据时用status=abstain或partial，保留候选集合与具体不足。传播路径只能标为observed_dependency_path或candidate_propagation_path，验证前不称verified_causal_path。

## 7. 最小实验与判断门

比较条件：B0末端错误/位置启发式；B1应用日志；B2同一归因算法+应用依赖；B3同一算法+已有跨层证据；B4=B3+质量约束/拒答；B5可选候选重放。增量实验固定模型、提示、可见任务信息和预算，分别报告实际输入token，避免将更多上下文或不同调用次数混成方法增益。

指标：Step Top-1/Top-k、Agent准确率；无条件正确率、回答覆盖率、已回答错误率；候选路径在有效标签子集的匹配；证据引用有效率、耗时与成本。轨迹及其扰动版本按原始run分组拆分，不能当独立样本；报告配对差异和置信区间。覆盖率下降本身不能说明方法改善。

先运行小规模pilot排除泄漏、错误映射和过简故障，pilot不承担统计泛化结论。正式样本量依据pilot方差、最小有意义差异和预算再定，不预设虚假的录用级样本数。

下一研究门：在同一真实任务中，跨层证据是否真的解决了应用日志无法区分的候选？若只是重复已有信息，应如实报告，再研究其在缺失或身份冲突时的效用。
