# AgentOps 研究进展 v0.1｜2026-09-21

## 1. 当前研究方向

面向 LLM 多智能体系统，建立一条可审计的 AgentOps 故障分析链路：

```text
运行时观测 → 结构化执行轨迹 → 故障归因 → 根因诊断与定位
```

核心对象不是单个模型的最终答案，而是多 Agent 在任务执行过程中的消息、工具调用、状态转移、依赖关系和最终失败之间的关系。

## 2. 证据状态

### VERIFIED：已经具备的材料

- `Reference paper/01_agent_observation/` 已整理 AgentOps、AgentSight、AgentMonitor、AgentTrace 等观测与追踪材料。
- `Reference paper/02_failure_attribution/` 已整理 Who&When、CDC-MAS、EDGE、MAST、TraceElephant 等归因、错误依赖和失败分类材料。
- `Reference paper/03_diagnosis_localization/` 已整理 Watson、eInfer、Beyond Natural Language 和 Tools Fail 等诊断相关材料。
- 本地已有 AgentSight 与 Watson 的代码、测试和运行结果，已归档到 `lab/`。
- `Reference paper/literature_index.md` 已建立论文—链路—用途索引。

### INFERRED：基于现有材料的研究判断

- 观测、归因和诊断在现有工作中经常被分别处理，跨层证据如何支持同一条可验证 RCA 链仍有研究空间。
- 只输出“哪个 Agent 出错”不足以支撑工程诊断；需要同时给出责任步骤、触发证据、传播路径和定位置信度。
- 完整执行轨迹对归因有价值，但完整记录会带来隐私、成本、存储和跨框架适配问题，因此“记录什么、何时记录、如何最小化”本身可以成为方法设计的一部分。

### UNVERIFIED：尚未证明的部分

- 还没有在统一任务集上证明跨层观测比只看最终输出、只看消息日志或只用 LLM judge 更准确。
- 还没有确定一个稳定的故障本体、标注协议和跨任务评测集。
- 还没有证明诊断结果能够转化为有效修复、重试、回滚或 Agent 重配置。
- AgentSight/Watson 的本地实验材料目前支持原型复现和证据提取，不能直接当作新方法的有效性结果。

## 2.1 已完成的 AgentSight + Watson 复现工作

以下内容来自 `lab/agentsight/` 和 `lab/Watson/` 中的脚本、报告及原始产物，状态标为 `VERIFIED`；它们是复现和流程验证结果，不等同于新方法的论文级效果。

### AgentSight：真实 Agent 运行观测

- **环境**：Windows 10 + WSL2，内核 `6.18.33.2-microsoft-standard-WSL2`；AgentSight 1.0.31；Claude Code 2.1.270；Node.js 22.14.0；DeepSeek `deepseek-v4-pro`。
- **任务**：让 Claude Code 创建并读回 `hello.txt`，只开放 Write/Read 工具，不开放 Bash 和网络工具。
- **观测结果**：验证脚本 13/13 断言通过，退出码为 0。
- **捕获证据**：进程树 12 个节点、30 条审计事件、3 条 LLM 调用、3 条 token 记录、2 个工具调用、2 个网络端点；会话记录约 16 秒，数据库共 67 行。
- **关键价值**：在不改 Agent SDK、不架设代理的情况下，同时得到进程、文件副作用、工具调用、模型调用、prompt 和 token 统计，为后续“观测—归因—诊断”提供了执行轨迹基础。
- **工程发现**：WSL2 默认缺少 tracefs 挂载会导致 eBPF 探针静默失败；这已在诊断脚本中记录并绕过。

证据位置：`lab/agentsight/source/thesis_adapter/test/result.md`、`lab/agentsight/results/upstream/session/` 和 `lab/agentsight/source/thesis_adapter/test/verify.sh`。

### Watson：离线流程与真实 API demo

- **离线流程验证**：运行 4 种故障场景（`accept`、`wrong`、`judge_reject`、`alternating`）× 4 个候选数（k=1/3/5/10），共 16 组确定性实验；覆盖输入导出、候选生成、严格答案匹配、消融、judge、汇总、预算耗尽和缺失输入审计。
- **离线实验边界**：使用 `FakeClient`/`ScriptedClient` 和合成调用，不调用真实模型；16 组不是 16 个真实任务，不能据此声称模型准确率或推理忠实性。
- **AgentSight 数据审计**：读取已有 `session.db`，确认当前样例存在 response 但缺少配对 request；不完整记录被保留并跳过真实重建，没有用不配对输入/输出伪造成功。
- **真实 API demo**：2026-09-20 使用 DeepSeek Flash 完成两个自建文本决策任务（库存 `REORDER`、服务 `RESTART`），主 Agent、消融、候选、judge 和汇总共 12 次请求，无失败、无重试；实际 token 为输入 901、输出 350，按记录价格上界估算费用 ¥0.004602。
- **真实 demo 边界**：仅两个自建任务，未运行 MMLU/SWE-bench，不包含 eBPF 采集，也未验证通用推理准确率；严格文本匹配、单次离散消融、同模型 judge 和缺少独立人工验证仍是限制。

证据位置：`lab/Watson/docs/thesis/实验说明.md`、`lab/Watson/results/raw/offline_experiment/`、`lab/Watson/results/raw/real_demo/20260920T095310948675Z/`。

### 对当前主线的意义

这两组工作已经形成一个可运行的纵向原型：AgentSight 提供系统级执行证据，Watson 对可获得的调用记录进行旁路重建和一致性判断。当前仍缺少的是把 AgentSight 的多源事件映射到 Watson 的诊断输入，并在同一批带责任标签的失败任务上测量归因与定位效果；这正是下一阶段需要补齐的连接层，而不是把已有 demo 当成闭环结果。

## 3. 建议收敛后的研究问题

### RQ

在多智能体任务失败时，能否利用跨层、可追溯的执行轨迹，可靠识别责任 Agent、责任步骤和根因类型，并在观测成本受限时保持可接受的诊断准确率与延迟？

### Object

具有消息传递、工具调用和多轮协作的 LLM 多智能体工作流；失败包括任务失败、工具静默错误、错误传播、循环/掉队和最终结果不满足约束。

### Intervention

设计一个统一的执行证据模型与诊断管线：

1. 从运行时采集消息、工具、状态、时序和依赖信号；
2. 构建 Agent—步骤—工具—结果的执行图；
3. 先检测异常，再进行责任归因；
4. 对候选根因执行反事实删除、重放或局部验证；
5. 输出带证据链、置信度和定位粒度的诊断报告。

### Measurement

- 观测：事件覆盖率、丢失率、时间/存储开销、跨框架迁移成功率；
- 归因：Agent-level / step-level Top-1、Top-k、MRR、宏平均 F1；
- 定位：根因类型准确率、证据链完整率、反事实验证通过率；
- 工程价值：诊断延迟、人工排查时间、修复/重试成功率、误报率；
- 成本：每任务 token、日志字节数、额外模型调用次数。

### Baseline

- 最终输出或错误信息直接判断；
- 只使用消息/对话日志的 LLM judge；
- 规则和时间顺序基线；
- 图结构/错误依赖基线；
- 现有归因方法和完整轨迹方法（以 Who&When、CDC-MAS、EDGE、TraceElephant 等本地材料为对照）。

### Boundary

第一阶段不声称解决开放世界的所有 Agent 故障，不覆盖无法获得任何执行证据的黑盒系统，也不把“诊断出根因”与“自动修复成功”等同。真实隐私数据和高风险外部动作应单独做安全审查。

## 4. 是否值得发论文

### 结论：值得，但必须收窄贡献

当前方向有论文潜力，理由是它同时连接了 AgentOps 观测、MAS 失败归因和可验证诊断三个已有研究群；本地文献库中已经存在清晰的基线和未闭合接口。仅仅把 AgentSight、Who&When、Watson 等模块串起来则不足以形成新论文，容易被评价为工程集成。

更可发表的贡献形态是以下三者至少占两项：

1. **方法贡献**：提出跨层执行证据模型或可验证诊断算法，而不是简单调用 LLM judge；
2. **基准贡献**：构建有完整轨迹、明确责任步骤和根因标签的可复现实验集；
3. **实证贡献**：证明观测粒度、证据缺失和反事实验证如何影响归因与定位，并提供成本—准确率曲线。

### 方向评分（1–5）

| 维度 | 分数 | 判断 |
|---|---:|---|
| 新颖性 | 4 | 跨层观测到可验证诊断的闭环仍有空间；单点观测或单点归因已有较多工作。 |
| 可行性 | 4 | 已有 AgentSight、Watson 代码和运行材料；难点是统一数据模型与标签。 |
| 证据可得性 | 3 | 可以注入故障并生成轨迹，但真实 MAS 数据、人工标签和跨框架验证仍缺。 |
| 论文契合度 | 5 | 与现有 AgentOps、观测、归因和诊断笔记高度一致。 |
| 风险控制 | 3 | 范围过宽、归因标签主观、LLM judge 偏差和实验规模是主要风险。 |

### 最可能的审稿质疑

- 贡献是否只是已有工具和提示词的拼接？
- “根因”如何定义，谁来标注，如何处理多因果和责任链？
- 观测信号增加后，准确率提升是否只是因为泄露了更多答案信息？
- 在不同 Agent 框架、模型和任务上是否仍有效？
- 诊断结果是否真的减少了人工调试时间，而不只是提高了一个离线分数？

## 5. 专利前景

有一定专利可能，但专利点应落在可实施的技术方案，而不是“用 AI 做 Agent 诊断”这一抽象目标。更具体的候选是：

- 一种面向多智能体执行图的分层采集与自适应采样方法；
- 一种融合消息、工具、状态和依赖边的故障责任定位方法；
- 一种通过局部重放/反事实删除验证根因的诊断系统；
- 一种根据诊断置信度自动选择继续观测、重试、回滚或人工介入的闭环系统。

专利新颖性、创造性和权利要求范围需要进行正式专利检索；当前只能标记为 `AUTHOR_INPUT_NEEDED`，不能据此断言可授权。论文应优先形成可公开的评测协议和实验结果，专利则应在公开前先与导师/学校知识产权流程确认。

## 6. 下一阶段研究闸门

在进入大规模实现前，先完成一个最小闭环：

1. 选定 2–3 个可复现实验框架和 3 类可注入故障；
2. 固定事件 schema：`task / agent / step / message / tool / state / dependency / outcome`；
3. 为每次失败标注责任 Agent、责任步骤、根因类型和证据区间；
4. 实现“只看最终输出、只看消息、完整轨迹、完整轨迹+反事实验证”四个基线；
5. 只有当完整链路在归因准确率、定位准确率或人工调试时间上产生稳定优势，才把预测/早期预警扩展为第二贡献。

当前最关键的缺口是统一数据 schema 和可信标签，而不是继续堆叠更多论文或模型。
