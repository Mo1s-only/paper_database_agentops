# AgentOps 实验工作台：页面说明与使用指南

适用版本：Observatory 2.0。核对日期：2026-10-23。

这份说明对应重建后的本地平台，按照页面实际提供的功能编写。文中的样例来自已保存运行；样本数、费用和关联结果只属于相应运行。

## 1. 先理解三个概念

| 概念 | 页面中的例子 | 用途 |
| --- | --- | --- |
| 实验名称 | `错误传播 · 第 2 次验证` | 便于自己识别，可以重复 |
| 数据集／受控场景 | `error-propagation-v1`、`trail` | 决定输入是什么，以及可以执行哪种实验 |
| 运行 ID | `run-20261023-154718-2cd83726` | 唯一标识一次执行，用于区分每次结果 |

同一个名称、同一个数据集可以执行多次，每次获得新的运行 ID，并保存自己的数据库、过程记录和报告。

打开某次运行后，四个页签都跟随这个运行 ID。切换页签是在查看同一次执行的不同证据；切换运行才是在查看另一次实验。

一次运行需要分别回答四个问题：

1. 输入是什么，能否打开原始文件？
2. 是否执行了模型调用，调用是否成功？
3. 应用工具事件是否关联到系统记录？
4. 任务产物是否齐全，是否有可计算的场景评分？

这些问题可以得到不同答案。例如，API 会话成功、工具关联成功，但模型漏写结果文件，整次运行仍可能显示“部分完成”。

## 2. 启动平台

在 PowerShell 中执行：

```powershell
cd C:\Users\Administrator\Desktop\论文方向\web_coding\agentops_thesis_observatory
powershell -ExecutionPolicy Bypass -File .\Start-Observatory.ps1
```

默认地址是 [http://127.0.0.1:8780/](http://127.0.0.1:8780/)。端口被占用时，启动器会选择相邻可用端口，并打印、打开实际地址。以后以启动器提供的地址为准。

启动器会复用同一工作区的新版服务。仅打开平台、查看记录、预检、刷新和重新扫描，都不会发起模型 API 调用。

## 4. 左侧导航栏

### 4.1 所有运行

显示平台已登记的独立运行，包括历史导入和本平台新执行的运行。

- 搜索框：按名称、运行 ID 或数据集查找。
- 状态筛选：查看已完成、部分完成、失败、运行中等记录。
- 名称或右侧箭头：打开该次运行详情。
- 运行数量：登记记录的数量，不代表成功次数或论文实验样本量。

例如，想核对历史成功样本，可以搜索 `real-canary-20261022-45`；想查自己刚执行的记录，可以搜索填写的实验名称。

### 4.2 新建实验

进入配置页面，选择名称、类型和输入，再预检、启动。具体步骤见第 10 节。

### 4.3 最近运行

提供最近登记运行的快捷入口，包含名称、时间和状态。完整列表在“所有运行”中。

### 4.4 重新扫描按钮 ↻

重新扫描本地历史工件并更新索引。当你在平台外增加实验目录，或补充了原始报告，可以使用这个按钮。

重新扫描只是登记和读取已有工件，不会重跑实验。

### 4.5 本地服务连接状态

底部显示平台是否连接到新版本机服务。连接失败时，先确认后台服务正在运行，并使用启动器输出的地址。

## 5. 每次运行顶部的信息

| 区域／按钮 | 作用 |
| --- | --- |
| 实验名称 | 这条运行的可读名称 |
| 运行 ID | 核对本次结果最重要的标识 |
| 数据集 | 这次使用的登记输入 |
| 时间 | 本次创建时间；有结束记录时也显示结束时间 |
| 状态标签 | 执行状态，不自动等同于论文验收结论 |
| 历史导入／本平台运行 | 说明记录来自已有实验目录，还是新版平台启动 |
| 刷新 | 重新读取这次运行的工件 |
| 再运行一次 | 预填名称与数据集，进入新建页面；确认后创建新 ID |
| 停止运行 | 运行中才出现，发送停止请求并保留已有工件 |

“再运行一次”需要在新建页检查执行类型。历史运行的旧配方不一定是当前目录项提供的执行方式。例如，历史 TRAIL 样本可能做过真实 API 派生回放，而当前 `trail` 目录项提供的是本地输入结构复核。重复按钮不会自动复现所有历史命令。

停止运行不会撤销已经发出的请求，也不会撤销已产生的费用；已有调用信息仍保留在该次运行中。

## 6. “总览与证据”页签

这是阅读一次运行的主要入口。建议从上到下看状态提示、API、关联、输入，再看详细记录。

### 6.1 提示／错误区域

存在缺失或失败时显示具体阶段与原因。例如：

- `capture_authentication`：采集到认证失败的请求。
- `task_output`：缺少任务应生成的文件，无法完成场景评分。
- 后处理相关阶段：原生事件解析或关联分析没有完整完成。

提示区描述的是某个阶段的问题。仍应查看下面各卡片，确定哪些阶段已经留下有效证据。

### 6.2 真实 API 证据卡片

| 字段 | 含义 | 阅读方法 |
| --- | --- | --- |
| 会话成功数 | CLI 摘要记录的成功会话数 | `2 / 2` 表示两个 CLI 会话都完成 |
| HTTP 2xx 记录 | SQLite 中响应状态为 2xx 的 LLM 记录数 | 可进入 `llm_calls` 查看 HTTP 状态码 |
| HTTP 错误 | SQLite 中观测到的错误响应记录 | 401 通常对应认证失败；429 对应限流或配额问题 |
| 模型 | 会话摘要或数据库记录的模型名称 | 核对本次实际记录的模型 |
| 费用 | CLI 报告的美元费用 | 摘要不完整时显示未知；不是供应商最终账单 |
| 调用摘要 | 打开本次 `capture-summary.json` | 核对会话、用量和结果字段 |

一个 CLI 会话可能有多轮模型交互。因此，`2 个会话`与`5 条 HTTP 200`可以同时成立。数据库中的 HTTP 记录数也不直接等同于去重后的供应商计费请求数。

常见显示状态：

- **已确认**：已有成功会话及对应摘要证据。
- **无需 API／本地核验**：所选类型执行本地输入检查。
- **请求失败**：已观测到请求，但响应失败，例如 HTTP 401。
- **未知／待核验**：缺少足以确认调用完成的工件。

“未知”不是 0；“无需 API”也不是调用失败。

### 6.3 跨层关联卡片

展示原生应用工具事件与系统语义工具记录的关联情况。

- **原生 ID**：从 Agent 原生日志解析出的工具调用 ID 数量。
- **系统 ID**：系统侧工具记录中可用于对齐的 ID 数量。
- **工具匹配数**：卡片优先展示 `session-and-tool`；没有该模式时使用已有的 `shared-tool-id` 结果。
- **原始关联报告**：查看这次运行的逐模式结果及来源范围。

`3 / 3 工具匹配`表示实际观测到的 3 个原生工具调用得到匹配。若任务配方原本期望 4 次工具调用，这个数字并不说明模型完成了全部 4 步；仍需检查原生 Trace 和任务产物。

### 6.4 工件可追溯程度

当前检查输入来源、API/CLI、数据库和跨层工具关联四类证据。

`4 / 4 项有证据`表示这四类存在可用证据。它不是任务准确率，也不是论文研究达标率。对于本地输入复核，API 和系统采集属于不适用项，不应要求它与真实跨层实验有相同的卡片结果。

### 6.5 跨层关联模式图

每一行是一种方法；右侧两个数字依次是 `accepted / abstain`。

| 模式 | 检查什么 | 结果边界 |
| --- | --- | --- |
| `shared-tool-id` | 原生工具 ID 是否对应唯一系统工具记录 | 证明工具身份匹配 |
| `session-and-tool` | 进一步检查应用会话到系统进程映射及工具归属 | 证明相应会话范围内的工具身份关联 |
| `process-and-tool` | 按通用进程与工具证据规则关联 | 需要该模式自己的证据条件，不能由其他模式通过代替 |
| 受控 Bash 进程桥 | 使用显式 hook 工具 ID 标记与 eBPF 进程谱系核对 | 属于受控插桩结果；按实际 Bash 桥接证据展示 |

- `accepted`：这条关系满足当前方法的证据条件。
- `abstain`：证据不足，方法拒绝给出确定关联。
- 未知：没有相应结果工件，不能当作已评测后得到 0。

绿色通常表示已匹配，浅灰表示 abstain；受控 Bash 桥使用单独颜色。条形长度按本图数值缩放，比较不同运行时以右侧数字为准。

例如，历史 run45 的语义工具匹配是 4/4；受控进程桥只有两个 Bash 被接受，两个 Write 拒判。它们衡量的关系不同，结果可以同时成立。

### 6.6 系统采集记录图

展示当前 SQLite 各表的真实行数。总览最多展示七类计数；完整表清单在“数据与 SQLite”页签。

条形越长，只表示该表记录更多。不能由行数直接推断模型能力、监控精度或因果归因效果。

对于输入复核，可能只看到 `input_records`，它表示本地输入检查记录，并非系统监控事件。

### 6.7 工具 ID 匹配证据表

有逐条关联工件时才显示，包含：

- Agent 与会话 ID。
- 原生工具调用 ID。
- 已匹配或拒判状态。
- 对应 SQLite 行的精确引用。

点击“查看精确引用”展开目标位置；点击“查看 tool_calls”进入本次数据库对应表。可以据此逐条核对，而不只看汇总数字。

### 6.8 任务与归因结果 · 应用侧

有场景评分报告时才显示，列出故障类型、责任 Agent、责任步骤、责任边和传播边等字段与冻结真值的匹配结果。

这里的“本场景精确匹配”只适用于报告中的样例范围。一个受控场景的精确匹配不能直接作为其他数据集上的泛化准确率。

受控故障实验可能预期任务出现错误。例如，场景故意让服务状态被错误传播，下游做出错误决策；观察到这个预设故障，可以是实验按设计执行的结果。

如果必要文件缺失，例如没有 `decision.json`，平台不生成虚构评分，而是在提示区说明。此时本模块可能不出现。

### 6.9 本次使用的真实输入

显示输入名称、ID、形态、原始文件路径、记录数及执行方式。“打开原始文件”会在新标签页显示支持查看的登记文件。

对于受控场景，“1 个受控场景”指一个任务定义。源文件是 Python 脚本，可以包含多个 `SCENARIOS` 配方；查看时找到所选 ID 对应的定义。例如，`error-propagation-v1` 对应服务观测、`handoff.json` 交接与下游决策流程。

对于历史公开样本派生回放，本次实际输入可能是一个冻结的 `workspace/public-input.json`。页面另有公开来源链接时，可继续查看其来源样本。

### 6.10 证据检查与运行过程

“证据检查”逐项说明有证据、不适用或待核验的原因。

“运行过程”是平台、采集器和分析阶段的事件记录，例如排队、启动、采集、解析、关联和报告生成。它用于回答程序执行到了哪一步，与原生 Agent Trace 分开阅读。

## 7. “Trace 时间线”页签

### 7.1 顶部统计

- **事件／span 数**：当前加载的会话和工具区间数量，不是 HTTP 请求总数。
- **已记录 Agent**：当前 Trace 中出现的 Agent 数量。
- **记录覆盖时长**：有时间信息的区间，从最早开始到最晚结束所覆盖的时间。

### 7.2 横向时间线

每行可能是一段会话，或一次 Bash、Write 等工具调用。横向位置表示在本次记录中的相对开始位置，长度表示记录时长，不同 Agent 使用不同颜色。

点击某行可以展开原始记录字段，查看工具 ID、会话、时间及来源引用。

这些时间来自原生流的本地接收记录，不能直接当作已经校准的 eBPF 执行时钟。缺少时长时，页面使用浅色整行表示。

### 7.3 没有 Trace 时

先看本次类型：

- 输入结构复核没有运行 Agent，Trace 为空是正常情况。
- 真实实验正在采集或尚未完成解析时，Trace 可能暂时不可用。
- 历史记录可能只剩数据库或摘要，没有原生事件文件。

继续到数据页、文件页核对现有来源。不能用另一条运行的 Trace 填补本次空缺。

## 8. “数据与 SQLite”页签

### 8.1 真实输入与原始文件

可通过“打开原始文件”查看支持的完整文件，也可点“直接预览源文件”在页面内阅读。页内预览最多显示前 40,000 字符；超出部分可通过原文件入口查看。

### 8.2 数据库和数据表选择器

先选择数据库，再选择数据表。表名后的行数来自本次数据库的实际查询。

表格当前最多预览 100 行，底部显示总行数与是否截取。总数大于预览行数不表示数据丢失。

常见表的含义：

| 表名 | 保存什么 | 适合核对的问题 |
| --- | --- | --- |
| `llm_calls` | 采集到的模型请求／响应语义记录 | 提供方、模型、HTTP 状态、错误类型是什么？ |
| `tool_calls` | 系统语义工具记录 | 原生工具 ID 是否存在？所属会话、PID 是什么？ |
| `token_usage` | 已解析的 token 用量记录 | 是否捕获到用量数据？ |
| `network_targets` | 聚合的网络目标 | 是否观测到相关网络端点？ |
| `process_nodes` | 进程节点与父子关系 | 本次进程谱系有哪些节点？ |
| `audit_events` | 进程、文件等审计事件 | 系统侧实际记录了哪些行为？ |
| `resource_samples` | 资源采样 | 本次采集留下了哪些资源样本？ |
| `input_records` | 本地输入逐条复核结果 | 读了多少行，哪些行结构有效或异常？ |

表名和列随原始实验而变化，不要求每条运行都有上述所有表。

表格中的 `NULL` 表示原字段没有值。`[REDACTED]` 表示页面对相应内容做了脱敏；它不表示原数据库没有该字段。数据库预览使用只读连接。

网络目标数量是聚合目标数，不能当成 API 调用次数；也不能只凭网络目标存在就认定调用成功。

### 8.3 运行产物内容

存在任务输出时，可以展开查看 `handoff.json`、`decision.json`、`route.json`、`result.json` 或冻结的公开输入等 JSON。

如果某个应有文件未生成，它不会出现在产物列表中。结合页首提示或场景状态报告判断缺失原因。

## 9. “图表与文件”页签

### 9.1 图片区

直接渲染该次运行可展示的 SVG、PNG 等图片。点击图片可打开原图。

平台会依据本次数据库行数生成图表。例如，`charts.svg` 或“平台按本次证据生成/evidence.svg”表示对已有数据的可视化，不是新的实验观测。

两张图片如果都基于同一数据库，应看作同一来源的不同展示，不重复计入独立实验结果。

### 9.2 原始工件与报告

| 文件／入口 | 作用 |
| --- | --- |
| `state.json` | 本次配置、状态与过程字段 |
| `invocation.json` | 启动配方、预算、凭据来源等非密钥信息 |
| `capture-summary.json` | 会话、成功情况与 CLI 用量摘要 |
| `real-alignment-comparison.json` | 各种跨层关联模式的结果 |
| `scenario-validation-report.json` | 有充分任务产物时生成的场景预测与评分 |
| `scenario-validation-status.json` | 场景评分的可执行状态、缺失产物等说明 |
| `audit-report.json` | 本地输入结构复核结果 |
| `report.md`、`report.json` | 本次运行的汇总报告 |
| `lifecycle.jsonl` | 平台执行阶段事件 |
| 平台按本次证据生成的报告 | 从当前已有工件生成的可读摘要 |

具体存在的文件以该次列表为准。文件页提供支持预览的工件，不是整个目录的无限制镜像；私有诊断和凭据文件不会全部显示。

报告是对原始工件的整理。需要验证结论时，继续检查对应的采集摘要、SQLite 行和关联报告。

## 10. 新建实验：完整操作步骤

### 10.1 当前可以选择的实验

以下是本次核对时的目录内容；本地数据修改后，记录数以页面即时读取为准。

| 实验类型 | 输入 ID | 当前数量 | 新启动是否调用模型 API |
| --- | --- | ---: | --- |
| 真实 API 跨层实验 | `error-propagation-v1` | 1 个受控场景 | 是，Agent A/B 两个会话 |
| 真实 API 跨层实验 | `routing-error-v1` | 1 个受控场景 | 是，Agent A/B 两个会话 |
| 已有输入结构复核 | `who-when` | 184 条 | 否 |
| 已有输入结构复核 | `trail` | 148 条 | 否 |
| 已有输入结构复核 | `agenttrace` | 550 条 | 否 |
| 已有输入结构复核 | `alignment-stress-1000` | 1000 条合成输入 | 否 |

目前“已有输入结构复核”只检查本地记录的 JSON 对象结构并生成输入数据库，不重新运行上游适配器，不重新执行公开轨迹中的任务，也不产生新的系统跨层评测样本。

### 10.2 操作顺序

1. 点左侧“新建实验”。
2. 填写可识别的实验名称，例如 `错误传播 · 第 3 次真实验证`。
3. 选择实验类型，再选择该类型下的输入。
4. 阅读右侧输入说明，打开原文件确认内容和执行方式。
5. 页面自动预检；需要时点“重新检查”。
6. 对真实 API 实验，阅读本次范围并勾选“允许本次实验调用真实 API”。
7. 当按钮下方显示可以创建运行时，点“启动实验”。
8. 页面自动进入新运行详情，记下新的运行 ID。
9. 观察运行阶段；页面可见时约每 2 秒刷新运行列表和活动运行证据。
10. 结束后依次核对 API、跨层关联、原生 Trace、任务产物与报告。

真实实验会在后台调用 Ubuntu WSL，不需要手动打开交互式 WSL 窗口。原生 Trace 和最终报告需要相应采集、解析阶段完成后才会出现。

### 10.3 预检分别检查什么

| 预检项 | 检查内容 |
| --- | --- |
| 输入文件 | 登记的源文件是否存在 |
| 采集器配方 | 是否是已经验证的源码构建采集器版本 |
| 本次调用范围 | 运行配方和预算记录是否可读取 |
| WSL 环境 | Ubuntu、root、Python 与 Claude CLI 是否可用 |
| API 凭据 | 既有凭据能否解密并交给 WSL |
| 运行兼容性 | 采集脚本、CLI 参数、工具 hook 和内核条件是否满足 |
| 运行状态 | 是否已有另一条真实实验占用执行位置 |

本地输入复核所需检查更少。预检本身不调用模型；它也不能提前保证供应商一定接受凭据或模型一定按任务要求生成输出。

当前真实实验优先使用既有 DPAPI 别名 `test`。这里的 `test` 是密钥存储别名，不是把字符串 `test` 当作 API key，也不是模拟模式。

### 10.4 按钮无法点击时

直接查看按钮上方的原因，通常包括名称为空、没有可用输入、预检未结束、预检失败、未勾选本次 API 确认，或另一条真实实验仍在运行。

历史上曾经成功或失败，不会单独成为禁止再次启动的条件。

### 10.5 费用怎样看

当前真实跨层配方规划两个 CLI 会话，各设置 $0.05 软预算；新建页显示本次规划 $0.10。

软预算不是供应商侧绝对硬限制，完成后的 CLI 报告费用也不是最终账单。费用信息缺失时，平台保留“未知”。同一会话可能包含多轮请求，CLI 内部也可能发生重试。

## 11. 状态、颜色和空缺怎样判断

### 11.1 页首执行状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 排队中 `queued` | 已创建记录，等待执行 | 等待启动阶段 |
| 运行中 `running` | 正在采集或后处理 | 看运行过程和已产生的数据库记录 |
| 已完成 `completed` | 当前配方要求的执行与检查已完成 | 继续按实验类型解释结果 |
| 部分完成 `partial` | 留下部分有效结果，但某项必要产物或分析存在缺口 | 看提示阶段及缺失内容 |
| 运行失败 `failed` | 启动、请求或执行没有成功完成 | 看具体错误及已保存证据 |
| 已中断 `interrupted` | 控制器重启等原因使运行没有正常收尾 | 核对已保存调用和费用，确认后再创建新运行 |
| 已停止 `stopped` | 收到停止请求并结束 | 已有工件仍可查看 |

绿色、蓝色、黄色、红色帮助定位状态；具体含义以卡片文字和原始报告为准。离线核验“已完成”与真实双 Agent 实验“已完成”代表不同的执行范围。

### 11.2 区分四种常见显示

| 显示 | 应怎样理解 |
| --- | --- |
| 0 | 相应数据已经记录或查询，数值为零 |
| 未知／未记录 | 当前缺少可确认的数据 |
| 不适用／无需 API | 当前实验类型不执行该项 |
| 未生成 | 所需阶段未执行、未完成或没有对应工件 |

有 SQLite 不一定调用过 API；输入复核也会生成 SQLite。没有 SQLite 也不能单独证明没有发出过 API 请求。应综合查看本次类型、调用摘要和 HTTP 记录。

## 13. 常见问题

**为什么一次实验显示调用成功，但整次状态不是“已完成”？**

因为还可能缺少任务文件、部分采集记录或后处理报告。先看具体失败阶段，再判断 API 与关联已经完成到哪一步。

**为什么图中会有 accepted 和 abstain 同时出现？**

方法可以接受证据充分的关系，同时拒绝证据不足的关系。也可能是不同方法有不同适用条件，不能把一条模式的结果套到所有模式。

**为什么再次运行后与历史结果不完全一样？**

每次调用都可能产生不同的模型行为、工具次数、时长与捕获覆盖。比较时确认输入、类型、采集器、模型和运行 ID，按各自工件解释差异。

**为什么文件列表里有图，但原目录没有同名图片？**

“平台按本次证据生成”的部分工件是按已有数据即时生成的展示。页面同时保留原始路径和原始报告入口，便于区分展示与采集来源。

**为什么数据库总数和屏幕上的表格行数不同？**

数据库数量、数据表数量、表内记录数是三种不同计数；表格预览最多 100 行。查看表格底部的总行数说明。

**为什么刷新后看不到别处刚补的历史实验？**

先使用左侧“重新扫描实验工件”；运行详情页的“刷新”主要读取已选中的这条运行。

## 14. 结果文件保存在哪里

新运行统一保存到：

```text
C:\Users\Administrator\Desktop\论文方向\lab\experiment\observatory_runs\<运行ID>\
```

真实跨层运行通常包含 `capture/` 目录，其中保存本次采集、SQLite、解析与关联工件；本地输入复核通常在运行根目录生成 `input.sqlite`、`audit-report.json` 等文件。

历史运行保留在原来的实验目录中。文件页的“本次运行所在目录”可以帮助定位。

平台自己的索引、服务日志位于项目 `runtime/`。它们用于运行工作台，与每次实验的原始工件分开保存。

## 15. 推荐的每次阅读顺序

1. 确认页首运行 ID、实验类型和输入。
2. 打开真实输入文件，确认本次到底运行什么。
3. 看 API 会话、HTTP 响应和费用证据。
4. 看各关联模式和逐条工具 ID 引用。
5. 看原生 Trace、数据库表及任务输出。
6. 有场景报告时，再看应用侧评分及其样本范围。
7. 记录缺少的证据，决定下一次需要补采什么。

平台组织和展示证据，不自动替你判断整个论文方向或研究贡献已经达标。
