本轮问题：显式应用事件、共享工具 ID 与有范围的进程身份，能否支持可审计的工具步骤关联，并在冲突或缺失时拒绝确定？

## 2. 代码与输入

| 文件 | 本轮用途 |
|---|---|
| `application_events.py` | 应用事件单条校验、会话/步骤/工具生命周期校验、排他写入与严格读取 |
| `schema/application-event.schema.json` | 可供其他组件采用的单条事件契约；完整流语义仍由运行时检查 |
| `observation-scope.template.json` | 绑定系统文件及 host/boot/PID namespace/clock 的待填模板 |
| `align_application.py` | 校验来源哈希，解析显式身份，按共享工具 ID 与范围约束对齐 |
| `run_application_gate.py` | 生成明确标注的合成双 Agent 输入、走 SQLite 规范化与 manifest 管线，执行协议矩阵 |
| `test_application_events.py` | 生命周期、冲突、标签隔离、顺序不变性与日志保护测试 |

基线输入为 12 条应用事件（两个 session 各 6 条）和 4 条合成 SQLite 记录（两个进程、两个工具）。进程、时间和工具 ID 都是夹具值。应用 writer 发出的 UUID 是本次夹具事件标识，不是外部服务商标识。

## 4. 保留的失败与修复

初次端到端运行保存在 `application_runs/20261010-v010/`：17/20 场景通过。失败原因是扰动脚本假设系统记录交替按“进程、工具”排列，而 SQLite 规范化实际按表输出，导致三种扰动施加到了错误记录。

已改为按来源行标识选择待扰动对象，并新增顺序不变性回归测试。修复后在全新目录重跑得到 20/20；初次失败没有覆盖或删除。该问题属于测试夹具定位错误，不能当作真实 Agent 故障，也不能忽略未修复时的失败结果。

## 5. 输入与输出隔离

匹配器只接收完整应用事件文件、已有白名单系统证据、manifest 和 scope。它不读取故障真值或旧分析结论。应用字段集禁止责任标签与任意附加内容；系统侧 validator/derived 记录不能供给共享 ID。

每条应用身份来自显式事件。accepted 关联包含应用行号、系统工具行和进程行；未被接受的条目不宣称跨层身份已确定。`application-trace.jsonl` 本身是显式应用记录，不等于所有系统事件都获得了身份。

新增 scope 是采集端声明式元数据。校验哈希与范围相等只能证明“输入符合协议”，无法证明 host/clock 声明是实测事实。这是下一阶段真实采集必须补齐的证据来源，不能事后手填以通过检查。
