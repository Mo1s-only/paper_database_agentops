`VERIFIED_FOR_THIS_REAL_CANARY`：本轮已实际调用现有 DeepSeek 端点，通过 Claude Code 执行两个 Agent 会话，并同时采集 AgentSight。完成原生工具事件解析、来源追溯和共享工具 ID 对齐。

CLI 会话数、原生响应 ID 数与 AgentSight LLM 表行数不是同一指标。这里不能把 2 会话写成只有 2 次模型请求，也不能把 7 条观测直接当作 7 次独立成功调用；原生响应 ID 也不是重试/网络请求的完整审计。

任务产物核查：route 要求 `required_available=1`；真实 Bash 返回 `available=0`；Agent B 写入 `observed_available=0, satisfied=false`。这说明受控工具错误被实际执行、任务要求未满足且最终判断与工具返回一致，不等于根因归因已经正确完成。

## 4. 实际暴露的问题

### 系统观测缺少一次 Read

原生日志中 Read 的共享工具 ID 为 `call_00_JMkQydrA66TBioCgrVH41847`。AgentSight 工具表未包含它；本次 debug 原始流中也没有该 ID 文本。LLM 响应记录中未找到该结构化工具 ID。

无法据此确定丢失发生在探针、传输重建还是事件解析。当前只标记观测缺口，不从应用日志复制一条“系统观测”来填补。

### 两侧 PID 与时间不直接可比

启动器 PID 为 A=81、B=133；通过共享工具 ID 找到的系统记录 PID 分别为 346、411。应用侧命名空间来自 `/proc/self/ns/pid`，不能据此断言 AgentSight 的内核 PID 属于同一编号范围。

两组候选对应的启动器执行时间估计与 AgentSight 进程起始时间还分别相差约 895 ms、894 ms。其原因与稳定性尚未验证，不能直接减去固定偏移来声称时钟校准完成。

因此最终系统 scope 明确记录命名空间映射未知、时钟转换未校准。保留严格模式全部拒绝的结果；新增显式的 `shared-tool-id` 模式，只根据同一运行、同一 host/boot、唯一原生工具 ID 建立工具身份关系，并明确不验证进程归属或时钟对齐。没有悄悄放宽原有严格模式。

## 5. 本轮代码完善

| 文件 | 作用 |
|---|---|
| `capture_real_application.py` | Linux 下真实双 Agent 采集、观察器预检、受限会话、流式日志及启动元数据 |
| `parse_claude_native.py` | 从实际 system/init、assistant/tool_use、user/tool_result、terminal result 解析生命周期 |

| `validate_real_application.py` | 回到原生工具 ID 和原始 SQLite 检查共享键，验证任务工件 |

解析出的 step_id 形如 `native-tool:<真实工具ID>`，是适配器定义的工具跨度，不是框架原生推理步骤。事件时间来自本机逐行接收时间，不冒充原始工具开始时刻。每条转换记录另有原生行号、接收时间行号与启动元数据引用。
