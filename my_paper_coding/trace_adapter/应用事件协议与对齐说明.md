# 应用事件协议与身份对齐｜v0.1

2026-10-10 真实接入更新：新增 `capture_real_application.py`、`parse_claude_native.py` 与 `prepare_real_alignment.py`，已用真实 Claude 原生工具事件验证；详见 [真实实验报告](真实应用对齐实验报告_2026-10-10.md)和[完整进度实验报告](完整真实进度实验报告_2026-10-10.md)。原严格规则仍为默认。`--identity-mode shared-tool-id` 只验证唯一共享工具 ID；`session-and-tool` 进一步要求 application session 在系统 LLM 记录中对应唯一 PID，且工具记录指向同一 PID。两者均不声称时钟校准或因果责任，不得把它们通过写成严格 PID/时间模式通过。下文合成验证段落保留为协议初版记录。

## 1. 目的与边界

v0.9 已能关联系统侧证据，但历史应用日志只有最终结果。本协议让新工作流显式记录应用身份，再用共享工具调用标识和进程范围连接系统观测。

协议覆盖 session、step、tool 的开始/结束生命周期；不宣称覆盖所有框架消息、LLM 请求或任务语义。事件身份说明“谁执行了什么步骤”，不说明“谁应对失败负责”。真实采集端尚未接入；当前端到端验证均为 `synthetic_fixture`。

## 2. 单条事件契约

机器可读定义见 `schema/application-event.schema.json`；运行时严格校验和生命周期检查位于 `application_events.py`，仅依赖标准库。

| 字段 | 含义与要求 |
|---|---|
| `schema_version` | 固定为 `agentops-application-event-v0.1` |
| `evidence_kind` | `runtime_observed` 或 `synthetic_fixture`，单一文件不允许混用 |
| `run_id` | 本轮实验标识，必须与 manifest 一致 |
| `event_id` | 应用事件唯一标识，不能重复 |
| `session_id / agent_id` | 由应用明确提供；同一 session 不允许中途换身份 |
| `sequence / timestamp_ms` | session 内从 0 开始连续序号；同一时钟域的毫秒时间，不允许倒退 |
| `event_type` | session.start/end、step.start/end、tool.start/end |
| `step_id` | 非 session 事件必须有值，session 内不重用 |
| `tool_call_id` | 仅工具事件有值；必须是真实工具调用的共享标识，不能为匹配而补造 |
| `process` | host_id、boot_id、pid_namespace、pid、start_ms，共同区分机器、启动、容器和 PID 复用 |
| `clock` | domain 与有界 uncertainty_ms；不确定度未知时无法通过新协议 |

事件不接收 prompt、response、工具参数或责任标签字段，避免把无关内容和评估真值带入身份解析。需扩展时应升级协议，不能偷偷增加字段。

生命周期检查：session 先开始后结束；step 先开始再进入工具调用；tool.end 必须对应同 step 的 tool.start；开放工具未结束时不能结束 step；开放 step 未结束时不能结束 session。session 中的 process 与 clock 固定。重试不能复用旧调用 ID，进程重启应建立新 session。

## 3. 写入与读取

`EventWriter` 用排他创建保护旧文件，每次写入前验证事件并刷新到磁盘；`finish()` 检查闭合。异常中断的部分日志保留，但严格读取器会拒绝把它当作完整日志。每个 session 使用独立 writer，不支持多个线程/进程同时写同一文件。

调用方必须提供测得的进程身份和时钟信息。writer 不测量宿主环境，不会把自身 PID 当成被观测 Agent PID，也不会从最终摘要猜测步骤。没有完整真实事件时应报告缺失，不应从预期工具顺序生成“观测”。

`read_events()` 返回事件与完整性摘要；应用轨迹保留文件行号。JSON Schema 描述单条记录；会话闭合、序号连续、唯一性等仍需运行时验证。

## 4. 系统观测范围

`observation-scope.template.json` 是待采集端填写的旁路元数据；空值模板不能作为有效证据使用。`source_path/source_sha256` 必须绑定 manifest 中同一次运行的原始系统文件。host、boot、PID namespace、clock 必须来自采集时的实测记录。

这份元数据当前是声明式输入，哈希只能锁定文件，不能证明 host/clock 声明本身真实。真实采集适配器和元数据实测来源仍需实现、核验；不能事后手填相同字符串来“通过”检查。

## 5. 接受与拒绝条件

`align_application.py` 只对 `tool.start` 做跨层身份判断：

1. 严格验证完整应用日志；校验应用工件属于 manifest 的 `app_log` 且哈希一致。
2. 系统文件必须通过 v0.9 白名单/哈希检查；scope 必须绑定该原始文件。
3. run、证据类型、host、boot、PID namespace、clock domain 一致。
4. 工具共享 ID 对应唯一系统工具记录，工具 PID 与显式应用进程一致。
5. 进程启动时间在声明的不确定度内对应唯一进程记录，且应用事件时间区间与系统工具时间均处于该进程生命周期内。
6. 同一个系统工具事件不能同时分配给多个应用身份。

缺失共享键或范围冲突时 `abstain`；重复候选、PID 冲突、时钟区间越界或多重所有者时 `uncertain`。只有条件全部满足才 `accepted`。匹配结果保留应用行号、系统工具行和进程行。

输出 `application-trace.jsonl` 的身份来自显式应用记录；只有 `application-alignments.jsonl` 中 accepted 条目建立跨层工具关系。`tool_identity_gate_passed=true` 仅代表该批非空 tool.start 全部被规则接受。`unified_trace_ready` 仍为 false，不代表全步骤对齐或归因完成；Precision/Recall 未有独立标签时保持 null。

## 6. 离线复现

在仓库根目录运行，输出目录必须是新目录：

```powershell
python my_paper_coding/trace_adapter/run_application_gate.py --output my_paper_coding/trace_adapter/application_runs/my-new-protocol-check
python -m unittest discover -s my_paper_coding/trace_adapter -p 'test_*.py' -v
```

脚本生成两个合成 Agent 的 12 条应用事件、4 条合成 SQLite 观测，经过现有 SQLite 规范化器和 manifest 哈希检查，再执行共享标识对齐及 20 项协议场景。所有 fixture 明确标记为合成；它不会启动 Claude、AgentSight 或付费 API。

已有冻结输入也可以单独运行：

```powershell
$appGate = 'my_paper_coding/trace_adapter/application_runs/20261010-v010-r2'
python my_paper_coding/trace_adapter/align_application.py --manifest "$appGate/run.json" --evidence "$appGate/evidence-events.jsonl" --app-events "$appGate/synthetic-application-events.jsonl" --scope "$appGate/observation-scope.json" --output "$appGate/new-alignment-review"
```

读取旧的 Claude 最终结果日志会被拒绝；本协议不把旧文件升级或补造成完整事件。
